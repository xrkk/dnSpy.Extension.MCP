## 1. 背景与目标

当前项目是在 dnSpy 进程内运行的 MCP 扩展，已经提供静态分析、有限 IL/元数据修改、托管动态调试、HTTP MCP 服务和 Python stdio 客户端。新需求是在独立分支中增加接近 dnSpy Assembly Editor 的**结构化程序集编辑能力**，并让宿主机 AI 能够通过 MCP 完成编辑、审查、验证、提交、恢复和导出闭环。

主要使用场景是在隔离的 VMware 或 VirtualBox 恶意代码分析环境中编辑和调试不可信 .NET 样本。系统需要优先保证：不覆盖原始样本、失败状态可辨认、操作可追溯、能够恢复到检查点，以及最终回报不把未验证结果描述为成功。

## 2. 术语

- **实时模块**：当前加载在 dnSpy 文档树中的 `ModuleDef`。
- **私有工作副本**：编辑事务独占、尚未提交到实时模块的程序集副本。
- **编辑事务**：从开始、应用结构化操作、审查到提交或回滚的一次完整编辑活动。
- **检查点**：包含源基线、规范化语义操作、验证证据、输出身份和谱系关系的持久恢复记录。
- **谱系**：从一个完整基线开始，由父子检查点组成的编辑历史树。
- **部分提交**：实时模块已经修改，但对应检查点尚未成功持久化的 `committed_without_checkpoint` 状态。
- **结构性错误**：会导致元数据、IL、资源关系或程序集结构无效，不能安全写出或重新加载的错误。
- **风险确认**：AI对非结构性兼容风险作出的明确接受，并在最终回报中列出影响范围和理由。

## 3. 正式需求目标

### 3.1 编辑事务与结构化编辑

| ID | 正式需求 |
|---|---|
| REQ-001 | 系统必须提供完整的编辑事务生命周期，至少覆盖开始、应用操作、统一审查、提交和回滚；未提交操作只能存在于私有工作副本中。 |
| REQ-002 | 系统必须支持常用类型和成员的结构化增删改，包括类型、方法、字段、属性、事件、参数、泛型参数、标志、签名、方法体、局部变量和异常处理结构。 |
| REQ-003 | 系统必须支持已确认的高级结构化元数据编辑，包括泛型约束、Custom Attribute、MethodImpl/Override、类型布局、Marshal、P/Invoke、Security Declaration 和字段初始数据。 |
| REQ-004 | 系统必须支持以 C# 编辑方法或类型，并把编译结果导入目标模块；该能力必须包含编译诊断和嵌入式调试信息处理。 |
| REQ-005 | 系统必须支持程序集及模块身份相关的结构化编辑，包括程序集名称、版本、区域性、模块名称、AssemblyRef 和入口点。 |
| REQ-006 | 系统必须支持托管资源和 Win32 资源的查看、导入、导出、增加、删除和替换，并维护 Win32 图标组所需的结构关系。 |
| REQ-007 | 系统必须将经过审查的事务提交到 dnSpy 实时模块，并在提交成功后建立对应检查点；失败不得被报告为完整成功。 |
| REQ-008 | 系统必须通过统一审查步骤返回操作差异、结构验证、静态验证、可执行时的动态验证、风险项目及确认要求；提交必须绑定未过期的审查版本。 |
| REQ-009 | 系统必须提供 MCP 自有的 Undo/Redo，使已提交的 MCP 编辑能够在检查当前实时模块未被外部修改的前提下撤销或重做。 |

### 3.2 检查点、恢复与导出

| ID | 正式需求 |
|---|---|
| REQ-010 | 系统必须为同一源谱系维护可浏览的持久检查点历史，支持恢复到任意已有检查点，并在从历史检查点继续编辑时保留分支关系。 |
| REQ-011 | 使用当前版本工具链重放历史检查点时，系统必须区分 `exact`、`validated_drift` 和 `unverified_drift`，并对三种结果采用不同的允许行为。 |
| REQ-012 | 系统必须提供显式导出能力，把当前有效检查点对应的程序集写入默认工作产物或用户指定路径，并验证最终落盘文件。 |
| REQ-022 | 检查点中的语义操作必须具有稳定、显式的格式版本；未来版本不得静默重新解释旧操作。 |
| REQ-024 | 系统必须使 `committed_without_checkpoint` 可查询、可在重连后重试检查点、可在无冲突时撤销，并在解决前阻止导出。 |
| REQ-025 | 当实时模块因 dnSpy 界面编辑而偏离当前检查点谱系时，系统必须检测偏离；只有显式接纳当前模块后，才能以它为新谱系基线继续记录。 |

### 3.3 影响分析、验证和恶意样本约束

| ID | 正式需求 |
|---|---|
| REQ-013 | 系统必须扫描当前 dnSpy 已加载模块，生成机器可读的跨程序集影响报告，并明确报告扫描范围而非宣称全局完整。 |
| REQ-014 | 系统必须提供不影响常见调试流程的最小强名称兼容处理；默认保留身份，仅在动态验证明确因强名称失败时允许建立移除强名称的调试分支。 |
| REQ-015 | 所有由 MCP 触发的样本执行必须经过 VMware/VirtualBox 环境检测；非匹配环境默认禁止执行，并只允许 dnSpy 本地 UI 进行当前进程生命周期内的覆盖。 |
| REQ-021 | 系统必须把程序集、资源、源代码、字符串和调试目标视为不可信输入；解析、显示、编译和检查点浏览不得隐式执行样本代码。 |
| REQ-023 | C# 编辑必须使用普通编译路径，禁止 analyzer、source generator、脚本和自定义构建任务；目标引用只能作为编译元数据读取。 |
| REQ-026 | 系统必须为超过 MCP 请求正文容量的资源提供虚拟机内文件路径导入/导出路径，同时返回文件身份、长度和 SHA-256 证据。 |
| REQ-027 | 已知的 `debug_dump_module` 暂停态 `TARGET_MISMATCH` 缺陷必须修复并加入回归验证，不能把响应契约已通过但实际 dump 失败视为成功。 |

### 3.4 UI、会话、兼容和可发现性

| ID | 正式需求 |
|---|---|
| REQ-016 | dnSpy UI 必须能够浏览和查看当前事务、待应用操作、差异、验证/风险、检查点树及检查点详情，并提供本地取消当前事务的操作。 |
| REQ-017 | 服务端监听器重启、传输会话关闭和客户端重连必须与编辑事务生命周期闭环：未提交事务回滚，已提交状态保留，同地址客户端可重新初始化。 |
| REQ-018 | 现有修改工具必须保留一个过渡版本并作为新事务模块的兼容入口，不能继续维护独立修改或撤销状态；过渡结束后允许移除。 |
| REQ-019 | 系统必须提供一致、机器可读的编辑状态、错误码、恢复建议和 MCP 输入/输出契约，使 AI 能区分冲突、验证失败、部分提交、能力不可用和导出阻断。 |
| REQ-020 | 每个实施阶段都必须同步维护英文/中文 README、MCP 完整说明、第三方全功能完整测试提示词和定向回归测试提示词，并以实际工具注册表为工具数量和契约的事实来源。 |

## 4. 固定约束

| ID | 固定约束 |
|---|---|
| CON-001 | 已实施且已经验证通过的调试状态机、句柄/事件/分页、ArtifactStoreLedger、配置 pending/committed 事务、SideEffectRequestCache、双执行通道、传输限制、认证/CIDR、监听器 Apply 重启、Python 客户端和 stdio 桥不得因本需求被简化或替换。 |
| CON-002 | 当前版本全进程最多允许一个活动编辑事务；传输会话上限不等于并行编辑事务数。 |
| CON-003 | 一个事务只能编辑一个普通纯托管单模块 EXE/DLL；混合模式、NetModule 和多文件程序集可以继续读取分析，但编辑开始必须明确拒绝。 |
| CON-004 | 编辑事务期间 dnSpy UI 仍可编辑实时模块；提交必须通过实时指纹检测这种外部修改并返回冲突，不能覆盖用户操作。 |
| CON-005 | 实时模块访问必须在 WPF Dispatcher 上完成；提交只持有短临界区，并采用预生成反向操作处理应用失败，不能长时间锁住 dnSpy UI。 |
| CON-006 | Undo/Redo 由 MCP 自己维护，不接入 dnSpy 原生 Ctrl+Z/Ctrl+Y，不修改或重新发布 dnSpy.AsmEditor。 |
| CON-007 | 应用任意 MCP 配置时继续重启 HTTP 监听器；未提交编辑事务随会话关闭回滚。地址不变时客户端自动重新初始化，地址或端口变化时由用户更新 AI 配置后重连。 |
| CON-008 | 编辑事务所有权必须来自服务端传入的权威传输会话上下文，不能相信工具参数中由调用者自报的会话 ID；无正式会话的兼容单次 HTTP 调用不得开始编辑事务。 |
| CON-009 | 每个源谱系使用一个检查点包：完整基线只嵌入一次，语义操作按顺序记录，源代码/资源等载荷按 SHA-256 去重，历史分支用父链接表达；包更新必须使用临时文件和原子替换。 |
| CON-010 | 历史重放使用当时运行的当前 MCP、编译器和依赖版本；规范化操作格式首版固定为 `dnspy.edit.op.v1`，未知版本或未知操作必须停止而非猜测。 |
| CON-011 | 有效检查点是默认导出的前置条件；部分提交、结构性错误和 `unverified_drift` 均不得导出为成功产物。 |
| CON-012 | 现有 MCP 请求正文 1 MiB 上限保持不变，不因资源编辑提高全局传输上限。 |
| CON-013 | 跨程序集影响扫描只覆盖当前已加载模块，结果必须包含 `scope=loaded_modules` 及实际扫描列表。 |
| CON-014 | 自动执行许可只识别 VMware 和 VirtualBox；本地覆盖不得持久化，也不得由远程 AI 调用。不得默认增加网络、共享目录或虚拟机逃逸检测。 |
| CON-015 | 调试符号只以嵌入形式维护，不创建或要求单独 PDB 文件。 |
| CON-016 | 每个谱系只有一个默认工作输出，后续导出原子替换；用户显式提供其他路径时可以产生额外文件。原始样本默认不得覆盖。 |
| CON-017 | 高风险结构化编辑在普通模式可用。非结构性风险可由 AI确认，但提交后的回报必须显式列出确认内容和受影响引用；结构性错误仍为硬阻断。 |
| CON-018 | 每阶段必须构建 net48 与 net10.0-windows；所有阶段执行 x86/x64 冒烟测试，架构敏感功能和真实启动路径执行完整双架构测试。 |
| CON-019 | 标准 `.resources` 仅对标量、字符串、字节数组和流提供语义编辑；自定义序列化类型只允许查看元数据/原始载荷哈希和整体替换，不得反序列化对象。 |
| CON-020 | 提交前必须验证私有副本；实时应用前预生成反向操作。应用失败时恢复，恢复失败则进入 `LIVE_STATE_UNKNOWN` 并阻止继续编辑和导出。 |
| CON-021 | 私有副本上的开始、应用和静态审查不属于实时写入；提交、Undo、Redo、导出和动态验证继续遵守现有调试空闲门禁。 |
| CON-022 | C# 编译不得执行第三方编译扩展点；动态运行只能在通过 VM 门禁后发生。 |
| CON-023 | `exact` 可进入提交；`validated_drift` 经明确确认后可形成迁移子检查点；`unverified_drift` 只供诊断，不得修改实时模块、成为检查点或导出。 |
| CON-024 | 新工具必须发布可由严格 MCP 宿主验证的内联输入/输出 schema，不得出现缺失 `$defs` 的引用；结构化输出顶层必须符合声明的对象形状和字段类型。 |
| CON-025 | C# 编译使用 dnSpy 公开的编译契约；结果导入由 MCP 在当前范围内自行实现，不引用 AsmEditor 内部类型，不使用脆弱反射代理。 |
| CON-026 | 已修复的 debug 契约兼容性必须保持，包括 `base_address`、线程 ID、`method_token` 格式及对象型 `structuredContent`，不得因新增工具回归。 |
| CON-027 | ZCode 不暴露 MCP resources 是宿主限制。工具全功能测试可以由 ZCode 完成；14 个 resources 的严格验收必须由 Python 客户端、Inspector 或其他支持 resources 的宿主完成。 |
| CON-028 | 实施阶段边界必须在开始实施前固定，不得到阶段执行时重新扩张范围或重新访谈已确定事项。 |

## 5. 实施范围分阶段边界

本节只固定范围和完成顺序，不规定具体类、文件或代码实现。

| 阶段 | 已确认范围 |
|---|---|
| 阶段 1 | 编辑事务、统一审查、实时提交/回滚、MCP Undo/Redo、检查点与谱系、状态/UI 浏览、常用类型和成员 CRUD。 |
| 阶段 2 | 高级结构化元数据：泛型约束、Custom Attribute、MethodImpl/Override、布局、Marshal、P/Invoke、Security Declaration、字段初始数据。 |
| 阶段 3 | C# 方法/类型编辑、编译诊断、受限结果导入和嵌入式调试信息。 |
| 阶段 4 | 程序集/模块身份、版本、区域性、AssemblyRef、模块名称和入口点。 |
| 阶段 5 | 托管资源、Win32 资源、图标组关系，以及最小强名称和调试兼容闭环。 |

每一阶段必须独立满足相应构建、契约、保存/重载、检查点和相关错误路径验收后，才能进入下一阶段。

## 7. 保留、简化和删除取舍

### 7.1 明确保留

- 保留所有已实施并验证通过的现有服务端、调试、传输、安全、配置和 Python 客户端机制（`CON-001`）。
- 保留私有工作副本、外部编辑冲突检测、检查点分支、跨版本三态重放和 UI 浏览。
- 保留高风险结构化编辑能力，但采用风险确认和最终显式回报，不以删功能规避风险。
- 保留使用当前工具链重放历史记录，以适应编译器和依赖版本变化。
- 保留普通纯托管程序集上的 C#、高级元数据、资源、程序集身份和入口点编辑范围。

### 7.2 明确简化及代价

| 简化项 | 简化后的形式 | 实际代价 |
|---|---|---|
| 编辑事务并发 | 全进程一个活动编辑事务。 | 不能并行编辑多个模块。 |
| 审查接口 | 预览和验证合并为统一审查。 | 不能把两者作为互不相关的外部阶段调度。 |
| Undo/Redo | 使用 MCP 自有历史，不接入 dnSpy 原生 Undo。 | Ctrl+Z/Ctrl+Y 不处理 MCP提交。 |
| 检查点存储 | 每个谱系一个可原子替换的包，不使用 SQLite。 | 更新时临时磁盘占用可接近包大小的两倍。 |
| 检查点内容 | 完整基线一次、语义操作和去重载荷。 | 任意 dnSpy UI修改不能自动还原为语义操作，必须建立新基线。 |
| 跨程序集检查 | 只检查已加载模块。 | 无法证明未加载依赖不受影响。 |
| 强名称 | 默认保留身份，必要时建立去强名称调试分支。 | 不能保证严格签名、自校验或 GAC 场景运行。 |
| 资源大载荷 | 小载荷内联，大载荷使用 VM路径。 | 宿主 AI不能直接通过单个 MCP请求上传超限资源。 |
| 输出文件 | 每谱系一个默认工作产物，额外文件必须显式指定。 | 默认只保留最新工作输出。 |
| 旧修改工具 | 只保留一个过渡版本，内部转入新事务。 | 单次旧调用包含审查、提交和检查点，耗时会增加。 |

### 7.3 明确删除或移出当前范围

- 原始编辑、混合模式编辑、NetModule/多文件编辑和原密钥重新签名移入 TODO。
- 删除 WPF/BAML 专用阶段、VB 编译器计划、Advanced 模式开关、数据库方案和 AI任务状态机设想。
- 删除“每个 MCP事务映射为一个 dnSpy 原生 Undo 项”的要求，改为 MCP自有 Undo/Redo。

## 9. 已知未知项、落地风险和后续方案必须解决的问题

以下内容不是新增功能要求，但后续方案必须明确其实现和验证方式：

1. **实时提交复杂度**：dnSpy 公开文档接口不能直接替换现有 `ModuleDef`。每类操作必须具有可靠的预检、正向应用、反向恢复和结果指纹；这是主要实施风险。
2. **C# 结果导入复杂度**：公开接口提供编译能力，但 dnSpy AsmEditor 的完整导入器是内部实现。后续方案必须限定并验证 MCP 自有导入器覆盖的当前范围。
3. **大型程序集内存**：即使限制为单事务，实时模块与私有副本仍会造成内存放大。无法安全创建副本时必须无副作用失败。
4. **外部 UI 修改识别**：需要能覆盖 dnlib 对象、IL、资源和元数据变化的稳定指纹；不能只依赖 MCP 自己维护的版本号。
5. **工具链漂移**：编译器、dnSpy、dnlib 或依赖变化可能产生 `validated_drift`。测试必须证明三态分类真实有效，不能仅比较操作是否无异常。
6. **强名称限制**：缺少原始私钥、严格验证、自校验和跨未加载程序集引用时，可能无法得到既保持身份又能调试的产物；必须诚实报告能力边界。
7. **VM检测局限**：VMware/VirtualBox 检测可能受定制固件或隐藏标志影响，也不能保证阻止逃逸；本地进程期覆盖是唯一人工恢复路径。
8. **ZCode resources 限制**：ZCode-only 验收不能达到 14/14 resources。完整测试文档必须把资源验收分配给支持 resources 的宿主，而不是把 BLOCKED 伪装成 PASS。
9. **大资源传输限制**：宿主 AI没有分块上传路径；超过请求上限的资源必须由用户或其他受控方式预先放入 VM。
10. **现有 dump 缺陷**：`debug_dump_module` 的 `TARGET_MISMATCH` 是独立于结构化编辑的新旧基线缺陷，在全功能验收前仍须闭环。
11. **进程崩溃窗口**：实时内存提交后、检查点完成前若 dnSpy 进程退出，内存修改和待完成记录可能丢失；既有源文件和已完成检查点必须保持安全。
