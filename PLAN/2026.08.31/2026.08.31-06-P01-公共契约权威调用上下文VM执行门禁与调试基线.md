## 4. 冻结的公共契约

### 4.1 权威调用上下文

新增内部不可序列化类型 `Transport/McpCallContext.cs`。最小字段如下：

| 字段 | 类型/枚举 | 来源和语义 |
|---|---|---|
| `TransportKind` | `legacy_sse | streamable_http | compatibility_plain_http` | 由 `McpServer` 路由确定 |
| `AuthoritativeSessionId` | nullable string | 只取服务端会话对象的 ID；plain/missing-header 兼容调用为 null |
| `ProtocolVersion` | string | 当前会话协商结果；兼容调用取服务器实际使用版本 |
| `IsInitializedSession` | bool | 只有该服务端会话成功处理 initialize 后为 true |
| `CanOwnEditTransaction` | bool | 仅 `IsInitializedSession && AuthoritativeSessionId != null`；这是 P02 唯一可消费的所有权能力 |

规则：

- `McpServer` 是唯一构造者；工具参数中任何 `session_id`、`owner_session_id` 或同义字段都不能改变上述值。
- legacy SSE 的会话在其 initialize 成功后取得上下文；Streamable HTTP 只有已识别 header、且对应会话初始化完成后取得上下文。
- 未带 `Mcp-Session-Id` 的兼容 Streamable/plain 工具调用保留既有兼容行为，但 `CanOwnEditTransaction=false`。
- 带未知 `Mcp-Session-Id` 的请求继续返回 HTTP 404，不降级为无会话调用。
- 现有 debug `session_id` 仍是调试目标会话；它不是传输所有者，不进入 `AuthoritativeSessionId`。
- `IMcpToolProvider.ExecuteTool` 与 `McpToolRegistry.ExecuteTool` 增加 `McpCallContext` 参数。静态和 debug provider 在 P01 不使用事务所有权，除接收参数外保持行为不变。

### 4.2 会话生命周期通知

新增 `Transport/McpTransportSessionLifecycle.cs`，由 MEF 导出，提供内部观察者接口。稳定关闭原因仅有：

- `client_delete`：Streamable HTTP DELETE 成功删除会话；
- `legacy_disconnect`：legacy SSE 连接结束并删除会话；
- `listener_stop`：服务器 Stop/Apply 重启时统一失效现存会话。

集中 `RemoveAndNotify` 必须满足：

- 幂等身份使用 `(TransportKind, SessionId)`；对相同会话的并发/重复关闭只通知一次，最先成功移除者确定关闭原因；
- 先从会话字典移除并释放 16 会话名额，再通知观察者；
- `Stop()` 清空 legacy 和 Streamable 会话，逐个发布 `listener_stop`；
- 单个观察者异常只记录日志，不能阻止其他通知、字典清理或监听器停止；
- P01 不注册事务观察者。P02/P03 后续使用该通知回滚未提交事务并保留持久状态。

### 4.3 环境分类和本地覆盖

新增 `Execution/VirtualizationExecutionGate.cs`，不增加包依赖，使用 `Microsoft.Win32.Registry` 只读以下值：

`HKLM\HARDWARE\DESCRIPTION\System\BIOS` 下的 `SystemManufacturer`、`SystemProductName`、`BIOSVendor`。

输入先 `Trim()` 并使用 invariant 小写归一化。冻结分类：

| 分类 | 判定 |
|---|---|
| `vmware` | 任一非空归一化字段包含 `vmware` |
| `virtualbox` | 产品名包含 `virtualbox`；或至少一个字段包含 `innotek gmbh` 且另一字段含 `virtualbox`/`innotek` 标记 |
| `physical` | 注册表成功读取到至少一个非空字段，但不匹配以上标记 |
| `unknown` | 读取失败、权限异常或三个值全部为空 |

`Oracle Corporation` 单独出现不得判为 VirtualBox。分类证据只公开命中的规范化 marker 标签，不返回固件序列号或完整注册表原文。

共享许可规则：`vmware`、`virtualbox` 允许；`physical`、`unknown` 默认拒绝。读取异常按 `unknown` fail-closed，不回退到 WMI、进程名或外部命令。

新增独立的进程内存覆盖服务，默认 false：

- 只由 dnSpy 本地设置页控件改变；
- 不写入 `McpSettingsSnapshot`、`ISettingsService`、环境变量、命令行或文件；
- MCP 产品工具和参数均无 setter；测试构建也不得借测试工具设置它；
- 覆盖使当前 dnSpy 进程内的 `physical/unknown` 暂时获准；dnSpy 进程退出自然清零；
- UI 显示当前分类、许可状态和高风险提示，控件文案明确“仅本次 dnSpy 进程”；
- 页面 Apply 才提交当前页面的覆盖选择；Cancel 不改变服务；应用其他配置仍按既有规则重启监听器。

### 4.4 共享执行门禁

统一入口枚举为 `debug_launch | debug_restart | edit_dynamic_validation`。所有入口调用同一 `IVirtualizationExecutionGate.Evaluate(entryPoint)`。

- `debug_launch`：在创建 lease、协调器会话、调试进程或调用 `Start` 前判定。
- `debug_restart`：在终止现有目标、清除状态或重新启动前判定。拒绝不能破坏当前暂停/运行目标。
- `edit_dynamic_validation`：P01 提供内部入口 seam；P02/P05/P06 后续只能消费这一 seam，不能复制检测。它还必须先遵守既有调试空闲门禁。
- 拒绝使用现有 `CAPABILITY_UNAVAILABLE` debug 域错误及其恢复建议，保留 `dnspy.debug.v1` envelope；不得用 HTTP 200 的文本错误伪装成功。
- 拒绝时进程创建数、Start 调用数、debug generation、现有目标状态和文件系统保持不变。

### 4.5 可观察能力和 schema

`debug_capabilities.result` 增加必有对象 `execution_environment`：

```text
classification: "vmware" | "virtualbox" | "physical" | "unknown"
execution_allowed: boolean
local_process_override_active: boolean
detection_source: "windows_bios_registry_v1"
marker_tags: string[]
```

运行 DTO、`DebugToolProvider` 内联 outputSchema、`tests/debug/contracts/dnspy.debug.v1.schema.json` 和所有 capability fixture 同步修改。继续使用 `schema_version=dnspy.debug.v1`，这是同一 v1 envelope 的加法字段，不改变既有字段语义或工具数量。严格 schema 验证必须证明运行载荷类型一致且没有 `$defs` 引用。

P01 不公开新的产品 MCP 工具。`DNMCP_TEST` 可提供不可广告的测试 probe，并且仅包含以下观察/注入面：VirtualBox、physical、unknown 硬件信号注入；三个执行入口的 Start/terminate 调用计数；当前调用的 `TransportKind`、`AuthoritativeSessionId`、`IsInitializedSession`、`CanOwnEditTransaction` 观察；按 `(TransportKind, SessionId)` 记录的 close reason、通知次数和活动会话数观察；一次性观察者异常注入。关闭旧会话后由新初始化的测试会话读取生命周期快照。生产模式必须对该 probe 返回能力不可用或完全不注册；probe 不能改变本地覆盖、伪造生产调用上下文或替代真实 DELETE/disconnect/Stop 动作。

## 7. 实施顺序与交接

首次第三方审核通过并取得实施授权后，实施者必须从基线创建 P01 独立功能分支；分支名属于操作细节，但不得直接在主分支实施，也不得夹带当前工作区既有无关修改。

固定顺序为 `IMP-001 → IMP-002 → IMP-003 → IMP-004 → IMP-005 → IMP-006 → IMP-007`。IMP-001/002 建立 P02 必需的身份和生命周期；IMP-003/004 建立所有动态验证的公共许可；IMP-005/006 独立证明 P01；IMP-007 只记录已实现和已验证事实。

P01 完成后向 P02 交接：

- `McpCallContext.CanOwnEditTransaction` 和服务端会话 ID 是唯一所有权来源；
- close reason 和幂等观察者接口；
- `edit_dynamic_validation` 的共享 gate/idle seam；
- P01 schema/error 基础和三项 ACC 原始证据；
- 禁止 P02 复制 VM 检测、从 args 恢复 owner 或发布兼容 HTTP 事务。

## 8. 独立验收契约

### 8.1 新测试命令

P01 创建驱动后，Windows 仓库根的实际命令固定为：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tests\edit\run-edit-tests.ps1 -Case EDIT-ACC-017
powershell -NoProfile -ExecutionPolicy Bypass -File tests\edit\run-edit-tests.ps1 -Case EDIT-ACC-027
powershell -NoProfile -ExecutionPolicy Bypass -File tests\edit\run-edit-tests.ps1 -Case EDIT-ACC-030
```

驱动工作目录、输入 schema、证据目录、`summary.json` 和退出码严格采用总纲 §10.1。驱动只能通过 Python client/MCP 和 Win10VM 能力编排，不以 curl、手写 JSON-RPC 或人工操作作为通过路径。

`EDIT-ACC-030.json` 必须在总纲既有字段之外增加 `outcome_checks: ["OUT-001-H01", "OUT-001-H02"]`。执行 `-Case EDIT-ACC-030` 时，驱动依次执行 H01、H02 和 ACC-030；三者不拆成新的案例文件或全局 ACC。证据固定写入：

- `<ArtifactRoot>\edit-tests\<run-id>\EDIT-ACC-030\out-001-h01.json`
- `<ArtifactRoot>\edit-tests\<run-id>\EDIT-ACC-030\out-001-h02.json`

`summary.json` 的 `EDIT-ACC-030` 案例记录继续以 `acc_id="ACC-030"` 和 `status=pass|fail|blocked` 表示 ACC-030 自身结果，并新增：

```text
outcome_checks: [
  { id: "OUT-001-H01", status: "pass|fail|blocked", evidence_path: "out-001-h01.json", reason: string|null },
  { id: "OUT-001-H02", status: "pass|fail|blocked", evidence_path: "out-001-h02.json", reason: string|null }
]
```

驱动总体状态和退出码同时聚合案例 `status` 与 `outcome_checks[*].status`：任何一项 fail → 1；无 fail 但至少一项 blocked → 2；三者全 pass → 0。这样 H01/H02 具有独立可审计结果，同时不改变总纲按稳定 ACC 记录案例的协议。

### 8.2 ACC-017 / RACC-017 / P01

- 前置：P01 生产构建、测试信号注入、Win10VM 的真实 dnSpy x86/x64 实例。
- 动作：真实读取 VMware；注入 VirtualBox、physical、unknown；逐类调用门禁；从本地设置页 Apply 覆盖；通过 MCP 尝试发现/设置覆盖；重启 dnSpy 后复核。
- 预期：VMware/VirtualBox 允许，physical/unknown 拒绝；只有本地覆盖在当前进程临时允许；MCP 不存在 setter；重启清零；检测不启动样本。
- 证据：marker tag、分类、capabilities、门禁响应、Start 计数、设置页自动化、重启前后状态、清理结果。
- 失败：远程可覆盖、Oracle 单标记误判、unknown 放行、把分类描述为隔离保证或产生未授权进程。
- 被阻断：只允许 Win10VM/宿主环境不可用且保存原始连接错误和零副作用；未实现或分类错误不是被阻断。

### 8.3 ACC-027 / RACC-027 / P01

- 前置：真实 x86/x64 调试 fixture、允许的 VMware、可写 ArtifactRoot。
- 动作：launch 后暂停；对目标模块和 mscorlib dump；改变 pause epoch 再 dump；restart 取得新 generation 后重新获取模块句柄并各 dump。
- 预期：每次 `ok=true`；artifact 和 manifest 均存在；响应、文件和 manifest 的 SHA-256 一致；不出现错误 `TARGET_MISMATCH`；旧 generation/handle 仍按既有规则拒绝。
- 证据：session/generation/epoch、模块身份、结构化响应、路径、长度/SHA、manifest、旧 handle 负例和最终 idle。
- 失败：只通过 schema 但 dump 失败、复用旧模块句柄冒充成功、SHA 不一致、残留进程/断点。
- 被阻断：只允许 ArtifactRoot 或已准备 VM 外部故障，并须证明没有产物/进程副作用。

### 8.4 OUT-001 权威交接检查与 ACC-030 / RACC-030 / P01

`OUT-001-H01/H02` 是 P01 独立交接检查，不是新增全局 ACC，也不改变总纲的 ACC 唯一归属。

- `OUT-001-H01`：分别从初始化后的 legacy SSE、初始化后的 Streamable HTTP、无正式会话兼容调用进入工具链；尝试在 args 伪造 owner。预期前两者得到各自服务端 ID，兼容调用不可拥有事务，伪造字段无效，未知 header 保持 404。
- `OUT-001-H02`：分别触发 DELETE、legacy disconnect、listener Stop，并重复/并发触发一次。预期字典名额先释放、每会话只通知一次、观察者异常不阻止清理、重启后旧会话失效。
- `ACC-030`：对 `debug_launch`、`debug_restart`、`edit_dynamic_validation` 执行 VMware/VirtualBox/physical/unknown 同一矩阵；调试活动时调用编辑 seam。预期三入口同判定；拒绝发生在任何 Start/terminate/状态变化前；编辑 seam 仍被 debug idle gate 拒绝。
- 执行载体：三者统一由 `EDIT-ACC-030` 编排；H01/H02 使用 §4.5 的 DNMCP_TEST 观察面，并由真实客户端动作触发三种传输和三种关闭路径，不能用 probe 直接伪造关闭。
- 证据：H01/H02 分别写入 §8.1 冻结的两个 JSON 文件，并在 `summary.json.outcome_checks` 独立记录；ACC-030 保持案例自身 `status`。证据内容包括上下文 probe、会话计数/close reason、入口判定、Start/terminate 计数、状态和事件前后快照、清理结果。
- 失败：H01/H02 中 args 可改 owner、兼容调用可拥有事务、会话泄漏/重复通知，均使 OUT-001 失败；ACC-030 中任一入口旁路或拒绝破坏现有目标，使 ACC-030 失败。
- 被阻断：只允许范围外运行环境中断；未接入任一传输/入口不是被阻断。

## 10. Fallback 和异常边界

| fallback/异常 | 依据 | 触发 | 行为 | 退出 |

## 11. 风险和工作量

| 风险 | 最小控制和证据 |
