## 4. 审计意见

### AUD-010：公共 schema 与 canonical fixture 仍存在两个不可同时满足的定义

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-003、REQ-DYN-006；CON-DYN-013、CON-DYN-014；RACC-DYN-002、RACC-DYN-011；方案 3.3—3.5；API-DYN-001；TYPE-DYN-011；IMP-002；ACC-002、ACC-028。
- 证据：
  1. 第 3.3 节的 22 个活动工具包含 `debug_capabilities`（API-DYN-001）。第 3.4 节、CON-DYN-014、API-DYN-001 和 ACC-028 均规定它在 gate=false 时仍成功。
  2. 第 3.5 节 contract 段却要求“22 个广告 API 各自”提供 `disabled-gate` fixture，且该 fixture 固定期望 `DEBUG_DISABLED`。因此 API-DYN-001 的 fixture 同时必须成功和失败。
  3. TYPE-DYN-011 把 `required_states` 定义为 0..8 项；同节封闭数组清单又规定 `DomainError.required_states` 最多 7 项。单一 JSON Schema 不能同时以 maxItems=8 和 maxItems=7 逐字表达。
- 风险：schema、fixture、handler 和 ACC-028 可各自选择不同解释，两个独立实现无法得到同一协议。
- 影响：公共协议、条目双向追溯、可交接实施性和验收边界未闭合。
- 建议：把 API-DYN-001 从 `disabled-gate=DEBUG_DISABLED` fixture 集合中明确排除并为其建立 gate=false success fixture；把 `required_states` 的唯一最大项数固定为 7，并同步 3.5、schema、fixture 和 ACC-028。

### AUD-011：四种 break_kind 没有到 dnSpy 常量、状态和事件的完整映射

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-002、REQ-DYN-004；RACC-DYN-004、RACC-DYN-009；方案 3.5 API-DYN-003、launch_mode 表、EVT-DYN-010；IMP-005、IMP-011；ACC-007/008/022/029/030；SRC-API-001。
- 代码证据：dnSpy v6.6.0 `StartDebuggingOptions.cs` blob `f275fad1fef4c0a7aad1ad29b87f62e938ddba51` 的 `PredefinedBreakKinds` 只有 `DontBreak`、`CreateProcess`、`ModuleCctorOrEntryPoint`、`EntryPoint`；`StartDebuggingOptions.BreakKind` 是传给 manager/engine 的 string。
- 已证实问题：方案公开 `none`、`process`、`module_cctor_or_entry`、`entry`，但 launch_mode 的“Start 映射”没有固定四值到上述上游常量的映射；也没有固定 `process` 和模块 cctor 暂停在 EVT-DYN-010 中使用哪个 `reason`。现有 ACC 主要验证默认 `entry`，没有逐 runtime/mode 覆盖四值及 `none` 不暂停边界。
- 风险：实施者可传 API 字面量、上游常量、null 或自行转换，并可把 process/cctor 暂停报告为不同事件；部分组合可能完全不暂停或在错误位置暂停。
- 影响：launch 生命周期、事件协议和六项发布矩阵不能直接编码或机械验收。
- 建议：在 API-DYN-003/launch 表逐值固定 `BreakKind` 映射，补齐 process/cctor 的状态和 EVT reason；在可支持的每种 runtime/launch_mode 上为四值给出正/负验收矩阵，明确 `none` 的无 paused 事件边界。

### AUD-012：v6 所称“整页事务”与现有逐属性持久化和即时启动机制不相容

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-003、REQ-DYN-011、REQ-DYN-015；CON-DYN-006、CON-DYN-014；RACC-DYN-003、RACC-DYN-012；EVD-CODE-003；方案 IMP-003；ACC-003、ACC-036；SRC-PROJ-001。
- 代码证据：`McpSettings.cs` blob `fdc31d531e9abb21800c3a456e3a9f53032a42f1` 的 `CopyTo` 依次设置 EnableServer、Host、Port；每个 setter 触发 `PropertyChanged`。`McpSettingsImpl_PropertyChanged` 每次都 `RecreateSection` 并写当前字段，且 EnableServer 变化会立即 `Start/Stop` server。`McpSettingsPage.cs` blob `3eebeb40eaba3884ad5d9fbef0cbaa9351dfcc69` 的 OnApply 只调用一次 CopyTo。
- 已证实问题：CON-DYN-014、IMP-003 和 ACC-036 把“一次 CopyTo”当作“本页各值一次提交”，却没有要求批量抑制 PropertyChanged/persistence/server side effect。按当前机制，idle 时同时把 EnableServer 从 false 改为 true并修改 Host/Port，server 会先按旧 Host/Port 启动，随后新 Host/Port 只被持久化；进程中断还可留下部分字段。
- 风险：远程绑定、认证相关设置和冻结门禁可出现持久化值与实际监听状态不一致；v6 新增的 active 拒绝不能修复 idle 提交路径。
- 影响：设置数据一致性、用户可见保存结果、远程安全状态和直接实施顺序未闭合。
- 建议：明确新增批量 ApplySnapshot/commit 边界：先完整验证，抑制逐属性持久化和 server 动作，一次写入全部字段并原子替换内存快照，最后只按新完整快照执行一次 Start/Stop/rebind；ACC-036 增加 persistence 调用次数、server 启停参数/顺序和中途故障注入。

### AUD-013：FB-002 要求返回的识别证据和工作流没有公共 wire 落点

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-002、REQ-DYN-003；NON-DYN-001；RACC-DYN-010；方案 3.4、TYPE-DYN-011、API-DYN-003、ACC-024、FB-002。
- 证据：FB-002 和 ACC-024 要求 `CAPABILITY_UNAVAILABLE` 同时返回识别到的目标种类、证据及 Mono 或 PE/x64dbg 交接；失败 envelope 只能包含 TYPE-DYN-011 error。TYPE-DYN-011 没有 target kind、evidence 或 recommended workflow 字段，`recovery` 只有泛化的 `choose_supported_workflow`，且明确 `message` 不作为机器判断依据。所有对象又固定 `additionalProperties=false`。
- 风险：实现者只能把关键交接信息塞入不可机械判断的 message，或添加违反 schema 的字段；ACC-024 无法按共同 schema 判定“正确工作流”。
- 影响：不支持范围的正常失败闭环和 FB-002 验收未成立。
- 建议：为 TYPE-DYN-011 增加受限、稳定的结构化 details variant，或为 API-DYN-003 的该错误固定 `detected_target_kind`、`evidence`、`recommended_workflow` schema；同步 ACC-024 对每类 fixture 逐字段断言。

### AUD-014：ArtifactRoot 自身及其父链未纳入 reparse/final-path lease

- 严重度：阻断性安全问题。
- 来源或方案 ID：REQ-DYN-010、REQ-DYN-011；CON-DYN-008；NON-DYN-002；RACC-DYN-007；方案 TYPE-DYN-008/018、IMP-009、ACC-019；EVD-OS-001。
- 证据：CON-DYN-008 只要求 session 目录是 ArtifactRoot 的非 reparse 直接子目录，并把当前 root 的 file ID 写入 marker；IMP-009 只要求用户路径规范化且字面上不位于 sample allowed root/扩展目录。ACC-019 覆盖 session 目录和内部 file reparse，但没有覆盖 ArtifactRoot 本身为 junction/symlink、父组件 reparse 或验证后替换。CON-DYN-011 的逐组件 handle lease 仅适用于 launch 输入，不适用于 ArtifactRoot。
- 风险：一个指向样本、扩展或其他目录的 root reparse 可使 artifact CreateNew 和 7 天清理落到字面路径之外；marker 记录被重定向目标的身份仍可能自洽，不能阻止越界写入/删除。
- 影响：产物隔离、保守清理和 NON-DYN-002 的任意路径写入边界未闭合。
- 建议：像 CON-DYN-011 一样对 ArtifactRoot 及父链使用 OPEN_REPARSE_POINT/final path/file ID 进行拒绝和 lease，验证最终 root 不在样本/扩展目录并在创建、写入、清理期间保持身份；ACC-019 增加 root/父链 reparse 与验证后替换 barrier。

### AUD-015：ACC-016 的命令使用 API-DYN-020/021 不存在的预算参数

- 严重度：高。
- 来源或方案 ID：REQ-DYN-006、REQ-DYN-009；CON-DYN-007、CON-DYN-009；RACC-DYN-006；方案 TYPE-DYN-017、API-DYN-020/021、IMP-008、ACC-016。
- 证据：API-DYN-020 只接受公共 paused 字段、frame_handle 和 PageRequest；API-DYN-021 另只增加 `depth` 1..4。node/string/response budget 是 TYPE-DYN-017 的服务端固定结果字段，不是请求参数。ACC-016 却要求“以最大允许和超限 depth/node/string/response 参数调用展开”。
- 风险：按 schema 提交 node/string/response 参数应为 `-32602`，按 ACC 文字又应触发截断或 `LIMIT_EXCEEDED`；测试作者必须自行改写操作。
- 影响：无目标代码执行的资源边界没有可执行的验收命令。
- 建议：depth 仅测试 4 与 5 的 schema 边界；node/string/response 通过确定性 fixture 的节点数、字符串字节数和总响应体大小触发，并分别固定 truncated 与 LIMIT_EXCEEDED 预期及 provider 调用计数。

### AUD-016：认证与 CIDR 失败的 HTTP 状态没有逐输入固定

- 严重度：高。
- 来源或方案 ID：REQ-DYN-011、REQ-DYN-013；CON-DYN-006；RACC-DYN-003；方案 3.4、IMP-003、ACC-003。
- 证据：3.4 只写“认证/CIDR 失败返回 401/403”；ACC-003 对无 token、错误 token、轮换后的旧 token统一写“401/403”，也未逐项固定 CIDR 不匹配的唯一状态、响应头和 body 边界。
