## 5. 审计意见

### AUD-027：所有 running→paused 观察都标记 manual，会吞掉断点、异常和 step 原因并可误结算 manual pause

- 严重性：高。
- 来源与方案位置：REQ-DYN-004/005/008、RACC-DYN-002/004/005、CON-DYN-003/004/013、方案第 3.2、3.5、3.6 节，EVT-DYN-010/013/014/015、API-DYN-006/019、IMP-004/005/006/008、ACC-007/008/012/014/028/034；SRC-API-001、EVD-API-011。
- 风险：v13 接受真实 paused 观察是正确方向，但第 3.2 节规定 public running 时无条件写 EVT-DYN-010(reason=manual)，并把当前唯一 pause record 以“目标状态已满足”成功结算。目标实际可能因 breakpoint、exception、step complete 或 ProgramBreak 停止；公共原因、事件顺序和 pending manual pause 的结果会与事实不一致。
- 代码证据：dnSpyEx v6.6.0 的 DbgRuntime.cs blob 1d1640882ac8acf1a71c2ceec60d05debcb57005 暴露 BreakInfos，并说明它在 runtime break 时更新、continue 时清空；DbgBreakInfoKind.Message 的 Data 是 DbgMessageEventArgs。DbgMessageEventArgs.cs blob 74c63c345fa171b6c6ae0380c6c77d00195578d8 为 ExceptionThrown、EntryPointBreak、BoundBreakpoint、ProgramBreak、StepComplete 和 Break 提供不同稳定 kind。方案已经把这些事实映射为 EVT-DYN-010 的 breakpoint/exception/step reason 以及 EVT-DYN-013/014/015，却没有在 v13 的唯一 paused 分支读取或排序它们。
- 确定性反例：目标 running，断点被命中。通用 ProcessPaused 到达时 public 为 running，按第 3.2 节只能产生 EVT-DYN-010(reason=manual)，与同一停止的 EVT-DYN-013 breakpoint_hit 冲突。若此时 P2 manual pause 已 scheduled/issued，它还会被成功结算为 reason=manual，即使其 callback 从未 Break 或真正停止原因是 breakpoint。step complete 和 exception 具有同样问题；第 3.6 节明文要求 step 完成/异常后转 paused，但未给出它们与 generic paused、EVT-DYN-014/015、pause_epoch 和响应的原子顺序。
- 影响：客户端无法可靠区分用户 pause、断点、异常和 step；事件日志不再如实反映目标状态，pending pause 的响应可假报 manual 成功；RACC-DYN-002/005 的机械解析和定位准确性不成立。
- 建议：在 DbgManager dispatcher 的同一原子事务中，从 owned runtime 的 BreakInfos 和稳定 DbgMessageKind 导出封闭 pause cause，并定义多原因优先级、EVT-DYN-010 与 EVT-DYN-013/014/015 的唯一顺序。把“目标已 paused”与“manual pause 导致该状态”分开：非 manual stop 可以结算等待中的状态请求，但 response/reason 必须有独立、稳定且不伪造因果的契约。
- 最小闭合条件：第 3.2/3.5/3.6 节、API-DYN-006、EVT-DYN-010/013/014/015、IMP-004/005/006/008 明确上述原因与顺序；ACC-007/008/012/014/028 至少覆盖无 pending control 的 breakpoint/exception/step，以及 P2 scheduled/issued 与三类 stop 碰撞，逐例断言 response、reason、pause_epoch、thread/location/breakpoint/step identity、事件顺序、callback 次数和 queue/cache 结算。

### AUD-028：known_retained 的“枚举并持有验证 handle”不能冻结目录 child 集合，写前 fail-closed 仍有 TOCTOU

- 严重性：高。
- 来源与方案位置：REQ-DYN-010/011、CON-DYN-008/009、RACC-DYN-007、API-DYN-001/024、IMP-009、ACC-019；方案第 2.2、3.5、4、6 节；EVD-OS-001。
- 风险：v13 要求每次新增目录或字节前枚举所有 known_retained child，校验 identity/length/SHA-256，并把目录和 child handle 持有到 CreateDirectory/CreateNew/commit 决定结束。该机制能阻止已打开 child 的冲突改写、删除或替换，却不能阻止同用户进程在枚举完成后创建一个此前不存在的新 sibling；因此“任何新增先 TARGET_MISMATCH、扩展不再增加数据”的保证不成立。
- 一手契约证据：Microsoft Learn CreateDirectory2A 官方示例以 FILE_LIST_DIRECTORY | SYNCHRONIZE 和 FILE_SHARE_READ 打开目录，即未授予 write/delete sharing；在该目录 handle 仍打开时，示例随后用 CreateFile3 在目录中成功创建 example.test，再关闭两个 handle。稳定 URL：https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-createdirectory2a。它直接证明目录 share mode 不冻结 child-name 集合；已打开 child handle 也只保护既有对象，无法预先保护尚不存在的 sibling。
- 确定性反例：S1 已定格为合法 known_retained。S2 admission 在 store lock 内枚举 S1 并打开全部已知 child，集合完全匹配。外部同用户进程在枚举结束后、S2 CreateDirectory 之前创建 S1/injected.bin；它不与任何既有 child handle 冲突，也不被扩展进程内 store lock 约束。扩展随后创建 S2 目录或 artifact，已经在 unknown child 存在时增加数据，直到下一次 scan 才可能检测。active-writer 在 CreateNew/commit 前也存在同源窗口。
- 影响：CON-DYN-008、IMP-009、ACC-019 声明的写前数据一致性和安全边界不可由给定 Win32 操作机械实现；处理 AUD-026 后新增的 S1→S2 正例并未关闭对手在“重验后、写前”注入 sibling 的反例。
- 建议：二选一并作为明确产品契约。若保持同用户可写 ArtifactRoot，就收缩保证为“最迟下次 scan 检测”，明确当前 admission 的竞态窗口、允许的一次 owned write 和能力披露；若必须保持写前 fail-closed，则引入能对命名空间变更提供原子互斥的受控服务/权限或隔离边界，并以一手 API 契约证明，不得把目录 handle 当作 child-set lock。
- 最小闭合条件：CON-DYN-008/009、API-DYN-001、IMP-009 明确所选保证；ACC-019 在枚举后分别停于 pre-CreateDirectory、pre-CreateNew、pre-commit 屏障，注入新 sibling 并断言精确 response、允许/禁止的 tree 增量、ledger、hash、handle/share flags 和恢复步骤。若改变 threat/permission/isolation 或 artifact 信任语义，必须全面复审。

### AUD-029：每次写 admission 全量重哈希最多 8 GiB，但没有时延、取消或副作用队列释放边界

- 严重性：中。
- 来源与方案位置：REQ-DYN-004/010/014、CON-DYN-008/009/013、RACC-DYN-004/007/009、API-DYN-024、IMP-009/011、ACC-019/022；方案第 2.2、3.5、3.6、4、6 节。
- 风险：方案把最多 128×4096 个 child、8 GiB 的全量 SHA-256 重验定义为“每次写 admission 的固定成本”，禁止时间缓存；所有 active-session 副作用又在容量 64 的 FIFO 中串行。没有 endpoint/operation deadline、取消点、最大允许 elapsed、磁盘最低条件或 queue slot 释放边界，故一个合法 dump 可在 hashing 中长期占用 store lock 和副作用队列，阻塞 pause/continue/terminate/restart。
- 方案证据：CON-DYN-008/009 要求每次可能增加目录或字节前全量重验；API-DYN-001 固定 8 GiB/128/4096 上限；CON-DYN-013 要求副作用命令串行。ACC-019 只记录 bytes_hashed 和“不跳过重验”，未规定耗时或取消；ACC-022 的发布门禁也没有该场景的精确通过/失败阈值。数值容量界限只证明工作量有限，不证明在调试控制需要的时间内可完成或可中止。
- 确定性反例：在同进程 127 个合法 known_retained session、总量接近 8 GiB 的允许状态下提交 debug_dump_module，随后提交 terminate。前者必须先读并哈希整个 retained 集合；在慢盘或受限 VM 上没有契约时限，后者只能排队，且方案没有规定请求取消后 hashing、store lock、cache reservation 和 queue slot 的结算。该结果不能由现有 ACC 的 bytes_hashed 断言判定通过或失败。
- 影响：性能、资源和现实落地门禁缺少当前证据；lifecycle 虽有 control_operation_seconds=30，但请求尚未从副作用队列出队时的等待没有机械边界，可能使用户无法及时终止目标。
- 建议：定义写 admission 的最大 elapsed/取消与稳定失败结果，并保证取消/超时不产生目录或字节、释放 store lock/cache/queue；或改用具有同等完整性证据但不需每次全量内容重哈希的设计。阈值必须绑定明确 Windows VM/磁盘最低条件或确定性可注入吞吐/取消 seam。
- 最小闭合条件：CON-DYN-008/009/013、API-DYN-024、IMP-009/011 给出时间与资源结算；ACC-019/022 覆盖接近 8 GiB/最大 child 数、hash 中取消/超时、紧随其后的 terminate，逐项固定 elapsed 上限、response、tree/hash、store-lock、cache reservation、queue slot 和 lifecycle 可恢复性。

## 6. fallback 逐项评定

### FB-001：raw runtime bytes 不可用时重构托管 PE

- 评定：通过。
- 依据：REQ-DYN-010、RACC-DYN-007、EVD-API-005、ACC-032。
- 必要性：上游明确允许 raw bytes 不可用，而 ForceMemory metadata 可用；重构只在该已证实分支触发。
- 可退出性：raw 可用即回主流程；重构也失败则固定 CAPABILITY_UNAVAILABLE 且零产物。
- 不掩错：manifest 明示 reconstructed 非原始等价，不借进程外工具继续，不掩盖 hash、identity 或写入失败。

### FB-002：不支持 runtime 的工作流交接

- 评定：通过。
- 依据：REQ-DYN-002/003、NON-DYN-001、RACC-DYN-010、TYPE-DYN-019、ACC-024/026。
- 必要性：它只把已识别的不支持目标交接到封闭 recommended_workflow，不伪造托管能力。
- 可退出性：用户切换工作流，或未来以独立审核方案新增能力；v1 不在当前流程内降级。
- 不掩错：固定返回 CAPABILITY_UNAVAILABLE，不启动进程、不创建 session，也不退化为 GUI 自动化。

结论：两项 fallback 均必要、可退出、不掩盖主流程错误，也未引入无来源复杂度。AUD-027/028/029 都是主流程契约缺口，不能由 fallback 评价抵消。

## 8. 结论
