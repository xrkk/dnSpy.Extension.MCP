## 2. 需求、约束、非目标和需求级验收

### 2.1 功能与安全需求

| 需求 ID | 规范性需求 |
|---|---|
| REQ-DYN-001 | 在 dnSpy 进程内通过 MCP 公共工具控制托管动态调试，不使用 GUI 键鼠自动化，不修改 dnSpy 核心。 |
| REQ-DYN-002 | v1 支持 Windows 上 .NET Framework 与 CoreCLR x86/x64 的启动；任意进程枚举附加、附加和分离不属于 v1。Unity/Mono、混合模式和纯原生同样不属于 v1。 |
| REQ-DYN-003 | 客户端先获得真实能力、协议版本和安全状态；`debug_capabilities` 始终可查询，其他未实现或未启用的调试工具不广告、不假成功。 |
| REQ-DYN-004 | 提供启动、暂停、继续、重启和终止，以显式状态机拒绝非法顺序；`debug_list_attachable_processes`、`debug_attach`、`debug_detach` 的稳定 API ID 仅作为 v1 禁用能力保留，不得广告或产生副作用。 |

CON-DYN-014 的 CIDR canonicalization 额外固定：拒绝 IPv4-mapped IPv6 形式的配置项，IPv4 网络只允许标准 dotted-decimal/prefix，IPv6 网络只允许非 mapped 的 RFC 5952 address/prefix；这样 CON-DYN-006 把 mapped peer 转为 IPv4 后只有一个匹配域，不允许两个实现分别按 IPv4 或 IPv6 配置匹配。`ISettingsSection` 中两个 JSON 键都按读取出的 .NET string 判定：用严格 UTF-8 编码所得字节核对 RFC 8785 canonical identity，两个有效值以 `StringComparison.Ordinal` 相等（等价于 canonical UTF-8 字节相等）判 pending=committed；不得比较设置存储后端的 XML/物理文件序列化字节。committed 存在但无效，或两键都缺失但 legacy candidate 无效时，必须保留原存储供诊断、以内存安全默认继续且在服务 Start 前记录固定警告 `Stored MCP settings were invalid. Safe defaults are active.`；不得静默加载部分字段或自动把 defaults 写成 committed。

CON-DYN-009、API-DYN-001.`limits.tool_result_bytes` 和 TYPE-DYN-017.`response_utf8_limit` 中的 8388608 统一表示：按调用方已协商 protocolVersion 完整渲染、包含 JSON-RPC 与 MCP tools/call 外层后的单个 response message JSON 的严格 UTF-8 字节数，SSE 的 `event:`/`data:` framing 不计入；不得只测 internal envelope。任何响应必须在首次写入前完整序列化并计数，不得发送 partial body/event。动态 API 成功响应预计超限时改为小型 LIMIT_EXCEEDED envelope后重新渲染；动态服务端输出不变量失败按 3.4 的 INTERNAL_ERROR；既有静态 tools/call 或 initialize/ping/resources 等非动态响应预计超限时固定返回 JSON-RPC `-32603`、原 request id、message=`Response exceeds the fixed transport limit.`、无 data。小于等于上限的既有静态 schema/成功语义不变；notification 仍按其协议无 response。该安全上限是 CON-DYN-005 兼容承诺的唯一资源例外。

## 3. 固定范围与公共协议

### 3.1 v1 支持范围

- .NET Framework EXE 与 CoreCLR apphost/EXE：仅启动。
- 有 runtimeconfig、可由用户显式指定 `dotnet` host 启动的 CoreCLR DLL。
- 无入口类库：仅使用用户提供、位于 AllowedSampleRoot 且单独校验哈希的 harness；扩展不生成 loader，也不附加到既有宿主。
- 动态/内存托管模块：枚举并导出有来源标识的 raw 或 reconstructed 产物。
- 运行前提：`DedicatedDebugInstanceAcknowledged=true` 且该 dnSpy 进程只供 MCP launch 使用；人工调试必须使用另一 dnSpy 进程。

### 3.2 组件与所有权

```text
McpServer
  -> McpToolRegistry
       -> StaticToolProvider -> WPF Dispatcher
       -> DebugToolProvider
            -> DebugSessionCoordinator -> DbgManager.Dispatcher
                 -> DebugEventBuffer
                 -> DebugBreakpointStore
                 -> DebugHandleStore
                 -> DebugArtifactStore
```

`McpServer` 不识别具体业务工具。静态调用保持 WPF Dispatcher；调试对象访问通过 `DbgManager.Dispatcher.BeginInvoke()` 和一次性 Task completion bridge 获取 DTO。initial launch 与 restart 的每次 Start 尝试是唯一线程例外：一个 WPF Dispatcher callback 只串行执行 reservation/start-claim 建立、`DbgManager.IsDebugging` 预检和 `DbgManager.Start`，只读取不可变 launch DTO 与线程安全 claim 状态，不读取或保留任何调试对象；Start 内部异步投递 debugger thread 后 callback 立即返回。process/runtime 匹配、建权、状态、事件、句柄和值解析全部只在 `DbgManager.Dispatcher` 完成。该 callback 不是覆盖人工 UI 的原子锁，不能据此声称排除 UI 并发 Start。事件处理器不得等待 HTTP、WPF、磁盘或另一 dispatcher。

coordinator 仅为 launch 建立含 request_id、开始单调时间、launch mode、expected runtime/architecture/path/file ID 的 start claim。claim 建立前必须验证 CON-DYN-014 gate 并快照现有 process/runtime；仅 claim 后、30 秒内新增且恰好一个完整匹配的 process/runtime 才在专用实例前提下成为 owned target。net48-exe/coreclr-apphost 要求新 process image 匹配 target identity；coreclr-dotnet 要求 process image 匹配 host identity 且同一 process 中 module-loaded 匹配 target identity；harness 要求 process image 匹配 harness identity 且同一 process 中 module-loaded 匹配 target identity。0 个超时、多个新增、任何不匹配新增，或目标 process 同时包含非 claim runtime，均使 claim 失败；MCP 不控制任何新增对象。若专用实例前提被违反，身份规则不提供无条件因果证明，按 DEC-DYN-001 接受残余风险。pause/continue/terminate 只调用 owned `DbgProcess` 实例操作；禁止 `BreakAll`、`RunAll`、`StopDebuggingAll`、`TerminateAll`、`DetachAll` 和 `DbgManager.Restart`。launch restart 按 CON-DYN-012 重新启动。

API-DYN-006/008/009 每次在 control-lane admission 成功时就创建内部 `ControlOperationRecord`，固定含 `session_id`、`generation`、单调递增的 `control_epoch`、`request_id`、`operation`、`prior_state`、`phase`∈{`scheduled`,`issued`,`settled`} 和以 `Stopwatch.GetTimestamp()` 计算的 30 秒 monotonic deadline；同一 active session 同时至多一个未 settled control record。deadline 起点是 cache reservation 与 control-lane slot 均已取得、但 Break/Terminate 尚未投递的时刻，包含 lane 等待、artifact 取消握手、dispatcher 排队和等待状态/退出事件的全部时间。scheduler 按 CON-DYN-013 优先 control lane；若存在 active artifact record，continue/restart/terminate/step 在改变或保留对应 lifecycle 状态后请求取消并最多等待 2000 ms grace。grace 内 artifact 完成最终对账时按正常路径继续；grace 后仍 pending 时，只要求 artifact request/cache 封口、general slot 让出并建立 canceling barrier，control 随即继续，不能仅因 I/O 未最终完成而以 `TIMEOUT` 结算或禁止上游调用。control 的 30 秒总 deadline仍继续计时；只有该 deadline 自身先获胜才返回 `TIMEOUT`。dispatcher callback 在调用上游前必须以 compare-and-swap 把 phase 从 scheduled 改为 issued；若记录已 settled则不得迟到调用上游。固定 deadline timer 只访问线程安全 coordinator 元数据、响应 gate、cache/queue 计数和事件 DTO，不读取、关闭或控制任何 dnSpy 对象；它以同一 compare-and-swap 与显式失败/正常观察竞争，确保请求 envelope、EVT-DYN-021、cache in-flight Task 和 control-lane slot 各结算恰好一次。deadline 获胜固定返回 `TIMEOUT`，可明确归属当前 control record 的同步异常或 adapter `explicit_failure` 固定返回 `INTERNAL_ERROR`；两者均写恰好一条 EVT-DYN-021。`control_epoch` 只排序本地 control record、封口响应并阻止 settled restart 复活或 generation 增加，不得被当作上游 paused/process-removal 事件的字段或因果证明；请求一旦 settled，任何观察都不得改写其缓存响应、EVT-DYN-021、cache/queue 结算或 reservation。

coordinator 另维护只由 DbgManager dispatcher 写入的 `observed_process_state`∈{`running`,`paused`,`exited`,`unknown`}：建权时从 owned `DbgProcess.State` 初始化，既有 continue/step 成功转移同步置 running，paused/removal 再按下述规则更新。上游 paused/process-removal 事件先且只按 active `session_id`、`generation` 和完整 owned process identity 验证；旧 session/generation/非 owned identity 一律不得改变状态或产生第二个 terminal event，但验证通过的真实观察绝不因存在较新 `control_epoch` 而丢弃。除 3.5 break_kind 已固定原因的 initial pause 外，每次 running→paused 观察必须在同一 dispatcher 事务中先读取 owned runtime 的完整 `BreakInfos` 快照，以原 collection ordinal 为次序并按封闭优先级 `exception > breakpoint > step > entry > process > manual > unknown` 选择唯一 primary cause：仅当前 session policy 要求暂停的 `ExceptionThrown` 可候选 exception；`BoundBreakpoint` 候选 breakpoint，能映射到 owned breakpoint 时附 breakpoint_id，不能映射时仍可作为 breakpoint primary 但不得伪造 EVT-DYN-013；只有匹配当前未完成 MCP step_id 的 `StepComplete` 可候选 step；`EntryPointBreak` 候选 entry；`ProgramBreak` 候选 process；`Break` 只有在当前唯一 pause record 已处于 issued 且尚未 settled 时才候选 manual；空集合、Unknown/Connected、未匹配 step 或无 issued pause 的 Break 一律候选 unknown。多个同优先级候选取最小 original ordinal，禁止按事件到达时机改序。paused 观察固定执行：①先把 observed_process_state 置 paused；②若公开状态为 running，增加 pause_epoch、转 paused，先写恰好一次 EVT-DYN-010（primary cause 及其 thread/location/owned breakpoint_id），随后按 `exception,breakpoint,step` 优先级和原 ordinal 写全部可构造的 EVT-DYN-014、owned-only EVT-DYN-013、current-step-only EVT-DYN-015；同一 break info 不重复写。若存在唯一未 settled pause record，scheduled/issued 均以“目标状态已满足”结算，scheduled callback 随后见 settled 必须不调用 Break；API-DYN-006 的 reason 是实际 primary cause，`request_effect` 在 stock dnSpy v6.6.0 下固定为 `state_satisfied`。即使 primary=manual 且 record=issued，也不得仅凭当前 record 与无 token Break 观察声明 caused_pause；P1 的迟到 Break 在 P2 issued 后到达时，P2 只可返回 `reason=manual,request_effect=state_satisfied`。已封口旧 pause response 保持原 TIMEOUT/INTERNAL_ERROR；③若公开状态已 paused，只去重观察，不重复 pause_epoch/事件；④若公开状态为 restarting/stopping/faulted，则保持该 lifecycle 状态，只在 status 暴露 observed_process_state=paused，不结算不兼容的 terminate/restart record。pause 自身在 scheduled/issued 明确失败或 deadline 时仍以当时 public running 返回 INTERNAL_ERROR/TIMEOUT且不使 handle 失效；若它已 settled 后才观察 paused，按②更新 public state，但没有仍 issued 的 record 时 Break 只能归 unknown，因此下一次 API-DYN-007 可正常 continue且旧 response 不变。

owned process removal 是权威 terminal 观察：先把 observed_process_state 置 exited，并在同一 dispatcher 事务中使 handle 失效、释放 ownership、写恰好一次 EVT-DYN-004；若唯一未 settled record 是 terminate（含首调与 confirmed-owned retry），则 scheduled/issued 均以目标已退出结算 API-DYN-009 成功，scheduled callback 不再调用 Terminate。若它是未 abandoned 且未 settled 的 restart，且在 deadline 前观察，则只按正常 restart 路径保留 session/reservation并进入 post-exit stopping→重新 lease/Start；若 restart 已 settled、`abandoned_restart=true` 或 control failure 已封口，则绝不 Start/增加 generation，而以 EVT-DYN-020(reason=restart_failed) terminal。其他非 restart removal 固定以 EVT-DYN-020(reason=terminated，非控制的意外退出仍按既有实际 reason) terminal 并回 idle；若此时有不兼容的未 settled pause record，先以 INTERNAL_ERROR、current_state=idle 和 EVT-DYN-021 结算它，不得留下 timer。T1 terminate 已 TIMEOUT 后的 T2 retry，无论 removal 在 T2 scheduled 还是 issued 到达，都只结算 T2 成功，T1 缓存响应和 EVT-DYN-021 不变；没有 T2 时仍只做一次 terminal 清理。terminate/restart 若在 phase=scheduled 时明确失败或超时，因上游尚未调用而恢复 prior_state，restart 同时释放 reservation；一旦 issued 后失败或超时仍进入 `faulted`，保留 active session、confirmed-owned identity，restart 另释放 reservation并设 `abandoned_restart=true`，直到上述 removal 或同 process terminate retry。若目标永不移除，唯一退出是重试 terminate或由操作者结束该 confirmed-owned process并等待权威 removal；不得 force-reset、假报 idle或改控其他对象。

公开状态固定为 `idle`、`starting`、`running`、`paused`、`restarting`、`stopping`、`faulted`；`attaching` 不属于 v1 enum。终止或进程退出完成后回到 `idle`，最终原因保留在事件中。

- `generation` 在请求通过参数/安全检查并取得唯一 start reservation、即将调用 Start 时增加；Start 或 claim 随后失败也不得复用该 generation。restart 仅在旧 generation 全部句柄失效后取得新 generation。
- `pause_epoch` 在进入暂停和离开暂停时增加。
- handle 包含 session、generation、pause_epoch 和对象定位；不匹配返回 `STALE_HANDLE`。
- HTTP 层不得缓存 dnSpy process/thread/frame/value 对象；解析、读取、关闭均在 debugger dispatcher 内完成。
- Start 在取得 owned process 前失败时依次写 EVT-DYN-002、EVT-DYN-020，释放 reservation 并回到 `idle`；owned target 正常或意外退出时使全部 handle 失效，依次写 EVT-DYN-004、EVT-DYN-020 并回到 `idle`。restart 为封闭例外：进入 `restarting` 时取得唯一 restart reservation 并保持原 active session；终止旧 owned process 正常按时移除只写 EVT-DYN-004，不写 EVT-DYN-020，旧 process 移除后公开状态为 `stopping` 而非 `idle`；重新校验/锁定并增加 generation 后直接进入 `starting`。成功进入 running/paused 后才释放 restart reservation；Start/claim 阶段失败写 EVT-DYN-002、EVT-DYN-020、释放 reservation/session 后回 `idle`，歧义按 ownership lost 进入 `faulted`；旧进程终止阶段则严格采用上述 control deadline 和 `abandoned_restart` 规则，不得进入 Start/claim 分支。
- 每个 session 的事件 cursor 从 1 开始且仅在该 session 内单调；EVT-DYN-020 是唯一 terminal event，写入后冻结。终止 session 的事件日志保留到 terminal 后 10 分钟或下一次 launch 取得 start reservation（二者先到者），之后以该 session_id 调 read/wait/status 返回 `NOT_FOUND`；不得把新 session 事件映射到旧 session_id。
- ownership lost 后保持 `faulted`，清空“可控制”标志但保留只读事件身份。仅当已确认 owned process 自行退出，或 `DbgManager.IsDebugging == false` 且 manager 中已无 claim 后新增 process/runtime 时，清空句柄和 claim、写 recovery 后回到 `idle`。在此之前只允许 capabilities、status、read/wait events；不得以 terminate 试图清理归属不明对象。只有上一段由 issued terminate/restart 控制失败产生、且仍保有已确认 owned identity 的 `faulted` 是 terminate 重试例外；两类 fault reason 必须由 coordinator 封闭枚举区分，不得只按字符串或进程 PID 猜测。

稳定 ID `debug_list_attachable_processes`（API-DYN-004）、`debug_attach`（API-DYN-005）、`debug_detach`（API-DYN-010）是 v1 禁用能力：三个 protocolVersion 的 tools/list 都不得广告；直接 tools/call 必须返回 `CAPABILITY_UNAVAILABLE` 且无副作用。启用时 tools/list 恰含上述 22 个活动工具，关闭或未确认专用实例时只比现有静态工具多 `debug_capabilities`。

### 3.4 响应、错误与能力

协商后的 MCP protocolVersion 决定 tools/list 与 tools/call 的外层表示，内部 `dnspy.debug.v1` envelope 不随版本变化：

| MCP protocolVersion | tools/list 中动态工具 | tools/call result |
|---|---|---|
| `2024-11-05` | 只含该版本允许的 name、description、inputSchema，必须省略 outputSchema | 只含 `content` 和领域失败时的 `isError=true`，必须省略 structuredContent；恰好一个 text content block 的 text 是 canonical JSON envelope |
| `2025-03-26` | 只含该版本允许的 name、description、inputSchema，必须省略 outputSchema | 只含 `content` 和领域失败时的 `isError=true`，必须省略 structuredContent；恰好一个 text content block 的 text 是 canonical JSON envelope |
| `2025-06-18` | 每个广告的动态工具除 name、description、inputSchema 外必须含表达本节成功/失败 envelope 的 outputSchema；三个固定禁用 API 不在 tools/list 中 | 同时含上述 text content block 与 structuredContent；解析 text 后与 structuredContent 做 JSON 深比较必须相等；领域失败还含 `isError=true` |

现有 32 个静态工具在三版本下的 tools/list 与 tools/call wire shape 保持既有快照，不因本方案新增 outputSchema 或 structuredContent。以下是三版本共同表达的成功 envelope；字段全集固定，禁止额外字段：

```json
{
  "schema_version": "dnspy.debug.v1",
  "ok": true,
  "debug_context": {
    "session_id": "opaque",
    "generation": 1,
    "pause_epoch": 2,
    "event_cursor": 10,
    "state": "paused"
  },
  "result": {},
  "warnings": [],
  "untrusted_sample_data": false
}
```

失败对象把 `result` 替换为 `error` TYPE-DYN-011，`ok=false`，其余四个顶层字段仍必须存在；成功对象不得含 `error`，失败对象不得含 `result`。`warnings` 是最多 32 项、每项最多 1024 UTF-8 字节的服务端诊断 string array，不承载恢复协议。`untrusted_sample_data` 是 mandatory boolean：result/error/warnings 中任一文本或路径来自目标进程、样本元数据或样本输出时为 true，否则 false；客户端必须把 true 的整个 payload 当作数据而非指令。

领域错误固定包含 `DEBUG_DISABLED`、`CAPABILITY_UNAVAILABLE`、`INVALID_STATE`、`STALE_HANDLE`、`TARGET_MISMATCH`、`NOT_FOUND`、`ALREADY_EXISTS`、`LIMIT_EXCEEDED`、`TIMEOUT`、`OWNERSHIP_LOST`、`REQUEST_ID_REUSE`、`INTERNAL_ERROR`。错误 tool result 设置 `isError=true` 当且仅当 envelope 的 `ok=false`。HTTP 认证/CIDR 失败严格按 CON-DYN-006 在解析 JSON-RPC 前返回唯一的 401 或 403：401 含固定 WWW-Authenticate，403 不含；二者 body 均为空且无 MCP tool result。保留字 `UNAUTHORIZED` 在 v1 tool schema 中不得产生。协议级 JSON-RPC error 只承载 parse、method、invalid params 和服务器无法构造上述 envelope 的内部失败，不承载调试领域失败。

TYPE-DYN-011 的 code/message/recovery 固定一一映射，handler 不得按 API、异常文字或本地化资源改写：

| code | message | recovery |
|---|---|---|
| `DEBUG_DISABLED` | `Debug tools are disabled.` | `enable_debug_tools` |
| `CAPABILITY_UNAVAILABLE` | `The requested capability is unavailable.` | `choose_supported_workflow` |
| `INVALID_STATE` | `The operation is invalid in the current state.` | `query_status` |
| `STALE_HANDLE` | `The referenced handle is stale.` | `reacquire_handles` |
| `TARGET_MISMATCH` | `The target identity no longer matches.` | `reacquire_target` |
| `NOT_FOUND` | `The requested resource was not found.` | `requery_resource` |
| `ALREADY_EXISTS` | `The requested name already exists.` | `choose_new_name` |
| `LIMIT_EXCEEDED` | `A fixed resource limit was exceeded.` | `reduce_request_or_wait` |
| `TIMEOUT` | `The operation timed out.` | `wait_for_state` |
| `OWNERSHIP_LOST` | `Exclusive target ownership could not be established.` | `manual_resolve_then_wait_idle` |
| `REQUEST_ID_REUSE` | `The request_id was reused with different arguments.` | `use_new_request_id` |
| `INTERNAL_ERROR` | `An internal error occurred.` | `inspect_server_log` |

动态 tools/call 的固定判定顺序为：HTTP 认证/CIDR → short/long worker admission → 原始 body 限额与严格 UTF-8 解码 → JSON-RPC parse/method → transport session admission（若本请求分配）→ Draft 2020-12 结构 schema 校验 → `dnspy.debug.utf8-limits.v1` 确定性 UTF-8 字节校验 → API-DYN-001 直接执行，或 API-DYN-004/005/010 返回 `CAPABILITY_UNAVAILABLE`，或其余 API 在 `effective_debug_launch=false` 时返回 `DEBUG_DISABLED` → `effective_debug_launch=true` 时才进入 request_id cache/队列、coordinator state、session/generation/pause_epoch、资源预算及目标操作。worker/session admission 超限按 CON-DYN-009 返回 HTTP 429；原始 body 超限返回 HTTP 413；非法 UTF-8 字节序列或 malformed JSON 返回 JSON-RPC `-32700`；结构或 JSON 解码后 input string 的字节边界无效返回 JSON-RPC `-32602`，这些结果都不能被领域错误覆盖且业务副作用为零。严格 UTF-8 编码器拒绝未配对 surrogate，JSON 解码后的输入按 `-32602`，服务端输出出现该值则返回小型 `INTERNAL_ERROR` envelope。标准 schema 的 `maxLength` 只约束字符数，不得代替字节校验；字节数唯一使用严格 `Encoding.UTF8.GetByteCount` 对 JSON 解码后的 string 计算。`CAPABILITY_UNAVAILABLE` 优先于 `DEBUG_DISABLED`；`DEBUG_DISABLED` 优先于 `INVALID_STATE`、`NOT_FOUND`、`TARGET_MISMATCH`、`STALE_HANDLE`、`REQUEST_ID_REUSE` 和 `LIMIT_EXCEEDED`。在上述提前返回路径中，除完成适用的 admission/body/read/parse/结构/字节校验外，cache/queue/reservation/Dispatcher/文件系统/DbgManager/目标副作用计数均保持不变。

`-32700` 的 JSON-RPC object 固定恰为 `jsonrpc="2.0"`、`id=null`、`error={code:-32700,message:"Parse error"}`，error 不含 data；由 Legacy SSE、Streamable HTTP 或 plain HTTP 沿各自既有 JSON-RPC response transport 发送，不包装成 tool result。HTTP 429/413 则没有 JSON-RPC object。

仓库必须新增 `tests/debug/contracts/dnspy.debug.v1.utf8-limits.json`，顶层固定 `schema_version=dnspy.debug.utf8-limits.v1` 和按 JSON Pointer ordinal 排序的 `limits`。每项恰含 `pointer`、`direction`∈{`input`,`output`,`both`}、`max_utf8_bytes`。结构 schema 必须固定并复用以下 `$defs` 名称，清单也必须恰含这些 pointer/方向/上限：`/$defs/opaque_handle`/both/1024、`/$defs/session_id`/both/1024、`/$defs/page_cursor`/both/1024（含 next_page_cursor）、`/$defs/warning`/output/1024、`/$defs/value_node/properties/name`/output/65536、`.../type`/output/65536、`.../display`/output/65536、`/$defs/unsupported_target_evidence/properties/value`/output/1024、`/$defs/debug_list_attachable_processes_args/properties/name_filter`/input/256、`/$defs/debug_dump_module_args/properties/relative_name`/input/128；省略号只在本文排版中代表同一 `/$defs/value_node/properties/` 前缀，实际 JSON 必须写完整 pointer。TYPE-DYN-007.unavailable_reason 是结构 schema 的封闭 enum，不进入字节清单。所有 wire handle 字段必须 `$ref` opaque_handle，所有 session_id/page cursor/warning/evidence/value-node/input 字段必须引用对应 `$defs`，不得复制出第二套边界。输入超限在副作用前为 `-32602`；仅 TYPE-DYN-007 的 name/type/display 可在 Unicode scalar 边界截为最大合法前缀，并置该 node、PageResult 与 ValueBudgets 的 truncated=true；其他服务端生成输出（含 warning、evidence.value、handle、session/cursor）违反清单时返回小型 `INTERNAL_ERROR` envelope。结构 schema 与此清单共同构成公共契约；handler 不得硬编码未列出的字段级字节上限；CON-DYN-009/013 的 whole-body、whole-result 和 cache payload 总字节预算是独立资源计数，不属于字段清单。

### 3.5 公共类型、工具和事件契约

本节是 `dnspy.debug.v1` 的规范 schema。字段名后的 `?` 表示可选；未标 `?` 的字段必须存在。字符串均为 UTF-8 JSON string；时间为 UTC RFC3339、固定毫秒和 `Z`；未另行限定的 JSON integer 位于 `0..9007199254740991`。PID 为 `1..4294967295`；exit_code 为 `-2147483648..2147483647`。地址使用 `0x` 加 1—16 位小写十六进制；SHA-256 为 64 位小写十六进制；MVID 为小写 `D` 格式 GUID；metadata token 为 `0x` 加 8 位小写十六进制。runtime_family∈{`net48`,`coreclr`}，architecture∈{`x86`,`x64`}。所有 handle、session_id、page_cursor 和 next_page_cursor 是服务端生成、最多 1024 UTF-8 字节的无填充 base64url opaque string，客户端不得解析。事件 envelope 的 cursor 为 integer `1..9007199254740991`；DebugContext.event_cursor、API event 的 after_cursor/next_cursor/earliest_cursor/terminal_cursor 为 integer `0..9007199254740991`，0 表示该 session 尚无事件或从日志起点读取。两类游标不得互换。

API-DYN-020 第一次取页时先按 CON-DYN-009 预留 snapshot 槽，再在当前 pause_epoch 建立最多 1024 个 locals 根节点的 immutable snapshot，保持 provider 原始顺序；每页只返回 page_size 指定的最多 100 项，后续 page_cursor 只续读同一 snapshot。API-DYN-021 第一次取页时同样先预留槽，再以输入 value_handle 为请求根，使用上游对每个 parent 的原始直接子节点顺序做确定性 breadth-first 遍历；只使用 CON-DYN-007 的 raw field/array child API，在请求 depth 与全局 4 层上限内物化最多 1024 个 descendant（不重复返回输入根），并绑定为当前 pause_epoch 的 immutable expansion snapshot，后续 page_cursor 只续读该 snapshot且不得重新求值。更深节点的 parent 可位于同一 snapshot 的更早页，不在当前页重复。物化时按最终 provider/BFS 序列为每个可展开节点预分配独立 value_handle 并写入 immutable parent 引用，跨 snapshot 不去重；当前页 canonical response 完成后只把该页 handle 从 snapshot-owned 原子转移为 returned-handle。最终页只销毁 snapshot/page cursor 并释放 2-slot，已转移 handle 保留到 epoch 结束；未完成 snapshot 的未发出 handle 继续计入同一上限。达到 4096 handle 上限时按 TYPE-DYN-007 返回不可展开的截断节点，不再分配 handle或物化其 descendant；创建/序列化失败关闭本 snapshot 的全部未转移 handle并释放 slot。命中 depth/node/value-handle/string 预算时，受影响的 frontier parent 或 string node 的 `truncated=true`，TYPE-DYN-003.truncated 与 TYPE-DYN-017.truncated 同为 true；仅因 page_size 尚有后续项时二者都为 false并返回 next_page_cursor。continue/restart/session terminal 后所有 snapshot/page_cursor/value_handle 一并为 STALE_HANDLE，两类 value handle 在 debugger dispatcher 各关闭恰好一次。

API-DYN-003 的 launch_mode 与参数组合固定如下，任何多余、缺失或跨模式字段均为 JSON-RPC `-32602`，不得猜测或降级：

### 3.6 状态、转移、重复与并发

`Y` 表示允许，`R` 表示只允许读取已完成/故障 session 的保留事件，`Y*` 表示只允许本节定义的 confirmed-owned control-fault 恢复，`N` 返回 INVALID_STATE。faulted/terminate 不满足 Y* 时，fault reason=ownership_lost 固定返回 OWNERSHIP_LOST，其他 fault reason 返回 INVALID_STATE；不得仅因存在 PID 放行。表中 active/paused 的 session/generation/pause_epoch 仍须匹配。本矩阵只在 3.4 固定门禁通过且 `effective_debug_launch=true` 后适用；API-DYN-001 不进入矩阵，API-DYN-004/005/010 不参加状态判定并在任何状态先返回 `CAPABILITY_UNAVAILABLE`，其余 API 在 gate=false 时先返回 `DEBUG_DISABLED`。

固定转移：

- idle + launch → starting；claim 成功 → running 或 paused；Start 错误、0 个匹配超时 → 写 start_failed/session_end 后 idle；歧义或可检测的外部并发 → faulted。
- running + pause → paused；scheduled/issued pause 的 explicit failure 或 30 秒 deadline 按 3.2 返回 INTERNAL_ERROR/TIMEOUT并在响应时保持 running。其后任何同 session/generation/owned identity 的真实 paused 观察都不看 control_epoch：public running 固定按 BreakInfos primary cause 转 paused并允许 continue；当前唯一 pause record 若仍 scheduled/issued则以实际 reason 和固定 `request_effect=state_satisfied` 结算，若已 settled则只对账状态且绝不改写旧 response。无 issued pause + Break、无可映射 break info 和已 settled pause 的 late Break 都必须 reason=unknown，不得伪造 manual。paused + continue → running。
- paused + step → running；收到同 step_id 的 StepComplete 或异常，按 3.2 先写 EVT-DYN-010，再写 EVT-DYN-015 或 EVT-DYN-014并转 paused；step 与 breakpoint/exception 同一 stop 时按封闭 cause 优先级只选一个 EVT-DYN-010 primary reason，但全部可构造 detail event 仍按固定顺序各写一次。无法匹配当前 step_id 的 StepComplete 不得生成 EVT-DYN-015或把 cause 标为 step。
- running/paused + restart → restarting → stopping → starting → running/paused；全过程保留原 active session 和唯一 restart reservation，公开状态不得经过 idle。旧 process removal 只有在当前 restart record 未 settled、未 abandoned 且 deadline 前到达时才进入 post-exit stopping→重新校验/锁定→generation 增加→starting；Terminate 尚未 issued 即失败/超时时恢复 prior_state 并释放 reservation；issued 后失败/超时进入 confirmed-owned control-faulted、释放 reservation、设置 abandoned_restart并禁止 Start/新 generation，任何随后 removal 只写 process_exited/session_end(reason=restart_failed) 后 idle。
- running/paused + terminate → stopping → 写 session_end → idle；Terminate 尚未 issued 即失败/超时时恢复 prior_state，issued 后失败/超时进入 confirmed-owned control-faulted。该 faulted + terminate 只可重试同一 owned process；actual removal 在重试 scheduled/issued 任一阶段都结算当前 retry 成功并使其 callback no-op，然后只写一次 process_exited/session_end(reason=terminated) 并 idle；旧 timeout/error response 永不改变。
- 非 restart 的 target exit → 写 process_exited/session_end 后 idle；ownership ambiguity → faulted；faulted 只按 3.2 的观察条件写 recovery/session_end 后自动回 idle，无公共 force-reset。

gate=true 后，统一副作用请求缓存先于 session 查找、start reservation 和命令队列判定；因此 launch 在 session_id 产生前的并发重试也共享同一 in-flight Task 和最终响应。active session 的有副作用队列按 CON-DYN-013 固定为 control 8 + general 56、总容量 64；任一 lane 或总量越界都在入队前返回 LIMIT_EXCEEDED。control record 在 lane admission 时建立并开始 deadline；general 请求状态在真正取得 coordinator mutation 时复核。排队或 artifact worker 期间发生 state/generation/pause_epoch 变化的请求返回 INVALID_STATE 或 STALE_HANDLE；artifact 在 CreateNew 后的特殊结算只按 CON-DYN-009 记录 aborted_owned。缓存保留、容量、RFC 8785 参数规范化和 ID 复用严格执行 CON-DYN-013；不得因 session 已终止而提前丢弃。终止事件日志按 3.2 的独立窗口保留，缓存命中不延长事件窗口。所有 page_cursor 绑定查询筛选和 generation；数据变化导致 page_cursor 无法继续时返回 STALE_HANDLE，不静默重新从第一页开始。restart reservation 和 control lane 优先于 new launch、general lane 与静态 mutation gate；post-exit/pre-Start 窗口内 new launch 和六个静态写工具均必须为 INVALID_STATE。三个禁用 API 始终先返回 CAPABILITY_UNAVAILABLE，不进入缓存、reservation 或任一 lane。

## 6. 验收契约

## 7. Fallback 清单

### FB-001：raw runtime bytes 不可用时重构托管 PE

- 依据：REQ-DYN-010、RACC-DYN-007；EVD-API-005 明确 raw bytes 可不可用且 ForceMemory metadata 可用。
- 触发条件：托管模块的 raw bytes 不可用，且 ForceMemory metadata 成功。
- 行为和影响：输出 `reconstructed` PE；manifest 声明非原始字节、重构 API 与布局，不用于原始文件哈希等价判断。
- 退出方式：raw bytes 可用即优先 raw；两者均不可用返回 `CAPABILITY_UNAVAILABLE`，不调用进程外 dump 工具。

### FB-002：不支持 runtime 的工作流交接

- 依据：REQ-DYN-002、REQ-DYN-003、NON-DYN-001、RACC-DYN-010。
- 触发条件：识别为 Unity/Mono、混合模式原生阶段、纯原生，或契约报告 runtime 不支持。
- 行为和影响：不创建/继续伪托管 session；API-DYN-003 以 CAPABILITY_UNAVAILABLE 返回 TYPE-DYN-019 的受限种类、证据和 recommended_workflow；不得仅用 message 承载，不得由三个固定禁用 API返回 details。
- 退出方式：用户切换工作流，或未来经独立审核方案新增 capability；v1 不降级为 GUI 自动化。

除 FB-001、FB-002 外无 fallback。认证失败、端口占用、hash/path/所有权/ArtifactRoot lease 不符、未知/无效 artifact child、设置验证或 staged/committed 提交失败、非法状态、过期句柄、预算超限、缺显式宿主、memory 超范围均直接失败；ApplySnapshot 只激活 committed、失败时恢复 old server或强制 Stop、孤立 pending 启动时 fail closed；artifact store 对 active/known_retained/stale 全部内容保持零自动删除，只有当前进程账本精确重验的 known_retained 不阻断，stale/超限要求停扩展后人工清空再重启；control operation 的 TIMEOUT/INTERNAL_ERROR、confirmed-owned faulted、权威状态对账和已封口响应保护都是主流程安全失败/恢复处理，不是 fallback。不得以 fallback 掩盖主流程错误。
