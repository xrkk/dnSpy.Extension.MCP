## 5. 审计意见

### AUD-023：artifact 清理的“自有”判定可由同用户数据满足，存在删除非自有文件的路径

- 严重性：高。
- 来源与方案位置：REQ-DYN-010、REQ-DYN-011、CON-DYN-008、RACC-DYN-007、IMP-009、ACC-019；方案第 2.2、4、6 节；EVD-OS-001。
- 风险：方案把可观察、可复制的结构字段当作跨重启的所有权证明。句柄 final path、volume serial 和 file ID 只能证明“正在操作哪个对象”，不能证明“该对象或其每个 child 由扩展创建”。因此清理可把同用户写入的数据误分类为扩展自有数据。
- 证据：CON-DYN-008 规定 marker 只含固定 schema、目录名相同的 session_id、created_utc 和当前 ArtifactRoot 身份；这些值均可由能写默认用户临时目录的进程构造。该节随后会在 marker 结构有效且超过 7 天时，对 session 目录中的每个 direct file 仅做 reparse/身份 preflight 后逐项删除，没有逐 child 的来源登记或允许清单。紧随其后的全局配额段又明确承认“外部同用户进程可制造未知项”，并声称 invalid/伪造 marker 永不自动删除，但正文没有区分“结构有效的伪造 marker”和真实 marker 的机械谓词。即使 marker 来自真实旧 session，同用户进程在 terminal、目录 lease 释放后插入一个普通 direct file，该文件也会通过当前 preflight 并被删除。ACC-019 只覆盖字段缺失/不匹配、reparse、嵌套目录和身份替换，没有覆盖结构完全合法的伪造 marker、复制的旧 marker，或向合法过期 session 注入未登记普通文件。
- 影响：违反 RACC-DYN-007 的目录隔离和“清理只删自有数据”承诺；会导致非自有数据删除。该缺口同时使 CON-DYN-008 的 `invalid/伪造 marker` 分类、IMP-009 的直接编码条件和 ACC-019 的通过边界不成立。
- 建议：必须在当前 threat boundary 内二选一并写成唯一契约：一是取消跨重启自动删除，未知或无法证明来源的 stale session 只报告并由操作者处理；二是建立相对于“可写 ArtifactRoot 的同用户进程”仍可信的 session/child provenance，并只删除逐项登记且身份/内容均匹配的 child，任何未登记 child 都使该 session 零删除。单独增加由同一用户可取得密钥生成的 HMAC、或只增强 marker 结构校验，不足以闭合已声明的同用户边界。ACC-019 至少新增四个确定性 fixture：结构合法的伪造 marker、复制旧 marker、新建伪 session、合法过期 session 在 terminal 后注入未登记普通文件；所有反例必须证明零删除。
- 最小闭合条件：CON-DYN-008、IMP-009、ACC-019 对所有权信任根、逐 child 判定、未知项处理和删除范围给出同一机械规则，并能让上述四个反例零删除；否则本意见未关闭。

### AUD-024：pause/terminate/restart 依赖异步上游事件，却没有完成期限、失败映射和晚到事件规则

- 严重性：高。
- 来源与方案位置：REQ-DYN-004、CON-DYN-003、CON-DYN-004、CON-DYN-009、CON-DYN-012、CON-DYN-013、RACC-DYN-004、API-DYN-006/008/009、TYPE-DYN-011、IMP-004/005、ACC-007/008/034；方案第 3.2、3.5、3.6、4、6 节；SRC-API-001/EVD-API-001/EVD-API-007。
- 风险：请求可永久保持 in-flight，active-session command queue 无法前进，coordinator 停在 stopping/restarting 或等待 paused，request_id 重试永久等待同一 Task，六个静态写工具也因非 idle 状态永久被阻断。实现者无法判断何时返回 TIMEOUT、是否进入 faulted、是否保留 owned process/session，以及 deadline 后的晚到 break/disconnect 事件如何处理。
- 证据：上游 `DbgProcess.cs` blob `c9691fea6cd3e090e1b0215b800cc3d1a463e628` 的 `Break()`、`Run()`、`Terminate()` 都是返回 void 的命令。`DbgManagerImpl.cs` blob `841ba23fa194df7156878542b167b01edb825f55` 明确 `DbgThread(Action) => Dispatcher.BeginInvoke(callback)`；逐进程 `Terminate`/`Break` 只把命令异步排入 dispatcher，而 process 真正从集合移除、状态改为 Terminated 和 process-exited message 发生在后续 OnDisconnected 路径。CorDebug `DbgEngineImpl.cs` blob `a0353d02968c3018dbf25571ac09ca1c5db9b802` 的 BreakCore 还能在 `TryBreakProcesses` 失败时发送错误消息，TerminateCore 只调用 `TerminateProcesses()`，没有向扩展返回可等待的 Task。方案仅为 launch claim 和 debug_wait_event 写了 30 秒上限；CON-DYN-012/状态机要求 restart“等待移除”，API-DYN-006 要返回 `state=paused`，API-DYN-009 要返回 `state=idle` 和 terminal_cursor，但没有控制完成 deadline、错误到 DomainError/EVT 的映射或晚到事件 fencing。TYPE-DYN-011 已定义 TIMEOUT，却没有把它列入 API-DYN-006/008/009。现有 ACC 只验证正常完成和人工 barrier，不注入 Break error、永不 disconnect 或 deadline 后迟到 disconnect。
- 影响：REQ-DYN-004 的显式状态机、RACC-DYN-004 的可复现 lifecycle、CON-DYN-009/013 的资源上限以及 API-DYN-006/008/009 的精确结果都不闭环；正常路径也可能因上游未完成而永久失去可用性。
- 建议：为所有需要观察上游状态/事件才能形成响应的控制操作固定 monotonic deadline，并逐项定义：deadline 起点、TIMEOUT 或其他固定错误、coordinator/session/ownership/handle/queue/cache 状态、是否允许后续操作、晚到 break/disconnect/process-exited 的代际 fencing 和唯一恢复路径。terminate/restart 超时不得声称 `idle` 或启动新 generation；只有实际观察到 owned process 移除后才能释放相关所有权。把这些字段和错误加入 API/TYPE/EVT/状态表及 IMP-004/005，而不是留给 handler 自行判断。
- 最小闭合条件：用上游可注入 seam 在 ACC-007/008/034 或新 ACC 中覆盖 Break 明确失败、Break 永不完成、Terminate 永不产生 disconnect、deadline 前完成、deadline 后晚到完成和 restart 旧进程不退出；每项都必须有唯一 response、终态、事件、资源计数和恢复步骤，且 driver 进程本身有固定超时。否则本意见未关闭。

## 6. fallback 逐项评定

### FB-001：raw runtime bytes 不可用时重构托管 PE

- 评定：通过。
- 依据：REQ-DYN-010、RACC-DYN-007、EVD-API-005、ACC-032。
- 必要性：上游明确允许 raw bytes 不可用，而 ForceMemory metadata 可用；重构只在该已证实分支触发。
- 可退出性：raw 可用即回主流程；重构也失败则固定 `CAPABILITY_UNAVAILABLE` 且零产物。
- 不掩错：manifest 明示 reconstructed 非原始等价，不借进程外工具继续，不掩盖 hash/身份/写入失败。

### FB-002：不支持 runtime 的工作流交接

- 评定：通过。
- 依据：REQ-DYN-002/003、NON-DYN-001、RACC-DYN-010、TYPE-DYN-019、ACC-024/026。
- 必要性：它只把已识别的不支持目标交接到封闭 recommended_workflow，不伪造托管能力。
- 可退出性：用户切换工作流，或未来以独立审核方案新增能力；v1 不在当前流程内降级。
- 不掩错：固定返回 `CAPABILITY_UNAVAILABLE`，不启动进程、不创建 session，也不退化为 GUI 自动化。

结论：两项 fallback 都必要、可退出、不掩盖主流程错误，也未引入无来源复杂度。AUD-023 涉及安全清理/恢复路径而非 fallback；AUD-024 涉及主 lifecycle 的异常终止性，均不能由 fallback 评价抵消。
