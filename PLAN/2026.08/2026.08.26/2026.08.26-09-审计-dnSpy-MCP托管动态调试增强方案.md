## 5. 审计意见

### AUD-025：上游 paused/disconnect 事件不携带 control_epoch，本地 epoch fencing 会丢弃真实状态并错误结算连续控制请求

- 严重性：高。
- 来源与方案位置：REQ-DYN-004、CON-DYN-003/004/009/012/013、RACC-DYN-004、API-DYN-006/008/009、IMP-004/005、ACC-007/008/034；方案第 3.2、3.6、4、6 节；SRC-API-001、EVD-API-001/007/011。
- 风险：v12 把 control_epoch 当作迟到 paused/disconnect 的因果 fencing 条件，但公开上游事件没有该字段。连续同类操作中，扩展不能判断一个真实事件由旧请求还是当前请求产生；按方案的“存在较新 epoch 则只记诊断”规则会让目标实际状态与 coordinator 公开状态分离，并可能让当前请求再次超时。
- 代码证据：DbgManager.cs blob e1c907ebc532b2b66e71a57d86fd1c271f6fd00e 的 ProcessPausedEventArgs 仅含 Process 和 Thread。DbgMessageEventArgs.cs blob 74c63c345fa171b6c6ae0380c6c77d00195578d8 的 DbgMessageProcessExitedEventArgs 仅在 process 基类信息之外增加 ExitCode。两者都没有 request_id、operation 或 control_epoch。DbgManagerImpl.cs blob 841ba23fa194df7156878542b167b01edb825f55 以 Dispatcher.BeginInvoke 排队控制，Break_DbgThread 只有 EngineState.Running 时才调用 engine.Break；OnEnginePaused_DbgThread 发出的 ProcessPaused 仍只带 process/thread。CorDebug DbgEngineImpl.cs blob a0353d02968c3018dbf25571ac09ca1c5db9b802 的 BreakCore 发送通用 break 或 CouldNotBreak 消息，也不携带 MCP 控制标识。
- 方案证据：第 3.2 节规定 pause 超时后保持 public running；迟到 paused 仅在“没有较新 control_epoch 且 public state 仍为 running”时转 paused，否则只记诊断。该节又要求所有 process/state 迟到事件按 session/generation/control_epoch/owned identity fencing。IMP-004/005 把此规则设为不可变，但没有定义上游无 epoch 时如何取得事件所属 epoch。
- 确定性反例：初始 public/actual 都为 running。P1 pause 以 epoch=1 issued，30 秒先到而返回 TIMEOUT，public 仍 running。P2 pause 随后合法出队并取得 epoch=2。此时 P1 引发的真实 paused 到达；事件只有 process/thread。按 v12，因为已有较新 epoch=2，该事件只记诊断，public 仍 running。上游 manager 已把 EngineState 置 paused；若 P2 的 Break_DbgThread 随后执行，它因 EngineState 不再是 Running 而不会再次调用 engine.Break，也不会产生第二个 paused 事件。P2 再次 TIMEOUT，目标实际 paused、公开状态 running；第 3.6 状态矩阵因此拒绝 continue，只能终止目标。terminate 也有同源歧义：T1 issued 后 TIMEOUT，T2 在 faulted 中重试，随后到达的实际 process removal 只有 process/exit code；方案没有唯一说明它应结算 T2、只清理 T1，还是仅作 terminal observation。
- 影响：REQ-DYN-004 和 RACC-DYN-004 的状态机与可复现 lifecycle 不成立；API-DYN-006/009 的 current_state/response、EVT-DYN-010/021、queue/cache 结算和恢复路径无法同时满足。既不能用 control_epoch 证明事件因果，也不能把真实 owned-process 状态静默丢弃。
- 建议：明确区分“请求响应封口”和“权威目标状态对账”。本地 epoch 只能阻止旧请求改写其已封口响应、复活 restart 或增加 generation，不能作为无 token 上游事件的因果证明。对同 session/generation/owned identity 的真实 paused/removal，必须定义一个不依赖虚构 epoch 的唯一仲裁：更新权威实际状态，并机械规定当前兼容 control record 是否由该观察结算；不兼容或无法归因时进入明确的 reconciliation/fault 状态，而不是保持错误的 running。实际 process removal 必须有唯一 terminal 清理，同时规定任何当前 terminate retry 的 response。
- 最小闭合条件：在第 3.2/3.6 节、API-DYN-006/009、IMP-004/005 中写出上述仲裁；ACC-007/008/034 至少覆盖 P1 pause timeout→P2 pause 在 scheduled/issued/settled 各阶段→P1 late paused、pause timeout 后 continue、T1 terminate timeout→T2 retry→disconnect 在 T2 issue 前后到达。每例须固定实际/公开状态、当前和旧 response、EVT-DYN-010/021/terminal、queue/cache 与可恢复操作。

### AUD-026：“非当前 active writer 一律失败关闭”使第二个正常 artifact session 不可达，却仍广告 128 retained sessions

- 严重性：高。
- 来源与方案位置：REQ-DYN-010、CON-DYN-008/009、RACC-DYN-007、API-DYN-001/024、IMP-009、ACC-019/022/032；方案第 2.2、3.5、4、6 节。
- 风险：v12 为避免跨重启误删而采用零自动删除是安全方向，但 admission 规则没有区分“本进程创建且精确未变的只读 terminal session”和“跨重启或外部伪造的 stale session”。结果不是最多保留 128 个合法 session，而是第一个含 artifact 的 session 结束后，后续正常 session 的 artifact 创建全部失败，直到操作者停扩展、人工移走目录并重启。
- 方案证据：CON-DYN-008 规定 active session 目录 handle 只持有到 terminal，marker 只用于当前进程 active-session 写入，不构成跨重启证明；全部 pre-existing 内容统一 stale_untrusted。紧随其后的全局规则要求每次可能增加目录/字节前重扫，并规定 marker“结构合法但非当前 active writer”的项使新增 session/artifact 返回 TARGET_MISMATCH。CON-DYN-004 同时限定一次最多一个 active session。因此一个合法 S1 在 terminal 后必然不再是 current active writer；它作为 retained direct child 会在 S2 第一次 dump 的重扫中触发失败。API-DYN-001、ACC-002/028 却固定广告 artifact_sessions=128，CON-DYN-008/IMP-009/ACC-019 也把 128 当作 retained session admission 上限。
- 确定性反例：从空 ArtifactRoot 启动，S1 launch→pause→debug_dump_module 成功，随后 terminate 到 terminal，目录 S1 保留且 lease 释放。再正常 launch S2→pause→debug_dump_module。S2 创建自身目录前的强制重扫看到 S1 marker 结构合法但非 current active writer；按唯一文字规则返回 TARGET_MISMATCH，无法创建第二个合法 artifact session。现有 ACC-019 的 128/129 fixture 是合成配额边界，没有验证两个连续由扩展合法创建的 artifact-bearing session，故不能证明 advertised 128 的正常可达性。
- 影响：REQ-DYN-010/RACC-DYN-007 的 dump 正常状态变化不闭环；能力上报和现实资源容量不一致；ACC-022 的多运行时 Scenario all 若复用同一 ArtifactRoot 也没有确定执行条件。人工清理是异常退出方式，不能替代正常第二次 API 调用。
- 建议：在不恢复自动删除的前提下二选一并固定为协议。若要保留 128 能力，增加仅限本进程生命周期的已知 terminal-session ledger：保存目录和逐 child 的 final path/file ID/长度/哈希/允许清单；每次重扫完全匹配时把它作为只读 retained 计数而不阻断，任何新增、替换或内容变化立即 fail closed；进程重启后全部降为 stale_untrusted 并继续零删除。若产品明确只允许每个干净 root 一次 artifact-bearing session，则把能力、状态/错误、部署文档和 ACC 全部改为该限制，不得继续以 artifact_sessions=128 表示正常可用容量。
- 最小闭合条件：CON-DYN-008、API-DYN-001、IMP-009 和 ACC-019 对同进程 terminal session、跨重启 session、terminal 后外部注入/改写三类对象给出互斥且机械的 admission；新增 S1 dump→terminal→S2 dump 正例、S1 terminal 后注入 child 反例和重启后 S1 目录反例，并逐例固定 response、tree/hash、ledger、零 DELETE access 和恢复步骤。

## 6. fallback 逐项评定

### FB-001：raw runtime bytes 不可用时重构托管 PE

- 评定：通过。
- 依据：REQ-DYN-010、RACC-DYN-007、EVD-API-005、ACC-032。
- 必要性：上游明确允许 raw bytes 不可用，而 ForceMemory metadata 可用；重构只在该已证实分支触发。
- 可退出性：raw 可用即回主流程；重构也失败则固定 CAPABILITY_UNAVAILABLE 且零产物。
- 不掩错：manifest 明示 reconstructed 非原始等价，不借进程外工具继续，不掩盖 hash、身份或写入失败。

### FB-002：不支持 runtime 的工作流交接

- 评定：通过。
- 依据：REQ-DYN-002/003、NON-DYN-001、RACC-DYN-010、TYPE-DYN-019、ACC-024/026。
- 必要性：它只把已识别的不支持目标交接到封闭 recommended_workflow，不伪造托管能力。
- 可退出性：用户切换工作流，或未来以独立审核方案新增能力；v1 不在当前流程内降级。
- 不掩错：固定返回 CAPABILITY_UNAVAILABLE，不启动进程、不创建 session，也不退化为 GUI 自动化。

结论：两项 fallback 都必要、可退出、不掩盖主流程错误，也未引入无来源复杂度。AUD-025 是主 lifecycle 的事件仲裁缺口，AUD-026 是正常 artifact admission 缺口，都不能由 fallback 评价抵消。
