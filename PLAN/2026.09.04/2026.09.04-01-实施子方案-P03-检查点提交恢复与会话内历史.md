## 1. 目标、入口和边界

P03 把 P02 已验证的私有事务和实时短应用器闭合为唯一产品提交路径：成功提交必须同时得到实时模块目标状态和有效检查点；实时成功而检查点最终切换失败时必须进入可查询、可恢复的 `committed_without_checkpoint`。同一持久谱系包负责历史、Undo/Redo、任意点恢复、三态重放和默认导出身份，旧 6 个写工具只保留一个过渡版本并成为该路径的兼容 Adapter。

入口门禁已经由当前状态满足：

- P01 提供服务端权威 `McpCallContext`、会话关闭事实、VM 执行门禁、调试空闲事实和严格 schema 基线；
- P02 提供全进程单事务、私有 `EditWorkspace`、22 种规范化结构化操作、统一审查、完整指纹、结构/roundtrip 验证、预生成反向动作和实时故障恢复；
- P02 当前没有产品提交、检查点、导出或 Undo/Redo，旧工具仍存在独立实时写入，因此 P03 不依赖任何后序 Pxx 即可实施和验收。

核心维护范围：

- `Editing/` 中协调器、历史 Module、检查点存储、重放/导航、原子导出、部分提交恢复、schema 和测试 seam；
- `Tools/StaticToolProvider.cs` 与 `McpTools*.cs` 的 6 个旧写工具兼容迁移及独立写状态删除；
- `dnspy_mcp/` 新工具便利方法和 stdio 透明转发回归；
- `tests/edit/` 的 P03 契约、fixture、双架构自动编排和持久证据；
- README 中英文、MCP 完整说明资源、第三方完整测试提示词和 P03 定向测试提示词。

直接依赖范围：P02 `EditTransactionCoordinator`、`EditWorkspace`、`EditOperationRegistry`、`EditFingerprint`、结构/roundtrip 验证、`StaticWriteGate`；P01 `McpCallContext`、会话生命周期、`SettingsRootLease` 和调试空闲事实；现有 `ArtifactStoreLedger` 的 512 MiB 单文件上限及 Windows 非重解析路径实现模式；dnlib 4.5.0、WPF Dispatcher、Python client 和现有静态/debug/edit 回归。

明确排除：P04 高级元数据、P05/P06 C# 编译与导入、P07 身份/入口点、P08 资源/强名称、P09 UI 实现；dnSpy 原生 Undo/AsmEditor、原始编辑、数据库、持久任务状态机、分布式事务、HMAC、哈希链、DPAPI、进程崩溃后的未持久化恢复、自动删除未知磁盘对象，以及任何第二套实时写入或历史状态。

## 3. 模块和唯一事实来源

### 3.1 深 Module 与 seam

新增一个内部 `EditHistoryModule`，其 Interface 只暴露协调器所需的“解析当前谱系、准备提交、完成/恢复提交、读取历史、规划导航、准备导出、接纳新基线”行为；包格式、路径、哈希、ZIP 校验、分支选择、重放分类、容量和原子切换全部留在 Implementation 内。删除该 Module 会把同一复杂度重新散落到提交、Undo、Redo、恢复、导出和旧工具 6 个调用点，因此该 Interface 具有足够 Depth、Leverage 和 Locality。

磁盘故障是唯一需要替换的内部 seam：`IEditCheckpointStore` 仅提供受租约目录下的枚举、精确读取、创建同目录临时文件、flush/读回、原子创建或替换、观察身份和删除本次拥有临时文件。生产 `WindowsEditCheckpointStore` 使用非重解析 Windows 路径/句柄；测试 `InMemoryEditCheckpointStore` 提供确定性阶段故障。两个真实 Adapter 证明此 seam 必要。不得为时钟、哈希、ZIP、仓库查询或旧工具另造只有一个 Adapter 的浅 seam。

`EditTransactionCoordinator` 仍是全进程可变状态唯一权威；`EditHistoryModule` 不持有第二个事务状态。`StaticToolProvider` 在已有 `McpCallContext` seam 上把 6 个旧写调用交给 `LegacyEditAdapter`；`McpTools` 保留旧 schema 和纯参数解析/投影，不再执行实时写入或保存。

## 4. 公开 MCP Interface

### 4.1 公共信封、状态与身份

所有编辑结果继续使用 `schema_version=dnspy.edit.v1`、对象型 `structuredContent`、`ok/state/result|error/warnings/untrusted_sample_data`。P03 扩展状态枚举为：

`idle | editing | reviewed | applying | committing | committed_without_checkpoint | live_state_unknown`

成功提交、Undo、Redo、恢复、接纳和导出完成后协调器回到 `idle`；有效检查点是 `result.history` 事实，不是长期占用的 top-level busy 状态。`committed_without_checkpoint` 是可显式恢复的进程级阻断状态；`live_state_unknown` 只允许产品查询 `edit_status/edit_history`，`edit_rollback` 与其他全部产品 mutation/export 均返回 `EDIT_LIVE_STATE_UNKNOWN` 且状态不变，恢复建议固定为重启 dnSpy，不新增远程 live 修复入口。`committing` 通常是调用内瞬态；唯一允许跨调用保留的情形是 live 已确认恢复到 pre-fingerprint、但本请求 temp 删除失败的 `aborted_temp_cleanup`，此时不声称 live 未知或已提交，且只允许 `edit_status/edit_history/edit_recover(action=cleanup_temp)`。

服务端生成的身份格式固定为 128 位随机小写十六进制：`lineage-[0-9a-f]{32}`、`checkpoint-[0-9a-f]{32}`、`recovery-[0-9a-f]{32}`、`replay-[0-9a-f]{32}`。调用者可以引用已返回身份，但不能指定新对象身份。所有变更调用要求已初始化 SSE/Streamable HTTP 会话和 `request_id`；owner 只来自 `McpCallContext`。历史读取可由任意已初始化会话执行；plain HTTP 只得到不含路径/恢复细节的全局 busy/state 摘要。

| `edit_export` | `request_id, lineage_id, checkpoint_id` | `output_path` | `checkpoint, output{path,length,sha256,file_id}, replay` | 只导出可 exact 重放的有效点；省略路径使用唯一默认输出；显式路径仍限 ArtifactRoot。 |
| `edit_recover` | `request_id, recovery_id, action` | 无 | `resolved, action, checkpoint|restored_fingerprint|removed_temp, history` | `action=retry_checkpoint|undo_live|cleanup_temp`；前两者只处理 checkpoint-finalize partial，后者只处理 live 已回到 pre-state 的 aborted-temp cleanup；同 recovery ID 的已解决重试返回原终态。 |
| `edit_accept_live` | `request_id, assembly_name, source_family_id, superseded_lineage_id, expected_live_fingerprint, acknowledge_new_baseline` | `module_mvid` | `source_identity, lineage, root_checkpoint, superseded_lineage_id` | 仅在无事务/无部分提交时接纳调用内重新验证的 UI 偏离，原子创建新谱系根；不伪造语义操作。 |

`page_size` 默认 10、最大 100，cursor 继续使用现有不透明 base64 位置编码；结果排序固定为 lineage/checkpoint 创建序号升序，不能用文件系统枚举顺序。`edit_history` 返回的字符串和包内内容均标记为不可信样本数据。

### 4.3 既有 5 个编辑工具扩展

- `edit_begin` 追加可选 `source_family_id`。创建私有副本后按 §8.3 解析源对应活动谱系：无历史时记录待创建新谱系；head 在当前工具链为 exact 且其 replay image/semantic fingerprint 均等于 live 时绑定 `base_lineage_id/base_checkpoint_id`；存在活动谱系但不等时返回 `EDIT_LINEAGE_DIVERGED`，无事务和磁盘副作用，并要求 `edit_accept_live`。多候选时调用者必须用 history 返回的 family ID 消歧，不能用路径或 assembly name 猜测。
- `edit_status` 对 owner 继续返回 P02 事务详情，并对已初始化会话增加 `history` 和 `recovery`。无事务但有有效 head 时 `busy=false,state=idle`；部分提交时 `busy=true,state=committed_without_checkpoint`，返回 recovery ID、提交前后指纹、待完成 checkpoint、临时包身份和允许动作。非 owner 不泄露活动事务细节。
- `edit_apply/edit_review/edit_rollback` 在普通事务态保持 P02 输入、已验收字段及语义；rollback 不改变持久 head。安全纠正例外是 `live_state_unknown`：P03 明确废止 P02 对产品 `edit_rollback` 的放行，三者都返回 `EDIT_LIVE_STATE_UNKNOWN` 且不得释放 unknown、改变 live/head/package/residual 或恢复可编辑状态；`DNMCP_TEST` emergency cleanup 仍只供完成阻断断言后的 fixture 清场。

### 4.4 稳定错误和幂等

P02 错误保持不变；P03 新增：

| 错误码 | 触发 | 恢复建议 |
|---|---|---|
| `EDIT_CHECKPOINT_INVALID` | 包结构、哈希、身份、父链、容量或 ZIP 条目非法 | 不写 live/输出；检查或隔离该包 |
| `EDIT_CHECKPOINT_COMMIT_FAILED` | live 已成功但临时包无法原子切换 | 查询 status，调用 `edit_recover` |
| `EDIT_CHECKPOINT_CLEANUP_FAILED` | live 未成功或已回滚，但请求拥有的 temp 无法删除 | 查询 status，以同 recovery ID 调用 `edit_recover(action=cleanup_temp)` |
| `EDIT_EXPORT_BLOCKED` | 无有效点、部分/未知状态、结构错误或非 exact | 先恢复有效 exact 点 |
| `EDIT_REPLAY_CONFIRMATION_REQUIRED` | validated_drift apply 未绑定 replay/确认，或 Undo/Redo 的目标不是 exact 而是 validated_drift | 用 assess 返回的 replay ID 执行显式 confirmed restore；不得由自动导航代为确认 |
| `EDIT_REPLAY_UNVERIFIED` | unverified_drift | 仅诊断；不得 apply/checkpoint/export |
| `EDIT_OPERATION_VERSION_UNSUPPORTED` | 未知包、信封版本或操作 kind/version | 使用支持该版本的工具，不猜测 |
| `EDIT_HISTORY_CONFLICT` | expected head/live/replay 失效或 lineage/checkpoint 不匹配 | 重新读 history/status/assess |
| `EDIT_BRANCH_SELECTION_REQUIRED` | Redo 存在多个子分支且未选定 | 从响应候选中指定 child |
| `EDIT_LINEAGE_DIVERGED` | live 与当前活动 lineage head 不同 | 显式 `edit_accept_live` 或恢复 live |
| `EDIT_SOURCE_IDENTITY_CONFLICT` | source family 候选为零但路径别名冲突，或候选不唯一/显式 family 不匹配 | 读取 history 的候选摘要并明确选择或作为新源重新加载 |
| `EDIT_RECOVERY_NOT_FOUND` | recovery ID 不存在且无幂等终态 | 重新查询 status |

相同权威会话、工具和 `request_id` 且规范化 payload 相同返回原结果；不同 payload 返回 `REQUEST_ID_REUSE`。commit 成功或失败终态、历史动作、导出和接纳在所属会话存活期间保留有界 terminal 记录；会话关闭后不新增跨会话 terminal 索引或查询接口。部分提交的 `recovery_id` 跨传输重连有效；恢复成功后同 recovery ID/动作重试返回已解决结果，不重复 live 操作或包切换。监听器重启只销毁传输 session 和未提交事务，不销毁已提交 package 或进程内 partial/cleanup/unknown 阻断事实。

## 5. 检查点包与容量

### 5.1 路径和 ZIP 条目

- 最终包：`<ArtifactRoot>\edit-checkpoints\<lineage-id>.dnspy-mcp-checkpoints`
- 临时包：同目录同文件名追加 `.tmp-<temp-id>`；`temp-id` 由服务端独立生成 128 位随机小写十六进制 `tmp-[0-9a-f]{32}`，调用者的 `request_id` 原文、清洗值或截断值永不进入路径。相同幂等请求从请求终态取回原 temp ID，不重新生成；跨 session recovery 从 PartialCommit 取回。只由持有其创建句柄并核对 file ID 的请求完成或删除。
- 默认输出：`<ArtifactRoot>\edit-output\<lineage-id>\<sanitized-original-file-name>`；文件名仅取 `Path.GetFileName` 后移除 Windows 非法字符，空值退化为 `module.bin`。
- 包格式：ZIP，固定 `manifest.json`、`baseline/module.bin`、`operations/<checkpoint-id>.json` 和可选 `payloads/<sha256>.bin`。禁止绝对名、`..`、反斜线别名、大小写重复、重复条目、未知顶层目录和任意解压。

`manifest.json` 的 `format` 是版本化契约：历史包 `dnspy.edit.checkpoints.v1` 的既有 manifest 结构与值永不变更，新谱系（含显式 `edit_accept_live` 新谱系）写 `dnspy.edit.checkpoints.v2` 并把 result semantic fingerprint 升级为方法/类型归属绑定的强投影（`source_identity.v1` 基线语义仍用历史算法）；未知 format 硬拒绝、不得猜测或静默升级；v2 强投影对重复 type/method owner 必须能力失败，对签名/scope/声明链的环与超界（>2048 层）也必须能力失败，不得静默合并、截断或消歧。两版 manifest 至少包含：lineage/family/source 身份、源路径/SHA/MVID、baseline entry/hash、head、可选 superseded lineage、按创建序号排列的 checkpoint 节点、payload 索引和默认输出身份。checkpoint 节点至少包含 ID/parent/kind、operation entry/hash、producer MCP/dnSpy/dnlib/compiler 版本、review/validation 摘要、风险/确认、result image SHA、result semantic fingerprint 和创建序号。baseline 只出现一次；每个 checkpoint 只记录从 parent 到自身的 forward/inverse `dnspy.edit.op.v1` 信封，不嵌入完整程序集。

operation entry 中每个信封包含 `format=dnspy.edit.op.v1`、服务端 operation ID、kind/kind_version、规范化 forward、可执行 inverse、payload SHA 引用及其精确顺序。P03 将 P02 的内存 `Action` 反向动作深化为可序列化、可重放的结构化 inverse；删除对象必须记录恢复所需的完整语义和 token/attachment 位置，但不能接受任意 raw metadata/PE/heap/RVA 补丁。后序 Pxx 通过同一 registry 注册新 kind，未知项硬停止。

P03 额外冻结一个只由 `LegacyEditAdapter` 服务端 lowering 生成、不能由公开 `edit_apply` 输入的内部 kind：`kind=legacy_symbol_rename, kind_version=1`。其 forward/inverse 都包含 `target_kind=type|method|field`、definition 的精确 metadata token、old/new name，以及当前 same-module 需同步的 TypeRef/MemberRef 行清单；每行记录 table/token、old/new name，按 raw token 升序且不得重复。应用前必须解析并逐项核对 definition 与所有引用仍为 expected old 值，随后在同一协调器 live plan 内按 definition→引用 token 升序改变；inverse 以严格逆序核对/恢复。任一缺失、歧义、重复、值漂移或中途失败使整组按预生成 inverse 回到原双指纹，不产生 checkpoint。这样保留当前 closed-generic type/method/field rename 的引用修复和既有 counters，又不把任意引用行编辑或 raw metadata 暴露为新产品能力。

### 5.2 原子写和结构验证

P03 不假定 debug 功能已启用：`EditHistoryModule` 必须独立取得当前 `ArtifactRoot` 及其 `edit-checkpoints/edit-output` 子目录的 NTFS、非重解析、最终路径和文件身份租约，复用 `SettingsRootLease`/`FileIdentityModel` 的已验证规则；不满足时在任何 live/最终文件变化前返回能力错误。

更新包时从旧有效包流式复制 baseline、既有 operation entries 和唯一 payload 到新临时 ZIP，加入本次节点后 flush，关闭并从磁盘重新打开；只有 schema、条目集合、长度、SHA、父链、head、重放和容量全部通过才执行同目录原子切换。新包用无覆盖原子 rename；已有包用 Windows 原子 replace。没有 copy-over、先删旧文件或自动改名 fallback。切换失败保留旧包不变并进入 §7 部分提交。

包读取只按 manifest 声明的精确条目读取到有界缓冲区，不把 entry 路径写到磁盘，不实例化程序集内对象，不执行目标代码。内容 SHA 只能发现损坏/非一致修改，不声称防恶意篡改认证。

### 5.3 固定容量

容量复用既有、已验证常量，不另造全局传输上限：

- 单 final/temp package 压缩长度最多 `ArtifactStoreLedger.MaxFileBytes=536870912`；同一 lineage 的旧 final 加当前 temp 最多 `ArtifactStoreLedger.MaxSessionBytes=1073741824`。
- `edit-checkpoints` 仓库所有 final、当前 temp、孤立/清理残留和未知直接子对象合计最多 `ArtifactStoreLedger.MaxStoreBytes=8589934592`、对象总数最多 `ArtifactStoreLedger.MaxStoreChildren=4096`；最多 128 个有效 lineage final package。不能测得长度/身份的重解析或非法对象允许只读报告，但使后续写入 fail-closed。
- 单 package 的 ZIP 物理条目总数（含 manifest/baseline/operation/payload）最多 4096；checkpoint 与 payload 分别不得超过该总数，二者加固定条目必须仍小于等于 4096。
- 单 package 所有 entry 的声明解压长度 checked-add 不超过 `MaxSessionBytes=1073741824`；单次 package 校验/重放最多读取同一上限，且同一物理 entry 每次调用最多读取一次。manifest/单 operation entry 最多 P02 `MaxNormalizedOperationBytes=8388608`，baseline 最多 `MaxModuleBytes=16777216`，单 payload 最多 `MaxResourceBytes=8388608`。CRC、实际长度或 SHA 不符立即停止。
- replay 的规范化 operation 数由 `checkpoint_count * P02 MaxOperations` checked-add 计算，最大不超过 `4094 * 256=1048064`；达到上限前可完整重放任意已接纳 checkpoint，超过即 package invalid。运行时不得用 ZIP 压缩比绕过上述解压/读取/operation 计量。

所有限额、当前 final/temp/residual/unknown 对象数和压缩/声明展开字节随 `edit_status`/history capacity 投影可见。先枚举、核对身份并做 checked-add，再创建临时文件、分配或读取；达到上限返回 `EDIT_CAPACITY_EXCEEDED` 且旧包、live 和输出零变化。

多个小 checkpoint 的正常稳定磁盘态只有一个 lineage 包和一次 baseline；更新瞬态最多旧包加一个由当前请求拥有的新临时包。checkpoint-finalize partial 的 `undo_live` 已验证恢复 pre-live、但临时文件删除失败时不得回到 idle，也不得保留 `committed_without_checkpoint` 或再次接受 `undo_live`：同一 recovery ID 原子转为唯一的 `state=committing, recovery_kind=aborted_temp_cleanup`，只允许 `edit_status/edit_history/cleanup_temp`；重复 `cleanup_temp` 只重试 file-ID/length/SHA 绑定的删除，绝不重复 inverse。进程崩溃留下的 `.tmp-*` 不自动提升、删除或当作有效历史；下次浏览报告为计入仓库容量的未受信任残留，不阻断只读有效包，但非法/不可计量对象使新写入 fail-closed。该代价来自 `NON-010`。因此 ACC-029 的“稳定态无 temp”适用于无进程崩溃且恢复已报告成功的正常完成路径，不与已报告残留冲突。

## 6. 提交协议

`edit_commit` 在协调器现有单一串行门内按以下不可交换顺序执行：

1. 核对权威 owner、transaction/revision/review、全部风险确认、debug idle、实时 baseline 指纹和 lineage head；任何失败均不触碰 live/package。
2. 从已审查 private workspace 生成 forward/inverse operation 信封、目标 result image/hash/fingerprint 和新 checkpoint；新源同时生成 baseline root checkpoint。构建并读回验证临时包，但不切换最终包。
3. 在进入 WPF Dispatcher 前完成全部 forward/inverse 计划；Dispatcher 内再次核对 debug/live/head 后执行 P02 实时短应用并验证目标指纹。forward 失败用 inverse 逆序恢复。inverse 成功后事务结束、旧 package/head 保持、请求 terminal 在会话仍存活时保存原 forward 失败；随后删除本请求 temp，成功才回 `idle`。若删除失败则保留一个 `recovery_kind=aborted_temp_cleanup` 的进程级恢复记录并保持 `committing`；它绑定 pre-live/head、temp path/file ID/length/SHA、原失败和请求终态，只允许 `cleanup_temp`，不得 retry/finalize/再次 forward/inverse。inverse 失败进入既有 `live_state_unknown`，旧 package/head 保持；本请求 temp 立即降级为不可信、计入仓库容量的 residual，不再属于可恢复请求，不允许远程删除、finalize 或采信。产品只允许 `edit_status/edit_history`，其他产品调用均返回 `EDIT_LIVE_STATE_UNKNOWN` 且状态不变，并要求重启 dnSpy；测试模式可在完成 unknown 阻断断言后使用 P02 既有 emergency seam 清理 fixture，但该动作不进入产品 schema、恢复结果或通过能力。
4. live 达到目标后原子切换包。成功后更新单一内存索引/head，释放事务并返回 `idle`、checkpoint、history、确认项和前后指纹。
5. 包切换失败时不谎报完整成功：释放传输事务所有权但保留最小 `PartialCommit`（recovery ID、`operation_kind=commit`、源/family/lineage、pre/post head、待完成 checkpoint、临时包 path+file ID+length+SHA、提交前后指纹、forward/inverse 计划、线性化阶段和请求终态），状态设为 `committed_without_checkpoint`。

步骤 2 失败无 live/package 最终副作用；步骤 3 forward 失败会终止事务：inverse 与 temp cleanup 均成功时回到 pre-live/head/package 并返回原失败，cleanup 失败进入 `committing`，inverse 失败进入 `live_state_unknown`；步骤 4 失败只允许 §7 checkpoint-finalize 恢复。成功提交后重试不能产生第二 checkpoint。

会话关闭与提交的线性化点是 Dispatcher 内第一项 live 变更：在该点之前收到关闭事实时取消提交、删除本请求临时包并按未提交事务回滚；到达或越过该点后不能再通过会话关闭处理器直接丢弃状态、处置 temp 或重放请求，而必须由已取得协调器串行权的提交操作自身走到下表唯一终态。新会话只通过 status/history/recover 观察结果。

| close 与 live 结果 | temp cleanup/finalize | 唯一终态 |
|---|---|---|
| 线性化前 close | 删除成功 | 事务关闭；pre-live/head/package；无 temp/checkpoint；idle；terminal=canceled |
| 线性化前 close | 删除失败 | pre-live/head/package；`committing + aborted_temp_cleanup`；terminal=cleanup failed；只允许 query/cleanup |
| 线性化后，forward 与目标指纹验证成功 | package switch 成功 | 唯一有效 checkpoint/post-head；无 temp；idle；terminal=success |
| 线性化后，forward 与目标指纹验证成功 | package switch 失败 | post-live、pre-head/旧 package、原 temp；`committed_without_checkpoint`；terminal=checkpoint failed；只允许 query/retry_checkpoint/undo_live |
| 线性化后，forward 失败且 inverse 成功 | temp 删除成功 | pre-live/head/package；无 temp/checkpoint；事务关闭；idle；terminal=原 forward failure/rolled_back；不得 retry forward |
| 线性化后，forward 失败且 inverse 成功 | temp 删除失败 | pre-live/head/package；原 temp；`committing + aborted_temp_cleanup`；terminal=cleanup failed（details 保留原 forward failure）；只允许 query/cleanup_temp |
| 线性化后，forward 失败且 inverse 失败 | temp 降级为 residual | 旧 head/package；`live_state_unknown`；不建立 recovery；会话存活时 terminal=live unknown；只允许 `edit_status/edit_history`，包括 `edit_rollback` 在内的产品 mutation/export 全部拒绝且状态不变，产品恢复建议=restart dnSpy；测试 seam 仅供断言后清理 |

测试屏障固定为 `commit_after_guard_before_temp`、`commit_after_temp_validate`、`commit_dispatcher_queued`、`commit_after_live_first_mutation`、`commit_after_live_complete`、`commit_after_package_switch_before_response`。前三个关闭时按表中线性化前两行判定；后三个在 live 成功时按 checkpoint/finalize 两行判定。另在 `commit_after_live_first_mutation` 后注入后续 forward 失败，并分别覆盖 inverse 成功/失败与 cleanup 成功/失败，不能用“越过线性化点”掩盖 live 应用失败。

## 7. 部分提交和会话重连

checkpoint-finalize `PartialCommit` 是进程级唯一记录，不属于已关闭传输会话；它统一覆盖 `operation_kind=commit|undo|redo|restore|migration` 并投影为 `committed_without_checkpoint`。同一协调器还允许至多一个互斥的 `aborted_temp_cleanup` recovery，投影为 `committing`，仅表示已知 pre-live/head/package 下仍需删除本请求 temp；两类 recovery 不能同时存在，也不是第二事务状态。partial `undo_live` 完成 inverse 后若 cleanup 失败，原 recovery ID 从 checkpoint-finalize 原子转为这一 cleanup kind，旧 kind/allowed-actions 同时失效，不能出现两个 recovery。`live_state_unknown` 不建立 recovery ID，status 只返回未知状态、旧 head/package、计量 residual 摘要和 restart 指引。`edit_status/edit_history` 从任意新初始化会话可查询当前事实；仅在 partial/cleanup 时返回 recovery kind、允许动作和完整绑定身份。旧 session 仍按 P01 失效并释放 16 会话名额，新 session 不能续用旧未提交 transaction，但可引用当前公开 recovery ID。

- `retry_checkpoint`：重新验证当前 live 仍等于 post-action fingerprint、旧 package/pre-head 未变化且临时包仍精确匹配，随后只重试原子切换；不得再次应用 forward。成功采用 post-head/post-checkpoint 并回到 idle。
- `undo_live`：核对当前 live 仍等于 post-action fingerprint，在 Dispatcher 内应用预存 inverse 并验证 pre-action fingerprint；成功后旧 package/pre-head 仍为原值，再删除 file-ID/length/SHA 绑定 temp。只有 live 与清理都成功才回到 idle；清理失败时同 recovery ID 转为 `committing + aborted_temp_cleanup`，allowed action 从 `undo_live` 变为 `cleanup_temp`，以后任何重复 `undo_live` 都稳定拒绝且不重复 inverse。inverse 失败进入 `live_state_unknown`，temp 降级为 residual，partial/recovery ID 终止且不得再次调用恢复动作。
- `cleanup_temp`：只接受 `aborted_temp_cleanup`；先证明 live/pre-head/旧 package 仍匹配并以 path+file ID+length+SHA 证明 temp 仍是原对象，然后仅重试删除。成功回 idle；删除失败保持同 recovery；任一身份冲突 fail-closed 且不删其他对象。它永不应用 forward/inverse、切换 package 或创建 checkpoint。
- 任一恢复动作的 live/head/temp 身份冲突返回 `EDIT_HISTORY_CONFLICT` 且保持当前 recovery；inverse 失败进入无 recovery 的 `live_state_unknown`。partial/cleanup 阻断期间只允许 `edit_status/edit_history` 和当前 recovery 明列的单一动作；unknown 只允许 `edit_status/edit_history`，包括旧/新 rollback、begin、apply、review、commit、Undo/Redo/restore/accept/recover 和全部新旧导出在内的其他产品调用均以 `EDIT_LIVE_STATE_UNKNOWN` 拒绝且零状态变化。

进程崩溃或 dnSpy 重启会丢失内存 PartialCommit、cleanup recovery、unknown 和 live 修改；重启从未覆盖的源文件重新加载，磁盘 temp/residual 继续只读报告并计量，永不自动提升或删除。P03 不引入持久任务状态机恢复该窗口；这是 `NON-010` 已接受的代价。

## 8. 历史、三态重放和谱系偏离

### 8.1 分支导航

每个 lineage 有一个可变 head 指针，checkpoint 父链接不可变。Undo 的候选是 parent；Redo 只沿指定 child；restore 可选任意节点。任何自动导航先在当前工具链下完整评估候选 target，只有 `exact` 才能进入写路径；`validated_drift` 返回 `EDIT_REPLAY_CONFIRMATION_REQUIRED` 并要求显式 assess+confirmed restore，`unverified_drift` 或未知格式/种类/版本硬拒绝，全部拒绝均保持 live/head/package/output 不变。分类按 lineage 的 format 选择对应算法并禁止跨版本混比：v1 只有 image 与记录一致才 exact，image 不同一律 `unverified_drift`（即使历史语义相等）且不提供 migration；v2 在强语义相等且结构/往返验证通过时才可 `validated_drift`，经显式确认建立 migration child。导航计划本身绑定已验证 lineage format：计划构建与应用的 before/after 门用该版本 `SemanticDigest`（v1 历史、v2 强），未知 format 在任何内部入口（包括计划与摘要分派）硬拒绝；v2 初态 weak hash 相同但方法归属不同时，计划在应用第一个操作前拒绝且不改变 live/package/store。成功导航后的 head 在当前工具链下必须为 exact，live image/semantic fingerprint 必须同时等于该 target 的当前 replay 结果。Undo 后的新 commit 以当前 exact 历史 head 为 parent，旧 child 保留，从而自然形成分支。导航写包前先规划 current→最低共同祖先的 inverse 序列和祖先→target 的 forward 序列，并先构建/读回含 post-head 的 temp package；随后按提交同等 debug/live/反向恢复门禁改变 live，最后原子切换 package。

Undo、Redo、exact restore 和会改变 live 的 validated migration 共用 §6 的线性化点、复合失败优先级与 §7 recovery：prewrite/readback 失败时 live/head/final package 不变，temp 删除成功才回 idle，删除失败进入 `aborted_temp_cleanup`；live forward 失败且 inverse 成功时仍为 pre-head并按 temp cleanup 结果 idle 或 cleanup recovery，inverse 失败则进入无产品恢复的 `live_state_unknown` 且 temp 降级为 residual；只有 live 成功而 package finalize 失败时才以对应 `operation_kind` 进入 checkpoint-finalize partial，`retry_checkpoint` 只采用 post-head package，`undo_live` 只恢复 pre-action live/head。session close 只改变 owner/session 可见性，不覆盖当前操作根据 live/inverse/cleanup/finalize 得出的唯一终态。`edit_accept_live` 不得吞并、接纳或重新分类这些内部失败。

dnSpy Ctrl+Z/Ctrl+Y 不注册进 MCP 历史、不调用 AsmEditor，也不改变 package head。若它实际改变 live，下一次 MCP 导航/begin 由完整指纹检测为冲突/偏离。

### 8.2 三态和 replay ID

`edit_restore(action=assess)` 对目标从唯一 baseline 按父链逐 checkpoint 重放；每个 checkpoint 内重置事务局部 object-ID map，既有对象用重放时确定的 token/稳定身份，事务内新对象用该 checkpoint 信封命名空间。先校验 package/operation/payload，再用当前 P02/P04-P08 registry、当前编译器及依赖重放和结构/roundtrip 验证：

- `exact`：生成 image SHA 和 semantic fingerprint 都等于记录值；可以绑定 replay ID 执行导航/恢复或导出。
- `validated_drift`：image SHA 不同，但结构/roundtrip 通过且 semantic fingerprint 等于记录值；只返回诊断。明确 `confirm_validated_drift=true` 且 replay ID、live/head/工具身份仍一致时才可应用，并以目标 checkpoint 为 parent 建立零语义操作的 `migration` 子 checkpoint，记录当前工具链 image SHA，原点保留。
- `unverified_drift`：semantic fingerprint 不同或验证不能证明等价；只返回诊断，禁止 live、checkpoint、head、输出变化。

未知 package/operation format、kind 或 kind_version 不是 drift，直接返回 `EDIT_OPERATION_VERSION_UNSUPPORTED` 并停止。replay ID 绑定 lineage/checkpoint、package identity、工具链身份、分类、当前 live/head 和评估摘要；任一变化使它失效，必须重新 assess。

上述分类同样是 Undo/Redo 的前置，而不是 restore 独有逻辑。exact target 可自动导航；validated target 不能由没有 replay/确认字段的 Undo/Redo 隐式确认，必须改走 `edit_restore(action=assess)`，再以同一有效 replay ID 和 `confirm_validated_drift=true` 执行 apply。该 apply 不把 head 留在历史 validated 节点，而在它下面建立新的 exact migration child 并把 live/head 同时推进到该 child。由 migration child Undo 到仍为 validated 的 parent 因此零副作用拒绝；显式恢复会在 parent 下建立另一 migration child并保留旧分支。unverified 或未知版本永远没有替代写路径。

`edit_begin` 和 `edit_commit` 只接受当前 head 在当前工具链为 exact，且 live 的 image SHA 与 semantic fingerprint 分别等于该 exact replay 结果；仅 semantic 相同不足以开始或提交。这个不变量防止把 head 临时移到 validated 节点后绕过确认。工具链变化使当前 head 不再 exact 时，调用者必须先按本节完成 assess/confirmed migration，不能由 begin、普通 commit 或旧兼容入口自动迁移。

双工具版本 fixture 必须用真实不同 image、相同语义和不同语义三个固定程序集/包构造 exact、validated、unverified，不能仅伪造分类字段或把异常等同 drift。

### 8.3 UI 偏离和新谱系

仓库按源 family 身份和 `superseded_lineage_id` 解析唯一未被取代的 lineage leaf；多个无法唯一解释的 leaf 返回 history conflict。无历史的首次 transaction 可正常提交并创建 lineage；有历史时 begin 必须比较当前 live 与 active head。

`source_family_id` 是服务端随机 `family-[0-9a-f]{32}`，不是路径、assembly name、MVID 或其单值哈希。每个 package 保存 versioned `source_identity.v1`：family ID、origin MVID、baseline image/semantic SHA、可选 origin 文件的 handle-derived volume serial/file ID/final path hash/on-disk SHA，以及成功默认输出的 path hash/image SHA 别名；响应向已初始化会话返回这些摘要和 `match_basis`，plain HTTP 不返回路径或身份详情。所有 image/on-disk/semantic hash 继续使用 P02 的 SHA-256 小写十六进制；path hash 固定为 `SHA-256(UTF-8(FileIdentityModel 已规范化的 handle-derived final path))`，不再二次大小写折叠或字符串路径规范化。身份格式版本变化必须新增版本并由未知版本硬停止，不能静默改写 `source_identity.v1` 含义。

resolver 顺序固定：先使用当前进程中 `ModuleDef` 引用到 family 的绑定；否则在有效 package 中要求 MVID 一致，并以“live image SHA 与 semantic fingerprint 同时精确匹配某个在当前工具链为 exact 的 active leaf head”或“当前文件 volume/file ID、final path hash 和 on-disk SHA 全部匹配 origin/default-output 别名”形成原始候选。后一路径身份候选仍必须在 begin 前完成 replay 分类；不是 exact 或 live 双指纹不匹配时只能报告 conflict/迁移指引，不能开始事务。若请求显式提供 `source_family_id`，只保留该 family 的候选：恰好一个且只有一个 active leaf 时选择，零个或多个时 conflict；若未提供，原始候选恰好一个且只有一个 active leaf 时选择，超过一个时 conflict。Save As 只有在唯一匹配 exact head 内容时才归入原 family；同路径别名存在但 file identity 或 SHA 已替换时，即使原始候选为零也返回 `EDIT_SOURCE_IDENTITY_CONFLICT`，不静默新建；所有 conflict 都只列 family/lineage/MVID/image/semantic/path-hash 匹配摘要，不泄露原始路径。两个同 assembly/MVID 的 loaded module 仍由 P02 target resolver 在 history 前以 `target_ambiguous_or_not_found` 拒绝。无 `Location` 的模块仅可用进程绑定或唯一 exact head 双指纹匹配；跨进程无匹配时作为新 family，不假定旧路径。完全无候选且无冲突别名时首次 commit 才生成新 family。

`edit_accept_live` 在调用内重新解析 active lineage 并重新计算偏离，不依赖隐藏的“此前观察”票据；只有请求中的 family/被取代 lineage 与唯一候选精确相等、实际仍偏离、当前完整 live fingerprint 与 `expected_live_fingerprint` 一致、`acknowledge_new_baseline=true`、无活动事务/部分状态且 debug idle 才继续。它在同一 family 下把当前 live 完整模块像作为新 lineage 唯一 baseline/root，manifest 指向被取代 lineage；旧包不修改且继续可浏览。root operation entry 为空，绝不把 UI 修改猜成操作。创建失败时旧谱系和 live 不变。

## 9. 原子导出

导出前必须：无活动事务、无部分/未知状态、debug idle；目标 checkpoint package 有效且在当前工具链下 `exact`。validated 必须先经 §8 形成 migration 点，unverified/未知版本不能导出。

仓库把目标重放为字节，在最终路径同目录创建请求拥有的临时文件，flush 后用 dnlib 重新加载、执行结构/roundtrip、semantic fingerprint、长度和 SHA 核对。全部通过后，新输出无覆盖原子 rename，既有输出原子 replace；失败删除本次临时文件并保留旧输出字节/身份。默认路径永不等于源样本；显式路径必须是 ArtifactRoot 内非重解析普通文件目标，不能指向源、checkpoint package 或其 temp。不得使用 delete-then-move/copy-over fallback。

checkpoint 在创建时记录由 lineage、sanitized source name、result length/SHA 推导的默认输出身份，因此导出无需再次修改 package；显式输出身份只在响应中返回。这样避免 package 与输出两个文件需要伪装成跨文件原子事务。

## 10. 旧 6 个写工具迁移

`StaticToolProvider` 已经接收权威 `McpCallContext`，P03 在这里拦截 `patch_method_il`、`force_return`、`nop_method`、`revert_method_il`、`rename_symbol_by_token`、`save_assembly`，交给 `LegacyEditAdapter`。其他 26 个静态工具仍走 `McpTools.ExecuteTool`。plain HTTP 旧写调用因不能拥有事务而返回 `EDIT_OWNER_REQUIRED`。

- patch/force/nop/rename：单次旧调用内部执行 begin→结构化 apply→review→commit，调用本身作为对其精确意图产生风险的兼容确认；响应必须显式列出 confirmed risks、lineage/checkpoint 和兼容警告。rename lowering 必须生成 §5.1 的内部 `legacy_symbol_rename` v1 复合 operation，将 definition 与全部当前 same-module TypeRef/MemberRef 的 old/new 值、token、固定顺序和 inverse 一并进入 checkpoint；公开 edit_apply 不能提交该 kind。结构错误仍不可确认绕过。
- revert：只在当前 head 是同一方法的直接兼容 IL checkpoint 时映射为 MCP Undo；否则明确返回没有可安全撤销的兼容 patch，不跨越其他提交静默还原。
- save：映射到 `edit_export`。这是需求强制的有意兼容变化：省略 `output_path` 时不再 backup/覆盖源文件，而写入 ArtifactRoot 的唯一默认输出；显式路径也必须在 ArtifactRoot 内且不能是源文件、package 或 temp。无历史且 live 未修改时，可在同一安全仓库路径先建立仅含当前 baseline/root 的 lineage 再导出；有任何偏离、部分或未知状态时不能借此绕过门禁。旧响应固定投影 `saved_to=output.path`、`bytes_written=output.length`、`backup_path=null`，并追加 `source_preserved=true, sha256, file_id, lineage_id, checkpoint_id, warnings`；warning 明示默认行为已从覆盖源变为安全产物输出。
- `get_method_il.has_pending_patch` 从当前有效 head 的兼容元数据投影：当前 head 为该方法的兼容 IL commit 且 live 匹配时为 true，Undo、分支切换或后续提交后为 false。不存在内存 snapshot 字典。

删除 `McpTools.IL.cs` 的 `ilSnapshots`、`CilBodySnapshot`、`ilEditLock`、直接 live patch/revert/save 实现，以及 rename 的直接 live 写分派。可复用的 operand 解析、return sequence、symbol 解析和结果投影必须变为无副作用 lowering helper；所有 live 修改最终都由协调器同一提交/导航 Interface 完成。源码和注册路径机械扫描必须证明没有第二写状态。

过渡代价：旧调用耗时增加；其风险确认是一次调用绑定而非新接口的 review/commit 两步；`revert_method_il` 只安全撤销直接 head；`save_assembly` 无路径调用不再覆盖源文件或产生 backup，结果路径改为 ArtifactRoot。`tests/fixtures/run-tests.ps1` 中只定点更新这一旧保存断言为“源 SHA/file ID 不变、backup_path=null、默认产物位于 ArtifactRoot、旧字段和新 history/checkpoint 可见”；generic rename、执行、错误和其他静态断言必须原样继续通过，不能用整体放宽回归掩盖变化。README 和响应必须显式说明，P03 不延长到第二个过渡版本。

## 13. Fallback、风险和交接

允许 fallback 只有总纲已列项目：同地址重连/端口变化由用户更新、validated_drift 确认迁移、能力拒绝、查询和显式恢复、支持 resources 的验收宿主。P03 不新增数据库、后台修复、copy-over、自动选分支、自动接纳 UI 修改、自动提升孤立 temp 或自动重放修改请求。

现实风险及闭合方式：

- P02 反向动作目前是内存 `Action`，P03 必须在同一 operation registry 生成可序列化 inverse；每类 22-kind 至少一次 commit→Undo→Redo，删除/附件/token 类另有反例。
- package 与 live 不能成为真正跨文件系统/内存原子事务；§6 先完整预写、后 live、再单原子 replace，并以唯一 PartialCommit 暴露剩余窗口，不能隐藏。
- package 更新重写整个 ZIP，瞬态可接近两倍；这是已接受代价，ACC-029 测实际上界。
- 当前工具链变化可能让历史不 exact；三态和 migration 保留，不以“同版本应该相同”代替跨版本 fixture。
- 进程崩溃窗口不恢复；孤立 temp 永不自动采信，最后有效 package/source 安全。
- legacy 单调用兼容确认与安全 revert 范围缩窄必须写入文档和响应，不能伪装完全等价。

P03 完成后向 P04 交付：经审核的 `dnspy.edit.op.v1` 扩展注册点、可序列化 inverse 契约、唯一 package/history Module、完整 commit/navigation/export/recovery Interface、旧工具无旁路证明及 P03 双架构证据。P04 只增加高级元数据 operation kind，不重做本文机制。
