## 1. 目标、范围与边界

P02 建立全进程单活动编辑事务、服务端权威所有权、私有工作副本、常用结构化操作、统一审查、短临界区实时应用内核及失败反向恢复。产品接口只发布开始、查询、应用操作、审查和回滚；实时应用只能由 `DNMCP_TEST=1` 的不广告验收入口调用并在同一调用内恢复实时指纹。P03 建立检查点后才发布产品提交、导出、Undo/Redo，并迁移六个旧写工具。

核心维护范围：

- 新 `Editing/` 事务、工作副本、操作、审查、实时应用、错误/契约和工具提供器；
- `McpCallContext` 与 `McpTransportSessionLifecycle` 的 P02 消费，不改写 P01 权威来源；
- `McpToolRegistry` 注册结果、Python client 便利方法、`tests/edit/` P02 案例和自动 Win10VM 编排；
- README 中英文、MCP 编辑说明资源、完整测试提示词和 P02 定向提示词。

直接依赖：`IDocumentTreeView`、dnlib 公共 API、WPF Dispatcher、`StaticWriteGate`/调试空闲事实、P01 VM 执行许可、ArtifactRoot 路径策略、现有静态/调试/传输测试。

排除：检查点包、谱系、产品提交、导出、Undo/Redo、旧六写工具迁移（P03）；高级元数据（P04）；C# 编译/导入（P05/P06）；身份/入口点（P07）；资源/强名称（P08）；事务浏览 UI（P09）；`dnSpy.AsmEditor`、原始编辑、混合模式、NetModule、多文件程序集及并行事务。

## 4. 实施与数据流契约

1. `edit_begin` 在 WPF Dispatcher 内唯一定位 live ModuleDef，执行生成限额准入、确定性内存写出和 reload；成功后持有单一 private graph、baseline fingerprint、resolver/PDB 生命周期和事务 generation。
2. `edit_apply` 在 worker 解析并依据 generated operation row 构造 private action；在 private graph 原子应用、全结构验证、内存写出/reload 后才递增 revision、对象 ID 和 diff/risk。失败恢复 private fingerprint/revision/object map。
3. `edit_review` 固定 revision 和实时/private fingerprint，执行硬结构、完整 writer/reload、可选动态验证并产生当前唯一 full review slot；后续 apply 将其替换为 hash tombstone，旧 review 调用稳定返回 stale。
4. `edit_test_apply_and_restore` 由 generated lowering 编译 immutable plan；进入 Dispatcher 前预生成全部反向值。Dispatcher 内二次核对 review/debug/live fingerprint并按 generated primitive 顺序执行。actual trace 由 mutation adapter记录，测试 oracle独立读取 golden。
5. rollback/session close/timeout 使 generation cancelled；lease 结果不得在取消后发布。清理 private/validation graph、apply/review cache和 resolver；session tombstone/terminal slot按 generated transition释放。
6. 指纹输入为固定 writer 的完整 module image、嵌入 PDB image 和 identity projection；测试 external-mutation seam 只接受 generated case ID。五个 mutation case 分别通过 dnlib 公共 live graph 修改 `ModuleDef.Name`、`TypeDef.Name`、`MethodDef.Body`、`ModuleDef.Resources` 和 embedded-PDB document URL，独立读回必须变化、完整指纹必须变化且同一 live graph 最终恢复 baseline；另一个全局 channel-enumerator reorder case 必须令 raw-order digest 变化而 canonical fingerprint 不变。不得用独立字节缓冲区 XOR、伪造单例 table reorder 或替换 dnSpy live `ModuleDef` 充当证据。

## 5. 结构验证、动态验证和验收取证

- 硬验证覆盖 CFG/evaluation stack、opcode/operand、branch/EH、MaxStack、arg/local、signature/ParamDef/GenericParam、owner、semantics及全部入站/attachment；错误只能通过 generated error-details schema返回。
- 动态验证严格使用 generated 五态 oneOf；未创建 artifact 的状态只有生成 schema 指定的 null 表示。失败/阻断不生成 review，事件、cleanup和残留路径仍按 schema取证。
- fault runner 逐 operation 读取 operation-lowering 和 fault-golden，对 240 个 forward/reverse before/after fault 各建一个新事务。schema 强制 manifest 与 oracle 各为 240 个唯一行；actual trace 记录整次 forward→reverse 调用真实抵达的 before/after 有序前缀，上限由最长 6+6 primitives 机械推导为 24，注入时以 armed row 结尾；covered 为空或仅含本次 armed row。无服务器 suite 隐藏状态，runner 以唯一 suite ID 聚合 240 份互异 ArtifactRoot 证据，covered 的 fault_id 并集与 golden 恰好一次相等，并在每次调用前后 reset。
- 最大合法 review payload 上界为 2,191,378 bytes，小于 2,621,440-byte 内部 slot；含 65,536-byte 固定外层余量和 3 倍 payload 转义/重复因子的完整 JSON-RPC 保守上界为 6,639,670 bytes，小于 P01 固定 8,388,608 bytes。begin/apply schema payload 上界分别为 517,179/1,712,099 bytes，低于各自 1/2 MiB 逐响应缓存上限；64 entries/4 MiB 与 1024 entries/32 MiB 同时独立限流，先到者拒绝且零副作用。review 只保留一份 full slot 与最多 64 个 tombstone；每条 tombstone 固定两个 SHA-256、review ID 和 revision，独立上界 3,168 bytes，64 条总上界 202,752 bytes，小于 262,144-byte 槽；第 66 次连续新 review 返回 capacity error。rollback 完整响应上界 517,179 bytes，小于 1,048,576-byte terminal slot。apply/rollback/close/timeout 清零；九工具最大 wire 上界均写入 capacity golden，双架构 1000ms callback 门槛保持不变。
- 测试产物不得包含 Token；临时验证路径仅在 ArtifactRoot，正常结束必须 transaction idle、debug idle并清理临时文件。
