## 4. 活跃审计意见

### AUD-001：公开 schema 和 IL operand 契约仍不是唯一机械规范

- 首次提出轮次：第 1 轮；本轮结论：未闭合；严重度：高。
- 来源与证据：`REQ-002`、`CON-024`、`NON-001`；`OUT-002`；v2 §4.1 第 140-154 行、§4.3 第 166-193 行、`IMP-003/004`、`ACC-003`。
- 具体反例 1：§4.1 声称字段是封闭全集，但 success 仍只写 `capabilities/limits`、`capacity/risk 摘要`、“完整 diff”、`required confirmations`、“释放计数”等名称，没有展开每个嵌套字段的 properties/type/required/nullability/oneOf。§3.3 错误只冻结四字段，§4.4 又要求验证失败“附最多 64 条”四字段错误，却未冻结它们在 error 的字段名和 required 位置。实现 A 放 `error.details`，实现 B 放 `result.validation.errors`，都可声称遵循正文。
- 具体反例 2：方法体 operand 说“沿用现有标记语法”，但现有 README 语法的 `method:/field:/type:` 以 FullName 解析，而v2 §3.4 明确目标不得用名字猜测。§4.3 另写 `token:*`、`obj:*`，没有冻结具体 tag、token/object ID 嵌套格式、可用 opcode 或与旧 FullName tag 的关系。
- 影响：严格 MCP 宿主、Python client、22-kind golden、差异规范化及 P03 消费的操作事实没有唯一契约。影响 `RACC-003`、`ACC-003`、`IMP-003/004/005`。
- 最小闭合条件：在方案中给出五工具和 22 branch 的可展开完整 schema 或等价逐字段规范；冻结所有 result/error/details 结构；对 IL operand 使用受 opcode 约束的 discriminated union，引用类操作数只接受 token/object ID，明确旧 FullName tag 是拒绝还是只读转换。
- 闭合证据：从实际注册表取五工具 schema，严格验证 success、逐领域 error 和所有 22 branch；方法/字段/类型/MethodSpec/MemberRef 等 operand 用 token/object ID 往返且不按名称搜索。

### AUD-002：参数操作对 return ParamDef 和无 ParamDef 槽位仍无唯一语义

- 首次提出轮次：第 1 轮；本轮结论：未闭合；严重度：高。
- 来源与证据：`REQ-002/008`、`CON-017/020`；v2 §4.3 第 171-195 行、§4.4 第 199-210 行、`ACC-003`。
- 具体反例 1：`parameter_update` 的 target 只要是 ParamDef，未排除 `Sequence=0` 的 return ParamDef；其规则却无条件把类型同步到 `MethodSig.Params[Sequence-1]`。对 return ParamDef 将访问 `Params[-1]`，或者实现者必须自行决定改 RetType、拒绝或静默不改类型。
- 具体反例 2：CLI 方法签名槽位可没有 ParamDef row。对已有 `M(string)` 且第 0 槽无 ParamDef 的模块，`parameter_update/remove` 没有可寻址 target；`parameter_add` 又必须以当前参数数作 index 并追加新签名槽，不能用来为原槽位建 ParamDef。实现可拒绝、自动物化 ParamDef 或错误地新增第二个参数，ACC-003 的普通 fixture 仍可避开这个反例。
- 影响：常用参数编辑的字节语义和失败边界不稳定；结构验证可在运行时崩溃或将合法基线误拒。影响 `RACC-003`、`ACC-003`、`IMP-004/005/008`。
- 最小闭合条件：明确 `parameter_update` 只接受 `Sequence>=1` 的普通 ParamDef，return 类型只走 `method_update.return_type`；为无 ParamDef 槽位冻结 owner method+parameter index 寻址与 ParamDef 物化语义，或明确稳定能力拒绝。
- 闭合证据：return ParamDef update 负例；无 ParamDef、部分 ParamDef 和完整 ParamDef 三类既有方法的 update/remove/readback；失败时 revision/object map/private/live 指纹不变。

### AUD-004：异 ID 争抢、waiter 完成可见性和会话域幂等生命期仍未闭合

- 首次提出轮次：第 1 轮；本轮结论：部分闭合；严重度：高。
- 来源与证据：`REQ-001/017`、`CON-002/007/008`；v2 §3.1 第 78-86 行、§3.2 第 88-103 行、`IMP-001/007`、`ACC-001/002`。
- 具体反例 1：正文只冻结“任何时刻最多一个 lease”，未冻结不同 request ID 的 apply/review/rollback 同时到达时，后来者是等待、稳定失败还是 rollback 取消 in-flight。ACC-002 测了 close/timeout/Stop 对 in-flight，却不测 `apply vs rollback`或异 ID `apply vs review`。
- 具体反例 2：同 ID follower 已要求锁外 await，但 settle 顺序仍写“完成 waiter→清除事务”，未要求 `RunContinuationsAsynchronously` 或在释放 monitor 且清除事务后才完成 waiter。默认 `TaskCompletionSource.SetResult` 可内联 continuation，使其在事务未清除时反入 status/begin/Dispatcher。
- 具体反例 3：`request_id` 被声称作用域为整个权威会话，同 ID/同载荷必须返回首次完整响应；§3.3a 又规定事务结束后释放全部普通项。同一会话 rollback 后重放原 `edit_begin` ID，实现可再建事务，与会话域首次响应规则冲突。
- 影响：修订、缓存响应、rollback 可达性和客户端恢复策略可以分裂，并可再现 UI/worker 互锁或重复副作用。影响 `RACC-001/002`、`ACC-001/002`、`IMP-001/007`。
- 最小闭合条件：冻结异 ID 操作争抢的排队/失败/取消规则和码；锁内只固化终态、摘取 waiter 并清除事务，锁外异步完成 waiter；将 request ID 作用域收窄为明确事务 generation，或在会话生命期内保留可有界证明的幂等 tombstone。
- 闭合证据：异 ID `apply/review/rollback` 屏障矩阵；continuation 立即调用 status/begin/Dispatcher 的测试；同会话跨事务重放旧 begin/apply/rollback ID，证明无死锁、无 post-idle success 和无重复副作用。

### AUD-005：普通 cache 满载后的 review 可达性直接矛盾

- 首次提出轮次：第 1 轮；本轮结论：未闭合；严重度：高。
- 来源与证据：`CON-005`、`NON-018`；v2 §3.3a 第 105-114 行、§7 第 287 行、`ACC-009`。
- 具体反例：第 110 行规定普通缓存达到 1024 项或 32 MiB 后，新 `begin/apply/review` 必须返回 `EDIT_CAPACITY_EXCEEDED`；第 287 行又要求最大合法 256 操作事务在普通 cache“满载前后均可 review”。用唯一 request ID 的 review/revision-conflict 等响应填满普通缓存后，对一个新 review ID 同时有必须失败和必须成功两个互斥 oracle。rollback terminal slot 不能解决 review 通道。
- 影响：`ACC-009` 不可同时通过，最大合法事务不一定能进入审查，作者处理记录对 AUD-005 的闭合声明不成立。影响 `RACC-009`、`ACC-009`、`IMP-001/005/008`。
- 最小闭合条件：为最终 review 预留独立且有界的容量，或明确 review 的容量豁免；如不提供满载后审查，则删除该验收要求并冻结唯一恢复路径。1000 ms 定向验收另须固定计时器、预热/重复次数、原始每 callback 时长及任一超限即失败的判定法，避免单次幸运样本代替门槛。
- 闭合证据：精确填满项数与字节两条边界后，分别测试新 review、已缓存 review 重放、rollback、close 和 timeout；双架构最大准入 fixture 保存全部 callback 原始计时证据。

### AUD-006：动态五态和 primitive 独立 oracle 仍无完整可执行契约

- 首次提出轮次：第 1 轮；本轮结论：未闭合；严重度：高。
- 来源与证据：`RACC-003/009/010`、`CON-005/020/021/024`；v2 §3.1 第 86 行、§5 第 212-246 行、§7 第 270-297 行。
- 具体反例 1：第 220 行把动态结构冻结为含必有 `artifact:{path,sha256,created}`，只标出 `runtime_profile/failure/residual_path` 可 null；第 154 行又要求 SHA 为 64 位小写十六进制，路径只能在 ArtifactRoot。然而 `not_requested`、DLL/无入口的 `not_applicable`及 VM/debug 预检先拒绝的 `blocked` 都可以没有任何 artifact。省略 artifact、传 null、空字符串、零 SHA 或虚构计划路径均与部分规则冲突。
- 具体反例 2：规范 lowering 仍使用“每个标量字段”、“signature”、“每个 attachment/edge”等聚合词。例如 method/property/event add 没有冻结 name/attributes 是在 Dispatcher 外预构造并随 collection insert 一次可见，还是各自独立 live scalar mutation；两实现会产生不同的 before/after 集合，测试侧无法只由正文独立推导哪个是正确集合。
- 具体反例 3：验收依赖 `edit_test_fault`的故障 ID 选择、`edit_test_apply_and_restore` 的 `confirmed_risk_ids` 及证据输出，但§3.1 只列四个测试 seam 名称，没有其 input/output schema、异常注入生命期或清理后状态。实施和 runner 仍需要新增产品决策。
- 影响：严格动态失败证据可能无合法输出；遗漏的 live mutation 可能不进入 oracle；fault/coverage/trace 四集合可围绕同一未冻结实现自洽。影响 `RACC-009/010`、`ACC-009/010`、`IMP-003/005/006/008`。
- 最小闭合条件：对动态五态使用 `oneOf` 冻结 requested、artifact、cleanup、failure 的 required/nullability，明确“未创建产物”的唯一表示；将每个 kind 的实际 live primitive 逐字段/边展开并冻结预构造边界；给出四个测试 seam 的封闭 schema 和故障注入/清理状态机。
- 闭合证据：动态五态 golden 全部通过对应 output schema；每个 kind 的测试侧 oracle、实现 manifest、actual trace 和 covered 四集合对 before/after 完全相等；property/event/parameter/generic 多边变化可逐边注入。
