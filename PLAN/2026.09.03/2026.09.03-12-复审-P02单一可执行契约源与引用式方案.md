## 4. validator 独立性和失败能力

`validate_contract.py` 没有 Python import 生成器数据结构，并为工具名、operation、error、OperandType 和 mutation component 维护了固定期望集合；这一层结构独立性成立，也确实会对这些集合缺项、fault ID 重复或显式预算算术失败返回非零。

但是它先无条件执行 `contract_source.py` 覆盖生成物，再读取新生成结果，因此不能发现运行前生成物陈旧或被篡改；它也没有用生成 schema 验证 golden，没有从 schema 的字符串/数组上限推导最大序列化字节，没有验证 component-specific mutation 动作。原始运行已经给出有效反证：240 条不符合 primitive schema 的 fault row 与可超过 slot 两倍的合法 review 同时获得 655/655。

`requirements_fidelity` 也不是独立需求审计：代码只按 `errors` 是否为空硬编码 `6/6/0/0/0`，失败时硬编码 `6/4/0/1/1`，不读取需求、总纲、v4 或 RACC→IMP/ACC 证据。因此 validation report 的需求保真字段不能作为本轮门禁证据。

### 5.1 AUD-001 反例

v3 明确冻结了 TypeSig grammar、`modreq/modopt/fnptr/sentinel` 拒绝、各 attributes 已定义位掩码、add 默认值和 char 单 Unicode scalar。v4 删除这些正文后，源中 `TYPE_SIG` 仅为 1..4096 字符，attributes 仅为 `uint32`；`tagged_constant.char` 允许长度 1..2，因此 `"ab"` 通过 schema；`property_add.getter/setter` 允许显式 null，亦与 v3 的 add 禁止显式 null 不同。实现 A 接受任意 TypeSig/未知 flags，实施 B 按 v3 parser 拒绝，两者都能通过当前 schema 和 validator。单一文件已经建立，但没有成为完整唯一语义源，AUD-001 的原抽象根因仍在。

### 5.2 AUD-002 反例检查

专门复查 return ParamDef、无/部分/完整 ParamDef、materialized reverse 和 referenced delete。当前 source 的 `parameter_update.private` 含 `reject_return_param`、`materialize_private_paramdef_if_missing`，forward 首步为 `insert:paramdef_collection:if_missing`，reverse 末步为 `remove:paramdef_collection:if_materialized`；`parameter_remove` 对无 ParamDef 与签名尾槽也有对称步骤。七个 remove kind 均只有 hard-fail policy，不再同时把“仍被引用”写成可确认 risk。没有找到 09 所列两个原反例，故本项闭合；后续实现仍须用 v4 §7 的无/部分/完整 ParamDef 和 attachment 负例验收。

### 5.3 AUD-003 反例

`edit_test_external_mutation` 只输入 component enum 与 `mutate|reorder`，输出只有 component、前后 fingerprint、changed、semantic_change；没有证明真正改变了该 component 的 projection。重复执行同一个 TypeDef rename 并把输出 component 原样回显，可让所有 `mutate=true` case 全绿；`reorder` 走 no-op 可让所有 false case 全绿。validator 只检查 61 个名字和成对布尔值，无法识别该作弊实现。故逐 metadata table/edge/heap/PDB/resource/opaque 的证据仍不可达。

### 5.4 AUD-005 反例

容量公式按每 risk 1024 bytes、每 dynamic event 1280 bytes、每 validation error 1024 bytes相加，但 schema 的 `maxLength` 是字符，不是 UTF-8 字节；它还允许 64×4096 字符 warnings、32767 字符 artifact path、两组各 64 条 validation error 等内容，而公式没有从这些字段机械推导。独立构造响应在不使用 diff 的情况下已达 4,435,095 字节，证明“最大合法 review 小于 2 MiB”不成立。另 `capacity-golden.json` 只有一个 `review(new-id,no-lease)` transition；source 中关于新 review 替换当前 full slot/旧 review stale 的 `review_lifecycle` 没有被任何生成物发布给按 v4 要求消费 golden 的实施者。

### 5.5 AUD-006 反例

fault source 生成 row 时不产生 `target`，但 success/error 的 `execution_evidence` 都要求每 row 有非空 `target`，所以 golden row 不能直接成为 oracle row。若 runner补 target，便不是与 golden row 完全相等；若只比较 fault ID，方案/生成物又没有把“四集合完全相等”限定为 ID 投影。动态 `not_requested` branch 仍允许非空 events、任意 cleanup booleans 和 residual path，而 v3 曾明确要求 events 空、attempt=false、debug_idle=true、residual=null；validator 只检查五个 state const 出现，未检查状态不变量。
