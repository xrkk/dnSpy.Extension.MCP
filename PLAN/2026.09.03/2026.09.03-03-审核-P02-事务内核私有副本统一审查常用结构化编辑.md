## 4. 审计意见

### AUD-001：公开 schema 与逐操作语义没有真正冻结

- 首次提出轮次：第 1 轮（首次全面审核）。
- 严重度：高。
- 来源与证据：REQ-002、CON-024、NON-001；OUT-002；子方案 §3.1/§3.3/§4、IMP-003/004、ACC-003。§3.3 声称五工具发布内联 schema，但本文只给必要输入名和顶层信封；§4 只列字段主题，没有各 kind 的实际 JSON 属性、类型、required/nullable、枚举、默认、互斥、`additionalProperties`、成功结果与失败前置顺序。
- 具体反例：两个实现都可声称遵循 `method_update`，一个把未提供的 flags/body 解释为“保持不变”，另一个解释为默认值/空 body；`parameter_update` 的“序号”可被解释为 MethodSig 的零基索引或 ParamDef 的一基 `Sequence`（且 `Sequence=0` 是返回参数）；`type_remove` 可级联删除 nested/member，也可只从父集合移除。它们会产生不同字节、风险、反向操作和 diff，但当前 ACC 无法判定谁合规。字段 `List<System.String>`、构造泛型、矩形数组等常用签名也不在 §4 明列的类型语法内。
- 风险/影响：公开 MCP 契约、Python 方法、规范化差异、风险和未来 P03 操作持久化无法稳定互通；实施者必须做超出“局部类名可调整”的产品决定。影响 RACC-003/ACC-003、IMP-003/004/005，以及接口、错误、常用操作、P03 交接和可直接实施性通过项。
- 最小闭合条件：在方案中冻结五工具的完整 inline input/output schema；为每个 operation kind 列出精确 payload、父对象、target 二选一、字段类型/必填/默认/更新补丁语义、attributes 合法掩码、成功返回的 revision/object ID/diff；冻结 parameter/return parameter、property index signature、event/accessor、nested type 和 remove/cascade/reject 语义；明确支持或能力拒绝的常用 TypeSig 集合；定义未知字段/原始载荷的 `-32602` 拒绝。
- 复审证据：逐工具 schema fixture 经严格 JSON Schema 校验；每个 operation kind 的规范请求/响应 golden fixture；相同输入的规范化 diff/risk/object ID 规则；未知字段、互斥 target、原始载荷和歧义签名负例。

### AUD-002：写出/重载不是充分的结构验证，风险确认与结构硬阻断边界未闭合

- 首次提出轮次：第 1 轮（首次全面审核）。
- 严重度：高。
- 来源与证据：REQ-002/008、CON-017/020；OUT-002；子方案 §4 第 134/136 行、§5 第 142 行、IMP-004/005、ACC-003/010。当前静态清单只验证可写出、可重载、索引边界/唯一性/引用可编码；同时把“删除仍被本模块引用的对象”列成 risk，却未说明何时它已经是不可确认绕过的结构错误。
- 具体反例：`void M()` 的 body 使用 `pop; ret`、低于实际栈深的 `MaxStack`、普通 branch 跳入 try/handler、错误的 filter/catch 组合，都可满足“目标索引在边界内”且可能写出/重载，却不是有效可执行 IL；从 `G<T,U>` 删除 `T` 而字段/IL 仍引用 `!0/!1`，或删除仍由 Property/Event accessor 和 MethodSemantics 引用的方法，也可能留下悬空或语义错误图。仅给一个 risk ID 并允许确认，会违反结构错误硬阻断。
- 风险/影响：畸形私有副本可能被审查为可用并进入实时应用；反向恢复只能恢复字节状态，不能弥补错误成功判定。影响 RACC-003/010、ACC-003/010、IMP-004/005/006，以及结构验证、风险、实时应用和错误契约通过项。
- 最小闭合条件：冻结硬验证器及不变量：IL 栈数据流/ret/call/branch/leave、MaxStack、prefix、locals/args、EH 区间与控制流；MethodSig/ParamDef/GenericParam 编号和所有 `!n/!!n` 使用；Type/member ownership、MethodSemantics、accessor 签名/flags、嵌套关系和全部入站引用。明确“可确认风险”只能在结构图有效后产生，无法修复的 dangling reference 必须 `EDIT_VALIDATION_FAILED`，不能靠确认继续。
- 复审证据：每类硬不变量至少一个失败 fixture，证明 apply 原子恢复、revision 不增、review 不生成；另有结构有效但高风险的正例，证明风险确认和结构错误是两条不同路径。

### AUD-003：写出重载后的对象 ID 重绑定与指纹规范化算法缺失

- 首次提出轮次：第 1 轮（首次全面审核）。
- 严重度：高。
- 来源与证据：REQ-001/008、CON-004/020；OUT-002；子方案 §3.4、§4 第 134 行、§5、IMP-002/004/005、ACC-001/003/010。方案要求每次 apply 后完整写出/重载，又要求新对象保持事务域 `obj-*` 引用及 live/private 指纹可比较，但没有定义重载前后映射、删除后的失效规则或指纹的规范编码。
- 具体反例：第一次 `method_add` 返回 `obj-1`，写出/重载后原 `MethodDef` 对象已不在新工作图；第二次用 `obj-1` 设置 property getter 时，实现若按名称寻找会违反“不得名称猜测”，若保留旧对象引用会改到废弃图，若只记新 token 又需定义 writer 分配和重载解析的原子映射。指纹若直接枚举集合顺序、对象 `FullName` 或运行时 operand 形态，live 中的 MethodDef 与 reload 后的 MemberRef/Def 表达差异、PDB 是否实际加载、null/end sentinel 或新增 RID 排序都可能制造假冲突或漏冲突。
- 风险/影响：连续编辑、删除后引用、审查绑定、实时冲突和恢复前后相等性均不可靠。影响 ACC-001/003/010、IMP-002/004/005/006，以及私有副本、身份、指纹、审查和 P03 交接通过项。
- 最小闭合条件：冻结原对象 token 保持校验、新对象 ID→重载后 token/owner/kind 的映射生成与原子替换、删除/回滚后的 ID 失效规则；冻结逐表排序、字符串/签名/flags、operand 目标、IL/EH sentinel、资源和 Embedded PDB 的规范字节编码；写明 dnlib writer/load/PDB options、resolver 生命周期和旧 ModuleDef 释放所有权。任何 token/MVID/PDB 或重绑定漂移必须在工作区发布前失败。
- 复审证据：同一模块 live→copy→reload 指纹相等；集合顺序变化不误报、单字段/IL/EH/resource/sequence-point 变化必报；add→reload→用 object ID update/link/remove 的连续链；失败回滚后旧 ID 映射和指纹恢复；重复名称对象不靠名称重绑定。

### AUD-004：并发请求、会话关闭、超时与幂等缓存没有线性化协议

- 首次提出轮次：第 1 轮（首次全面审核）。
- 严重度：高。
- 来源与证据：REQ-001/017、CON-002/007/008；OUT-002；子方案 §3.1/§3.2、IMP-001/007、ACC-001/002。基线 `McpServer` 在并发请求线程路由工具，`McpToolRegistry` 不串行；`McpTransportSessionLifecycle` 从独立关闭路径同步通知观察者。方案只列状态和结果，没有定义这些事件的原子顺序。
- 具体反例：owner 的 `edit_apply` 已核对 revision 但尚未发布新 workspace 时，同一 session 收到 DELETE；关闭观察者先回滚并令全局 idle，原 apply 随后仍替换 workspace、加 revision 或返回成功，造成“已关闭会话成功修改不存在事务”。两个相同 request ID 同时进入时，也未规定后到调用等待、命中 in-flight 还是失败。600000ms 定时回调与恰在边界到达的 owner status/apply 同时竞争时，当前文本无法判断谁线性化成功。
- 风险/影响：会话所有权、单事务、原子回滚、revision、幂等响应和 600 秒边界都可能分裂；P01 的“通知一次”不能自动保证 P02 事务只结束一次。影响 RACC-001/002/009、ACC-001/002/009、IMP-001/006/007 和生命周期/所有权/幂等通过项。
- 最小闭合条件：给出协调器状态转换表和唯一同步域/队列；为 begin/apply/review/rollback/status、session close、listener Stop、timer、test apply/restore 定义线性化点、锁内/Dispatcher 内边界及关闭后的响应规则；冻结 in-flight 同 ID 合并和响应 settle 次序；说明 close/timeout 如何取消或等待正在执行调用，确保不会在 idle 后发布成功；定义 600000ms 相等边界。
- 复审证据：屏障控制的 apply-vs-DELETE、review-vs-timeout、begin-vs-old-close、同 ID 并发/异载荷并发、listener Stop-vs-apply 测试；事件/响应/revision/cache/最终 idle 的有序转录。

### AUD-005：资源界限与“Dispatcher 短临界区”不能同时由现方案保证

- 首次提出轮次：第 1 轮（首次全面审核）。
- 严重度：中。
- 来源与证据：CON-005、NON-018、OUT-002；子方案 §3.1 第 82 行、§4、§5 第 146 行、§8 第 188 行、IMP-001/004/006、ACC-001/009。缓存只写“有界”，操作/差异/review/object map 没有数量或字节上限；事务可被 owner 持续活动而永不过期。
- 具体反例：调用者每 599 秒提交接近 1 MiB 的 method body，累积数千操作、缓存响应和 diff；系统仍只持有“一个模块副本”，但其附属数据可无界增长。实时应用若把全部步骤放在一个 Dispatcher callback 内，可长时间冻结 UI；若拆成多个 callback，dnSpy UI 外部编辑又可在步骤间插入，破坏指纹门禁和反向闭环。当前没有最大操作量、预编译 apply plan 大小或可接受 UI 占用标准。
- 风险/影响：进程 OOM、响应超限、缓存无法保证既定重放、UI 卡死，或为缩短 UI 占用而引入原子性漏洞。影响 ACC-001/009、IMP-001/004/006、CON-005/NON-018，以及资源、兼容、实时应用和错误契约通过项。
- 最小闭合条件：冻结事务操作数/规范载荷/差异/review/object map/缓存条目与总字节上限、响应上限和容量不足错误/恢复建议；保证拒绝在副作用前且幂等；定义实时 apply plan 在 Dispatcher 外预计算、Dispatcher 内重新核指纹后一次有界执行的机制，或给出同等原子且可证明短占用的设计；超限模块按能力拒绝且不得靠 OOM 探测。
- 复审证据：各上限边界与超一测试、内存/缓存计数、重复请求保持确定性、超限零实时副作用；最大允许事务的 Dispatcher 时间/步骤证据和步骤间外部 mutation 竞争测试。

### AUD-006：ACC-003/009/010 的关键验收矩阵不足，需求保真门禁不能按 6/6 通过

- 首次提出轮次：第 1 轮（首次全面审核）。
- 严重度：高。
- 来源与证据：RACC-003/009/010，REQ-002/007/008，CON-005/017/020/021；OUT-002；子方案 §4/§5、IMP-004/005/006/008、ACC-003/009/010。ACC-003 的“每个种类至少一项 add/update/remove 或适用组合”没有固定 22 个 kind 的逐项矩阵和负例；ACC-009 用“每个实际边界”定义自身覆盖面，没有稳定 fault-point 清单/数量/manifest；ACC-010 从未请求动态验证，默认 `not_requested` 也能满足其当前文字。
- 具体反例：实现只给 type 做 add、method 做 update、field 做 remove，其余类别各挑一项，即可把“适用组合”解释为覆盖，却没有证明每类声明的增删改；实现把全部实时操作包成一个名为 `apply` 的故障点，就能声称遍历“每个实际边界”；`edit_review` 永远返回 `dynamic_validation=not_requested`，ACC-010 仍可只检查字段存在而通过，未证明可执行 EXE 的 passed/failed、DLL not_applicable、VM blocked、启动失败和临时文件/调试清理。
- 风险/影响：实现可在缺功能、缺恢复边界或动态验证不可用时产出全绿 summary。影响 ACC-003/009/010、IMP-004/005/006/008/009、测试证据和需求保真计数。
- 最小闭合条件：建立 operation-kind×add/update/remove/正例/非法结构/重载读回矩阵，逐个列出不适用项及原因；由规范化实时 apply plan 产生稳定 fault-point ID/顺序/总数并落盘 manifest，正向每点和至少一个反向点必须逐项命中；为动态验证增加 EXE passed、目标失败、VM blocked、DLL/no-entry not_applicable、启动/终止/删除失败与最终 debug idle/temp 清理矩阵；NON-001 增加注册表无原始编辑和原始载荷拒绝检查。
- 复审证据：固定案例清单、每项 request/response/readback、fault manifest 与注入覆盖集合相等证明、动态验证进程事件和清理清单、summary 对所有子检查的独立聚合。

### AUD-007：测试实时应用的结束状态文字与 P02/P03 边界直接矛盾

- 首次提出轮次：第 1 轮（首次全面审核）。
- 严重度：高。
- 来源与证据：REQ-007、OUT-002/OUT-003；总纲 §4.2 明确 P02 不发布无检查点提交；子方案 §1 第 24 行、§3.1 第 84 行、§3.2 第 88 行、§5 第 146 行、§8。§5 原文称测试入口“该入口不离开已提交状态”，但 P02 状态集合没有“已提交”，且同文要求同调用恢复实时指纹、不留下产品提交。
- 具体反例：实施者按字面让入口结束在 committed/实时私有指纹，或为满足状态集合自行新增 committed；这会直接形成 P03 检查点前的提交路径。另一实现恢复实时后回到 reviewed。二者相反而都可引用本文不同段落。
- 风险/影响：可能越过 P03 的检查点原子闭环，造成实时已改但无检查点、Undo 或恢复语义；也使 ACC-003/009 的最终状态 oracle 不确定。影响 OUT-002/003 边界、ACC-003/009、IMP-006 和状态/实时应用/交接通过项。
- 最小闭合条件：明确该句的唯一含义；固定成功、正向失败且恢复成功、反向失败三条路径的实时指纹、事务状态、review 可用性和响应 `ok/state`。成功测试入口必须在同一调用恢复提交前实时指纹，并明确不产生 committed/checkpoint/export/Undo 事实。
- 复审证据：三路径状态转换表及自动测试，证明产品 tools/list 无提交接口、测试入口结束时 live=pre-apply，且只有反向失败进入 `live_state_unknown`。
