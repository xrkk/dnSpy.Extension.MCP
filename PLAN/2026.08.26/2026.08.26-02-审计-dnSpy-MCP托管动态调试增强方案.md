## 3. 审计意见

### AUD-001：新公共工具只有名称和公共 envelope，没有可唯一编码的逐工具协议与完整状态机

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-003..011、CON-DYN-004、CON-DYN-005、CON-DYN-009、RACC-DYN-002..007；方案 3.2、3.3、3.4；IMP-002、IMP-004..009；ACC-002..019、ACC-024..027。
- 已证实问题：3.3 只列出 26 个工具名，3.4 只固定公共 envelope 和错误码。方案没有逐工具输入 JSON schema、required/optional 字段、类型/编码、枚举、默认值、分页/游标规则、result/event/capability 字段，也没有“工具 × 状态”的完整允许/拒绝矩阵和转移表。
- 证据：例如 debug_launch 未固定 target/host/harness/hash/argv/runtime/break-kind 的公开字段；debug_read_events 未固定 cursor/limit/timeout 与 event payload；debug_set_exception_policy 未固定策略枚举；debug_read_memory 未固定 address/module handle 的编码；debug_status、debug_capabilities 和全部 result 的字段集合未定义。ACC 多数仅写“调用/读取/逐项操作”，没有可直接复制的 JSON-RPC 请求。
- 风险：两个实施者可在不违反现有文字的情况下产出互不兼容的 schema、状态转移和恢复行为；测试也无法在实现前冻结契约，违反“实施者只读方案即可直接编码”和 CON-DYN-005 的兼容边界。
- 影响：需求覆盖表形式完整，但公共接口、异常/边界和状态变化尚未机械闭合；当前方案不可安全交接实施。
- 建议：为每个工具增加稳定 schema/result/event ID，固定字段、编码、默认值、上限和错误；增加完整状态转移表及幂等/重复请求/并发请求规则；让每个 ACC 引用固定请求 fixture 或给出完整 JSON-RPC 操作与精确响应断言。

### AUD-002：x86/x64 与 CoreCLR dotnet-host 支持没有完整进入同一提交的发布硬门禁

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-002、REQ-DYN-014、RACC-DYN-004、RACC-DYN-009、方案 3.1、IMP-011、ACC-007、ACC-008、ACC-009、ACC-022。
- 已证实问题：REQ-DYN-002 明确承诺 net48/CoreCLR x86/x64；ACC-007..009 没有 architecture 参数或四类位数组合。ACC-008 单独要求 coreclr-dotnet，但 ACC-022/IMP-011 的发布 verify 固定命令只有 net48 和 coreclr-apphost，没有 coreclr-dotnet。
- 证据：ACC-022 明列 run-debug-tests.ps1 -Runtime net48 -Scenario all 与 -Runtime coreclr-apphost -Scenario all，未列 -Runtime coreclr-dotnet，也未列 x86/x64 矩阵。
- 风险：只实现 x64、或 CoreCLR DLL 通过 dotnet host 已损坏的版本，仍可满足当前发布门禁并被打包。
- 影响：REQ-DYN-002 与 RACC-DYN-009 存在无硬门禁覆盖的支持分支，双向追溯不能证明发布闭环。
- 建议：固定 net48 x86/x64、CoreCLR apphost x86/x64、coreclr-dotnet x86/x64 的可执行矩阵；对 launch、attach/detach、断点、步进、locals 和 dump 明确适用组合；将同一矩阵作为 reusable verify 的硬依赖并在 ACC-022 列出实际命令。

### AUD-003：harness、断点启停和 FB-001 的关键分支没有确定性验收

- 严重度：高。
- 来源或方案 ID：REQ-DYN-002、REQ-DYN-007、REQ-DYN-010、RACC-DYN-005、RACC-DYN-007、方案 3.1、3.3、IMP-005、IMP-006、IMP-009、ACC-010、ACC-019、ACC-026、FB-001。
- 已证实问题：3.1 承诺无入口类库可用用户 harness，但 ACC-026 只验证 harness 的非法路径/哈希/argv，没有成功加载类库的正向生命周期；公开工具 debug_set_breakpoint_enabled 没有任何 ACC 执行启用/禁用及命中边界；ACC-019 没有确定性强制 raw bytes unavailable、ForceMemory 成功，以及 raw/ForceMemory 均失败三个 FB-001 分支。
- 风险：harness 路径、断点 enable/disable 或 reconstructed PE 可完全未实现/实现错误，现有 ACC 仍可能全部通过；fallback 可能掩盖失败或错误标注取证产物。
- 影响：功能闭环与 fallback 评定不完整。
- 建议：增加正向 harness fixture；增加 enable→不命中、disable→不命中、重新 enable→命中且只影响 owned breakpoint 的验收；为 FB-001 提供可注入的确定性 raw-bytes 状态或专用 fixture，分别验证 raw、reconstructed 和 CAPABILITY_UNAVAILABLE，核对 manifest 与哈希语义。

### AUD-004：紧邻 Start 重算哈希不足以满足 ACC-026 声明的 TOCTOU 拒绝

- 严重度：阻断性安全问题。
- 来源或方案 ID：REQ-DYN-011、CON-DYN-010、RACC-DYN-004、IMP-005、ACC-026。
- 已证实问题：CON-DYN-010/IMP-005 只要求路径无 reparse point并在紧邻 DbgManager.Start 前重算 SHA-256；校验完成到 Start/实际模块加载之间仍存在可替换窗口。ACC-026 却要求“校验后替换文件”必然在 Start 前被拒绝。
- 代码/API 证据：CorDebugStartDebuggingOptions blob 99c2d9eac5354d63113e43238c6ffccb404170c5 和 DotNetStartDebuggingOptions blob 50aae6c9100a65a87081a11afaa03615fe207742 只接受 Filename、Host、CommandLine/HostArguments 等字符串，没有把已校验文件句柄交给 Start 的契约。
- 风险：攻击者可在最后一次哈希后替换 target/host/harness；错误文件可能先执行，事后 ownership/hash 检测无法撤销执行。
- 影响：安全边界和 ACC-026 的通过条件在当前实施契约下不可达。
- 建议：明确句柄固定方案：以禁止写入/删除共享的句柄打开并从句柄校验最终路径、文件 ID 和 SHA-256，在 CreateProcess 完成前保持 host/EXE 句柄，在 CoreCLR DLL/harness 被目标 runtime 确认加载前保持对应句柄；若公共 dnSpy API 无法保证该机制，则降低承诺并重写 ACC，不得把“紧邻重算”表述为已闭合 TOCTOU。

### AUD-005：IsDebugging 预检与 Start 不是原子独占准入，仍可能并发影响人工会话

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-004、REQ-DYN-012、CON-DYN-003、CON-DYN-004、RACC-DYN-004、IMP-004、IMP-005、ACC-025、ACC-027。
- 已证实问题：方案以 DbgManager.IsDebugging == false 作为 launch/attach 前置条件，然后另行调用 Start；没有定义与 dnSpy UI 启动命令共享的原子门或调度域。ACC-025 只覆盖“UI 已先启动”，未覆盖两者同时通过预检的竞争。
- 代码证据：DbgManager.cs blob e1c907ebc532b2b66e71a57d86fd1c271f6fd00e 将 IsDebugging 与 Start 暴露为独立操作；DbgManagerImpl.cs blob 841ba23fa194df7156878542b167b01edb825f55 的 Start 在创建 engine 后异步排入 Start_DbgThread，Start_DbgThread 会把 engine 追加到 engines，没有独占检查。实现本身允许多个 engine。
- 风险：MCP 与人工 UI 同时启动时可各自创建 engine；之后进入 ownership_lost/faulted 只能检测冲突，不能撤销已经启动或附加的第二目标。全局 Restart 的历史 options 也会放大误操作风险。
- 影响：不影响人工 dnSpy 会话的需求和独占所有权决定尚未闭合。
- 建议：为人工 UI 启动与 MCP launch/attach 定义共享的串行化点；若仅能保证 UI 场景，可把准入检查和 DbgManager.Start 作为一个 WPF Dispatcher 原子操作，再把对象处理移回 debugger dispatcher，并补并发启动测试。若公共 API 无法建立该保证，应将并发启动列为明确阻断而不是事后 faulted 恢复。
