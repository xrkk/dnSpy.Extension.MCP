## 3. 固定范围与公共协议

### 3.1 v1 支持范围

- .NET Framework EXE 与 CoreCLR apphost/EXE：启动和附加。
- 有 runtimeconfig、可由用户显式指定 `dotnet` host 启动的 CoreCLR DLL。
- 无入口类库：仅附加到用户明确选择的宿主，或使用用户提供、位于 allowed root 且单独校验哈希的 harness；扩展不生成 loader。
- 动态/内存托管模块：枚举并导出有来源标识的 raw 或 reconstructed 产物。

### 3.2 组件与所有权

```text
McpServer
  -> McpToolRegistry
       -> StaticToolProvider -> WPF Dispatcher
       -> DebugToolProvider
            -> DebugSessionCoordinator -> DbgManager.Dispatcher
                 -> DebugEventBuffer
                 -> DebugBreakpointStore
                 -> DebugHandleStore
                 -> DebugArtifactStore
```

`McpServer` 不识别具体业务工具。调试调用通过 `DbgManager.Dispatcher.BeginInvoke()` 和一次性 Task completion bridge 获取 DTO；调试事件处理器不得等待 HTTP、WPF、磁盘或另一 dispatcher。coordinator 记录 MCP 拥有的 `DbgProcess`/runtime identity：pause/continue/terminate/detach 只调用该 process 的实例操作，不调用 `BreakAll`、`RunAll`、`TerminateAll`、`DetachAll`。restart 只能在 CON-DYN-004 的独占断言再次通过后调用 `DbgManager.Restart`。

公开状态固定为 `idle`、`starting`、`attaching`、`running`、`paused`、`restarting`、`stopping`、`faulted`。终止、分离或进程退出完成后回到 `idle`，最终原因保留在事件中。

- `generation` 在成功接受 launch、attach、restart 后增加。
- `pause_epoch` 在进入暂停和离开暂停时增加。
- handle 包含 session、generation、pause_epoch 和对象定位；不匹配返回 `STALE_HANDLE`。
- HTTP 层不得缓存 dnSpy process/thread/frame/value 对象；解析、读取、关闭均在 debugger dispatcher 内完成。
- Start/Attach 在取得 owned process 前失败时写失败事件、释放 reservation 并回到 `idle`；owned target 正常或意外退出时使全部 handle 失效、写退出事件并回到 `idle`。
- ownership lost 后保持 `faulted`，直至 `DbgManager.IsDebugging == false` 且已无 owned process/runtime；届时清空句柄和所有权并写 recovery 事件后回到 `idle`。在此之前只允许 capabilities、status、read/wait events，控制请求均为 `OWNERSHIP_LOST`。

### 3.3 工具集合

- 能力和状态：`debug_capabilities`、`debug_status`
- 生命周期：`debug_launch`、`debug_list_attachable_processes`、`debug_attach`、`debug_pause`、`debug_continue`、`debug_restart`、`debug_terminate`、`debug_detach`
- 事件：`debug_read_events`、`debug_wait_event`
- 断点：`debug_set_breakpoint`、`debug_list_breakpoints`、`debug_set_breakpoint_enabled`、`debug_remove_breakpoint`
- 检查：`debug_list_threads`、`debug_get_stack`、`debug_step`、`debug_get_locals`、`debug_expand_value`
- 取证：`debug_list_modules`、`debug_read_memory`、`debug_dump_module`
- 异常：`debug_set_exception_policy`

不新增 `debug_evaluate`、`debug_write_memory`、`debug_set_ip`、`debug_set_variable` 或通用 `debug_command`。

### 3.4 响应、错误与能力

文本 content 与可选 `structuredContent` 表达同一 JSON 对象：

```json
{
  "schema_version": "dnspy.debug.v1",
  "ok": true,
  "debug_context": {
    "session_id": "opaque",
    "generation": 1,
    "pause_epoch": 2,
    "event_cursor": 10
  },
  "result": {},
  "warnings": []
}
```

领域错误固定包含 `DEBUG_DISABLED`、`UNAUTHORIZED`、`CAPABILITY_UNAVAILABLE`、`INVALID_STATE`、`STALE_HANDLE`、`TARGET_MISMATCH`、`NOT_FOUND`、`LIMIT_EXCEEDED`、`TIMEOUT`、`OWNERSHIP_LOST`、`INTERNAL_ERROR`。错误 tool result 设置 `isError=true`，包含当前状态和机械恢复条件；协议级 JSON-RPC error 不承载调试领域失败。

## 7. Fallback 清单

### FB-001：raw runtime bytes 不可用时重构托管 PE

- 依据：REQ-DYN-010、RACC-DYN-007；EVD-API-005 明确 raw bytes 可不可用且 ForceMemory metadata 可用。
- 触发条件：托管模块的 raw bytes 不可用，且 ForceMemory metadata 成功。
- 行为和影响：输出 `reconstructed` PE；manifest 声明非原始字节、重构 API 与布局，不用于原始文件哈希等价判断。
- 退出方式：raw bytes 可用即优先 raw；两者均不可用返回 `CAPABILITY_UNAVAILABLE`，不调用进程外 dump 工具。

### FB-002：不支持 runtime 的工作流交接

- 依据：REQ-DYN-002、REQ-DYN-003、NON-DYN-001、RACC-DYN-010。
- 触发条件：识别为 Unity/Mono、混合模式原生阶段、纯原生，或契约报告 runtime 不支持。
- 行为和影响：不创建/继续伪托管 session；返回种类、证据与 Mono 或 PE/x64dbg 交接提示。
- 退出方式：用户切换工作流，或未来经独立审核方案新增 capability；v1 不降级为 GUI 自动化。

除 FB-001、FB-002 外无 fallback。认证失败、端口占用、hash/path/所有权不符、非法状态、过期句柄、预算超限、缺显式宿主、memory 超范围均直接失败；不得以 fallback 掩盖主流程错误。

## 10. 审核重点

- SRC-BASE-001 的 v0 需求是否在 v1 完整保留，实施/审核是否完全不依赖对话。
- exclusive MCP ownership、逐 process 操作和全局 Restart 前置条件是否杜绝误操作人工调试会话。
- locals provider、formatter 和 raw-field API 组合是否真正不执行 getter、DebuggerDisplay、ToString 或表达式。
- `DbgProcess.ReadMemory` 的零填充语义、模块内范围和验收是否与 v6.6.0 契约一致。
- 全端点 token/CIDR/限额、一次显示 token 与只存 verifier 是否可在双 TFM HttpListener 中机械验证。
- 六个现有静态写工具的全局调试门控是否完整且不改变 idle 下语义。
- launch 路径、reparse、紧邻 Start 的 hash 复核和 Windows argv quoting 是否覆盖 TOCTOU/命令拼接。
- raw/reconstructed provenance、artifact 配额与保守清理是否避免样本目录污染和误删。
- reusable verify 是否使 build/release 在同一 commit 上真正受 net48/CoreCLR E2E 阻断。
