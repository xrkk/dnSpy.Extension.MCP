## 2. 需求、约束、非目标和需求级验收

### 2.1 功能与安全需求

| 需求 ID | 规范性需求 |
|---|---|
| REQ-DYN-001 | 在 dnSpy 进程内通过 MCP 公共工具控制托管动态调试，不使用 GUI 键鼠自动化，不修改 dnSpy 核心。 |
| REQ-DYN-002 | v1 支持 Windows 上 .NET Framework 与 CoreCLR x86/x64 的启动和附加；Unity/Mono、混合模式和纯原生不属于 v1。 |
| REQ-DYN-003 | 客户端先获得真实能力、协议版本和安全状态；`debug_capabilities` 始终可查询，其他未实现或未启用的调试工具不广告、不假成功。 |
| REQ-DYN-004 | 提供启动、枚举可附加进程、附加、暂停、继续、重启、终止和分离，以显式状态机拒绝非法顺序。 |
| REQ-DYN-005 | 调试事件进入有界、单调游标日志，支持读取和最长 30 秒等待，报告游标过期和事件丢失。 |
| REQ-DYN-006 | 进程、线程、frame、value 句柄绑定 session、generation、pause epoch；恢复或重启后拒绝旧句柄。 |
| REQ-DYN-007 | 断点身份采用模块 SHA-256/MVID、MethodDef token、IL offset；验证指令边界、所有权和实际绑定状态。 |
| REQ-DYN-008 | 提供线程、调用栈和 step into/over/out；不长期持有 continue 后失效的 dnSpy 调试对象。 |
| REQ-DYN-009 | locals、参数、`this` 和对象字段只能以无函数求值、无 getter、无自定义可视化器、无 `ToString()` 的方式读取；v1 不提供任意表达式求值。 |
| REQ-DYN-010 | 提供受限模块枚举、只读内存读取和运行时模块导出；产物进入 session 临时目录并记录来源与 SHA-256，不污染样本目录。 |
| REQ-DYN-011 | 非回环 MCP 必须认证并限制绑定、来源、请求体、响应体、并发和会话；禁止 shell、写内存、SetIP、变量赋值、函数求值和运行时补丁。 |
| REQ-DYN-012 | dnSpy 存在任何活动调试时，现有静态写工具不得执行；样本产生的文本一律是不可信数据，不得作为指令。 |
| REQ-DYN-013 | 当前实验配置为 Windows VM `192.168.204.149:15100`，仅允许 Ubuntu host-only 源地址；仓库和首次启动默认仍绑定回环。 |
| REQ-DYN-014 | 使用 net48 与 CoreCLR 可执行 fixture 验证生命周期、断点、步进、安全取值、导出、附加/分离和安全边界，并作为构建与发布门禁。 |

### 2.2 固定约束

| 约束 ID | 固定决定 |
|---|---|
| CON-DYN-001 | 编译/运行基线为 dnSpyEx `v6.6.0`；保持 net48/net10.0-windows 双 TFM、`.x.dll`、MEF 发现和宿主依赖守卫。 |
| CON-DYN-002 | 两个 TFM 都继续使用 HttpListener；不得引入 Kestrel、按 TFM 分叉的服务器实现或 GUI 自动化。 |
| CON-DYN-003 | 静态 provider 只经 WPF Dispatcher；调试 provider 只经 `DbgManager.Dispatcher`；HTTP 层只持有不可变 DTO/不透明句柄。 |
| CON-DYN-004 | 同一时刻最多一个 MCP 调试 session 和一个 MCP 拥有的根目标；请求进入时已有任意调试则 launch/attach 拒绝。调试 session 独立于 transport session，transport 断开/idle 不终止目标，重连后须携带原 `session_id`；除 capabilities、status、list-attachable、launch、attach 外的调试调用都须匹配它。MCP 只控制经第 3.2 节唯一归属规则确认的 process/runtime，不调用全局 `*All` 或全局 Restart；人工并发 Start 无法由公共 API 原子禁止，属于显式外部竞争并按 CON-DYN-012 失败，不声称事先拦截。 |
| CON-DYN-005 | 保持现有 32 个静态工具名称、schema、成功语义和三种 MCP protocolVersion；领域失败使用 tool result `isError=true`，JSON-RPC error 仅用于协议、参数解析和服务器内部错误。 |
| CON-DYN-006 | 默认 `localhost:3000`；远程模式拒绝通配绑定、固定端口、全端点 Bearer 认证、CIDR allowlist、无 CORS 通配。远程明文 HTTP 只允许隔离 host-only 网络；其他网络配置验证失败并保持回环。当前 `192.168.204.149:15100` 只是部署实例。 |
| CON-DYN-007 | 安全取值固定走 locals provider：同时设置 `NoFuncEval` 和 `RawView`，并设置 `ShowRawLocals`；formatter 固定 `NoDebuggerDisplay` 且不启用 FuncEval/ToString；字段展开只使用 runtime raw-field API，不调用表达式 evaluator。 |
| CON-DYN-008 | 默认 ArtifactRoot 为 `Path.Combine(Path.GetTempPath(), "dnspy-mcp")`；只写带 marker 的 session 子目录；单产物 512 MiB、单 session 1 GiB；启动时只删除该根下带有效 marker 且最后写入超过 7 天的 session 目录。 |
| CON-DYN-009 | 固定传输硬上限：请求体 1 MiB、序列化 tool result 8 MiB、16 个 transport session、16 个并行短请求、8 个长连接、8 个 wait、10 分钟 transport idle；事件缓冲 4096 条且 8 MiB，先触达者生效；memory 单次 64 KiB。 |
| CON-DYN-010 | launch 的 target/host/harness 路径必须位于 allowed root；working directory 默认为 target 所在目录，显式值也须通过同一根目录检查；target 与 host 的 argv 分别使用结构化字符串数组并按 Windows quoting 规则构造，不经过 shell。文件路径与身份必须再满足 CON-DYN-011，单独“紧邻 Start 重算哈希”不构成 TOCTOU 保证。 |
| CON-DYN-011 | target、host、harness、working directory 及其从 allowed root 开始的每个目录组件均须以 Windows handle 打开：使用 `FILE_FLAG_OPEN_REPARSE_POINT`，目录另用 `FILE_FLAG_BACKUP_SEMANTICS`；拒绝 reparse point；由 handle 取最终路径和 FILE_ID_INFO；文件以读访问、仅 `FILE_SHARE_READ` 持有，目录句柄不授予 delete sharing。哈希只从已持有文件句柄读取。EXE/host、working directory 和目录组件句柄保持到 process-created 且 image identity 确认；CoreCLR DLL/harness 文件句柄保持到 module-loaded 且 path、file ID、MVID、SHA-256 确认。任何锁定、身份或确认失败只在已证明 target 为 MCP-owned 后终止该 target，再返回 `TARGET_MISMATCH`；尚未证明所有权时不得终止任何候选。不支持这些语义的文件系统返回 `CAPABILITY_UNAVAILABLE`。 |
| CON-DYN-012 | 公共 dnSpy API 没有人工 UI 与 MCP 共用的原子 Start 门。MCP 在 WPF Dispatcher 串行执行“建立 start claim、检查当前无调试、调用 Start”，随后只在 claim 窗口内恰好出现一个且匹配 expected path/file ID/runtime/architecture 的新 process/runtime 时建立所有权；0 个、多个或出现其他 runtime/process 均为 `OWNERSHIP_LOST`，不得控制任何新对象。使用期间用户不得从 UI 或其他扩展发起 Start/Attach；检测到时 fault。restart 固定为终止 owned process、等待移除、用已保存且重新校验/锁定的 launch 参数再次 Start，不调用 `DbgManager.Restart`；attach session 不支持 restart，返回 `CAPABILITY_UNAVAILABLE`。 |
| CON-DYN-013 | 第 3.5 节的 API/TYPE/EVT 稳定 ID 是公共协议唯一来源。所有 request object `additionalProperties=false`；所有有副作用工具要求 UUID `request_id`。同一 debug session 内请求在有界命令队列按出队顺序串行判定状态；同一 request_id 与同一规范化参数返回缓存结果，不重复副作用；相同 request_id 配不同参数返回 `REQUEST_ID_REUSE`。read/wait 不占命令队列。 |

## 3. 固定范围与公共协议

### 3.1 v1 支持范围

- .NET Framework EXE 与 CoreCLR apphost/EXE：启动和附加。
- 有 runtimeconfig、可由用户显式指定 `dotnet` host 启动的 CoreCLR DLL。
- 无入口类库：仅附加到用户明确选择的宿主，或使用用户提供、位于 allowed root 且单独校验哈希的 harness；扩展不生成 loader。
- 动态/内存托管模块：枚举并导出有来源标识的 raw 或 reconstructed 产物。

### 3.2 组件与所有权

```text
McpServer
  -> McpToolRegistry
       -> StaticToolProvider -> WPF Dispatcher
       -> DebugToolProvider
            -> DebugSessionCoordinator -> DbgManager.Dispatcher
                 -> DebugEventBuffer
                 -> DebugBreakpointStore
                 -> DebugHandleStore
                 -> DebugArtifactStore
```

`McpServer` 不识别具体业务工具。静态调用保持 WPF Dispatcher；调试对象访问通过 `DbgManager.Dispatcher.BeginInvoke()` 和一次性 Task completion bridge 获取 DTO；仅 start-claim 的建立、当前调试预检和 `DbgManager.Start` 调用在一个 WPF Dispatcher callback 内串行执行。该 callback 不是覆盖人工 UI 的原子锁，不能据此声称排除 UI 并发 Start。事件处理器不得等待 HTTP、WPF、磁盘或另一 dispatcher。

coordinator 为每次 launch/attach 建立一个含 request_id、操作、开始单调时间、expected runtime/architecture/path/file ID、attach PID/runtime identity 的 start claim。claim 建立前快照现有 process/runtime；仅 claim 后、30 秒内新增且恰好一个完整匹配的 process/runtime 可成为 owned target。0 个超时、多个新增、任何不匹配新增，或目标 process 同时包含非 claim runtime，均使 claim 失败；MCP 不控制任何新增对象。pause/continue/terminate/detach 只调用 owned `DbgProcess` 的实例操作；禁止 `BreakAll`、`RunAll`、`StopDebuggingAll`、`TerminateAll`、`DetachAll` 和 `DbgManager.Restart`。launch restart 按 CON-DYN-012 重新启动；attach restart 明确不支持。

公开状态固定为 `idle`、`starting`、`attaching`、`running`、`paused`、`restarting`、`stopping`、`faulted`。终止、分离或进程退出完成后回到 `idle`，最终原因保留在事件中。

- `generation` 在成功接受 launch、attach、restart 后增加。
- `pause_epoch` 在进入暂停和离开暂停时增加。
- handle 包含 session、generation、pause_epoch 和对象定位；不匹配返回 `STALE_HANDLE`。
- HTTP 层不得缓存 dnSpy process/thread/frame/value 对象；解析、读取、关闭均在 debugger dispatcher 内完成。
- Start/Attach 在取得 owned process 前失败时写失败事件、释放 reservation 并回到 `idle`；owned target 正常或意外退出时使全部 handle 失效、写退出事件并回到 `idle`。
- ownership lost 后保持 `faulted`，清空“可控制”标志但保留只读事件身份。仅当已确认 owned process 自行退出，或 `DbgManager.IsDebugging == false` 且 manager 中已无 claim 后新增 process/runtime 时，清空句柄和 claim、写 recovery 后回到 `idle`。在此之前只允许 capabilities、status、read/wait events；不得以 terminate/detach 试图清理归属不明对象。

### 3.3 工具集合

- 能力和状态：`debug_capabilities`、`debug_status`
- 生命周期：`debug_launch`、`debug_list_attachable_processes`、`debug_attach`、`debug_pause`、`debug_continue`、`debug_restart`、`debug_terminate`、`debug_detach`
- 事件：`debug_read_events`、`debug_wait_event`

不新增 `debug_evaluate`、`debug_write_memory`、`debug_set_ip`、`debug_set_variable` 或通用 `debug_command`。

### 3.5 公共类型、工具和事件契约

### 3.6 状态、转移、重复与并发

`Y` 表示允许，`R` 表示只允许读取已完成/故障 session 的保留事件，`N` 返回 INVALID_STATE。表中 active/paused 的 session/generation/pause_epoch 仍须匹配。

| API | idle | starting | attaching | running | paused | restarting | stopping | faulted |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| capabilities/status | Y | Y | Y | Y | Y | Y | Y | Y |
| launch/list-attachable/attach | Y | N | N | N | N | N | N | N |
| pause | N | N | N | Y | N | N | N | N |
| continue/step | N | N | N | N | Y | N | N | N |
| restart | N | N | N | Y | Y | N | N | N |
| terminate/detach | N | N | N | Y | Y | N | N | N |
| read-events/wait-event | R | Y | Y | Y | Y | Y | Y | Y |
| set/list/enable/remove breakpoint | N | N | N | list only | Y | N | N | N |
| list threads/get stack/get locals/expand/read memory/dump | N | N | N | N | Y | N | N | N |
| list modules | N | N | N | Y | Y | N | N | N |
| set exception policy | N | Y | Y | Y | Y | N | N | N |

固定转移：

- idle + launch/attach → starting/attaching；claim 成功 → running 或 paused；Start 错误、0 个匹配超时 → idle；歧义/外部并发 → faulted。
- running + pause → paused；paused + continue → running。
- paused + step → running；收到同 step_id 的完成/异常 → paused 或 faulted。
- launch session 的 running/paused + restart → restarting → stopping → idle → starting → running/paused；任一中间失败按 start_failed/ownership_lost 进入 idle/faulted。attach restart 不发生转移，只返回 CAPABILITY_UNAVAILABLE。
- running/paused + terminate/detach → stopping → idle。detach 只允许 attach session；launch session 调 detach 返回 CAPABILITY_UNAVAILABLE。
- target exit → idle；ownership ambiguity → faulted；faulted 只按 3.2 的观察条件自动回 idle，无公共 force-reset。

每个 session 的有副作用命令队列容量 64；第 65 个尚未入队请求返回 LIMIT_EXCEEDED。状态在出队时判定；排队期间发生 state/generation/pause_epoch 变化的请求返回 INVALID_STATE 或 STALE_HANDLE。request_id 成功或失败结果缓存到 session 结束后 10 分钟；同 ID/同规范化参数返回缓存结果，同 ID/异参为 REQUEST_ID_REUSE。所有分页 cursor 绑定查询筛选和 generation；数据变化导致 cursor 无法继续时返回 STALE_HANDLE，不静默重新从第一页开始。

- 对应实施：IMP-006、IMP-011；需求来源：REQ-DYN-007、CON-DYN-013、RACC-DYN-005。
- 前置条件和输入：循环命中两次的强身份 fixture；已验证 MVID、MethodDef token 和 IL 指令边界。
- 命令或操作：`powershell -NoProfile -ExecutionPolicy Bypass -File tests/debug/run-debug-tests.ps1 -Case ACC-031`；case 创建 enabled breakpoint，首次命中后禁用并继续一轮，再暂停、启用并继续，最后删除。
- 精确可观察结果：首次和重新启用后各产生一次 EVT-DYN-013；禁用期间不命中；list 的 enabled/bound 与每次 mutation 一致；删除后列表无该 ID，用户断点不变。
- 证据和边界：API-DYN-013..016 响应、事件计数和 dnSpy breakpoint 快照；禁用仍命中、启用不命中、状态错误或改动非 owned breakpoint 即失败。

### ACC-032：FB-001 三分支确定性验证

- 对应实施：IMP-009、IMP-011、FB-001；需求来源：REQ-DYN-010、RACC-DYN-007。
- 前置条件和输入：注入式 `IRawModuleBytesSource` 可固定返回 raw 成功、raw 不可用且 ForceMemory 成功、两者均不可用；模块内容固定。
- 命令或操作：`powershell -NoProfile -ExecutionPolicy Bypass -File tests/debug/run-debug-tests.ps1 -Case ACC-032`；case 分别执行三种注入并调用 debug_dump_module。
- 精确可观察结果：分支一 artifact.kind=raw 且字节/SHA 与输入相同；分支二 kind=reconstructed 且 manifest 明示重构 API/layout/非原始等价；分支三为 CAPABILITY_UNAVAILABLE 且无产物；三者均不调用进程外 dump 工具。
- 证据和边界：注入调用日志、artifact/manifest/hash 和目录快照；走错分支、伪称 raw、失败留产物或外部 dump 调用即失败。

### ACC-033：Windows 文件身份租约关闭 TOCTOU

- 对应实施：IMP-005、IMP-011；需求来源：REQ-DYN-004、REQ-DYN-011、CON-DYN-010、CON-DYN-011、NON-DYN-006、RACC-DYN-004。
- 前置条件和输入：NTFS allowed root；target、host、working directory、harness 的合法副本；测试 barrier 可在验证完成、Start 前以及 process/module identity 确认前尝试覆盖、删除、rename、reparse 替换。
- 命令或操作：`powershell -NoProfile -ExecutionPolicy Bypass -File tests/debug/run-debug-tests.ps1 -Case ACC-033`；case 在各 barrier 并发执行四类替换并记录 Win32 结果，再运行正常不替换对照；另在不支持稳定 FILE_ID_INFO/共享语义的文件系统运行一次。
- 精确可观察结果：合法 NTFS 对照从已哈希 handle 建权；租约存续期间覆盖/删除/rename/reparse 替换均因 share 冲突失败，或 identity mismatch 导致仅已证明 owned 的目标终止并返回 TARGET_MISMATCH；CoreCLR DLL/harness 在 module-loaded 后 MVID/SHA/FileId 复核；不支持文件系统在 Start 前为 CAPABILITY_UNAVAILABLE，无进程/session。
- 证据和边界：CreateFile flags、final path、volume serial/file ID/hash、替换 Win32 error、process/module identity、进程列表；仅二次按路径哈希、替换后建权、控制未知进程、未持有租约或 unsupported 文件系统启动即失败。

### ACC-034：人工并发 Start 与局部 restart

- 对应实施：IMP-004、IMP-005、IMP-011；需求来源：REQ-DYN-004、REQ-DYN-006、CON-DYN-004、CON-DYN-012、RACC-DYN-004。
- 前置条件和输入：可在 MCP WPF callback 的 precheck 与 `DbgManager.Start` 间注入 barrier，并能由测试模拟一次 UI Start；另有已建权 launch session 和 attach session。
- 命令或操作：`powershell -NoProfile -ExecutionPolicy Bypass -File tests/debug/run-debug-tests.ps1 -Case ACC-034`；case 在 barrier 触发 UI Start 后释放 MCP Start，记录 process/runtime 集合；再对 launch session restart，对 attach session restart。
- 精确可观察结果：并发场景不声称阻止 UI Start；MCP 只有观测到恰好一个匹配新 process/runtime 才建权，否则进入 faulted、产生 EVT-DYN-017 且不控制任何候选；launch restart 只 terminate 已拥有 process、等待 terminal event、重验租约后局部 Start，新 generation；attach restart 为 CAPABILITY_UNAVAILABLE；调用 spy 中全程无 `DbgManager.Restart` 或任何全局 `*All`。
- 证据和边界：barrier 时间线、process/runtime diff、ownership/event/state、generation 和 DbgManager 调用 spy；歧义仍建权、误控 UI 目标、全局 Restart/*All、attach 被重启或旧 generation 继续有效即失败。

## 7. Fallback 清单

### FB-001：raw runtime bytes 不可用时重构托管 PE

- 依据：REQ-DYN-010、RACC-DYN-007；EVD-API-005 明确 raw bytes 可不可用且 ForceMemory metadata 可用。
- 触发条件：托管模块的 raw bytes 不可用，且 ForceMemory metadata 成功。
- 行为和影响：输出 `reconstructed` PE；manifest 声明非原始字节、重构 API 与布局，不用于原始文件哈希等价判断。
- 退出方式：raw bytes 可用即优先 raw；两者均不可用返回 `CAPABILITY_UNAVAILABLE`，不调用进程外 dump 工具。

### FB-002：不支持 runtime 的工作流交接

- 依据：REQ-DYN-002、REQ-DYN-003、NON-DYN-001、RACC-DYN-010。
- 触发条件：识别为 Unity/Mono、混合模式原生阶段、纯原生，或契约报告 runtime 不支持。
- 行为和影响：不创建/继续伪托管 session；返回种类、证据与 Mono 或 PE/x64dbg 交接提示。
- 退出方式：用户切换工作流，或未来经独立审核方案新增 capability；v1 不降级为 GUI 自动化。

除 FB-001、FB-002 外无 fallback。认证失败、端口占用、hash/path/所有权不符、非法状态、过期句柄、预算超限、缺显式宿主、memory 超范围均直接失败；不得以 fallback 掩盖主流程错误。
