## 2. 需求、约束、非目标和需求级验收

### 2.1 功能与安全需求

| 需求 ID | 规范性需求 |
|---|---|
| REQ-DYN-001 | 在 dnSpy 进程内通过 MCP 公共工具控制托管动态调试，不使用 GUI 键鼠自动化，不修改 dnSpy 核心。 |
| REQ-DYN-002 | v1 支持 Windows 上 .NET Framework 与 CoreCLR x86/x64 的启动；任意进程枚举附加、附加和分离不属于 v1。Unity/Mono、混合模式和纯原生同样不属于 v1。 |
| REQ-DYN-003 | 客户端先获得真实能力、协议版本和安全状态；`debug_capabilities` 始终可查询，其他未实现或未启用的调试工具不广告、不假成功。 |
| REQ-DYN-004 | 提供启动、暂停、继续、重启和终止，以显式状态机拒绝非法顺序；`debug_list_attachable_processes`、`debug_attach`、`debug_detach` 的稳定 API ID 仅作为 v1 禁用能力保留，不得广告或产生副作用。 |
| REQ-DYN-005 | 调试事件进入有界、单调游标日志，支持读取和最长 30 秒等待，报告游标过期和事件丢失。 |
| REQ-DYN-006 | 进程、线程、frame、value 句柄绑定 session、generation、pause epoch；恢复或重启后拒绝旧句柄。 |
| REQ-DYN-007 | 断点身份采用模块 SHA-256/MVID、MethodDef token、IL offset；验证指令边界、所有权和实际绑定状态。 |
| REQ-DYN-008 | 提供线程、调用栈和 step into/over/out；不长期持有 continue 后失效的 dnSpy 调试对象。 |
| REQ-DYN-009 | locals、参数、`this` 和对象字段只能以无函数求值、无 getter、无自定义可视化器、无 `ToString()` 的方式读取；v1 不提供任意表达式求值。 |
| REQ-DYN-010 | 提供受限模块枚举、只读内存读取和运行时模块导出；产物进入 session 临时目录并记录来源与 SHA-256，不污染样本目录。 |

| REQ-DYN-015 | 动态调试只在用户显式确认的专用、非交互 dnSpy 实例中有效；该实例不得用于人工 UI Start/Attach，也不得安装会调用 `DbgManager.Start` 的其他扩展。此条件是部署前提而非扩展可证明的程序属性；不满足时不提供无条件因果所有权保证。 |

### 2.2 固定约束

| 约束 ID | 固定决定 |
|---|---|
| CON-DYN-001 | 编译/运行基线为 dnSpyEx `v6.6.0`；保持 net48/net10.0-windows 双 TFM、`.x.dll`、MEF 发现和宿主依赖守卫。 |

| CON-DYN-004 | 同一时刻最多一个 MCP 调试 session 和一个 MCP launch 的根目标；请求进入时已有任意调试则 launch 拒绝。调试 session 独立于 transport session，transport 断开/idle 不终止目标，重连后须携带原 `session_id`；除 capabilities、status 和 launch 外的已启用调试调用都须匹配它。MCP 只控制在 CON-DYN-014 专用实例前提下按第 3.2 节 launch 建权的 process/runtime，不调用全局 `*All` 或全局 Restart。 |

## 3. 固定范围与公共协议

### 3.1 v1 支持范围

- .NET Framework EXE 与 CoreCLR apphost/EXE：仅启动。
- 有 runtimeconfig、可由用户显式指定 `dotnet` host 启动的 CoreCLR DLL。
- 无入口类库：仅使用用户提供、位于 allowed root 且单独校验哈希的 harness；扩展不生成 loader，也不附加到既有宿主。
- 动态/内存托管模块：枚举并导出有来源标识的 raw 或 reconstructed 产物。
- 运行前提：`DedicatedDebugInstanceAcknowledged=true` 且该 dnSpy 进程只供 MCP launch 使用；人工调试必须使用另一 dnSpy 进程。

### 3.2 组件与所有权

```text
McpServer
  -> McpToolRegistry
       -> StaticToolProvider -> WPF Dispatcher
       -> DebugToolProvider
            -> DebugSessionCoordinator -> DbgManager.Dispatcher
                 -> DebugEventBuffer
                 -> DebugBreakpointStore
                 -> DebugHandleStore
                 -> DebugArtifactStore
```

`McpServer` 不识别具体业务工具。静态调用保持 WPF Dispatcher；调试对象访问通过 `DbgManager.Dispatcher.BeginInvoke()` 和一次性 Task completion bridge 获取 DTO；仅 start-claim 的建立、当前调试预检和 `DbgManager.Start` 调用在一个 WPF Dispatcher callback 内串行执行。该 callback 不是覆盖人工 UI 的原子锁，不能据此声称排除 UI 并发 Start。事件处理器不得等待 HTTP、WPF、磁盘或另一 dispatcher。

coordinator 仅为 launch 建立含 request_id、开始单调时间、launch mode、expected runtime/architecture/path/file ID 的 start claim。claim 建立前必须验证 CON-DYN-014 gate 并快照现有 process/runtime；仅 claim 后、30 秒内新增且恰好一个完整匹配的 process/runtime 才在专用实例前提下成为 owned target。net48-exe/coreclr-apphost 要求新 process image 匹配 target identity；coreclr-dotnet 要求 process image 匹配 host identity 且同一 process 中 module-loaded 匹配 target identity；harness 要求 process image 匹配 harness identity 且同一 process 中 module-loaded 匹配 target identity。0 个超时、多个新增、任何不匹配新增，或目标 process 同时包含非 claim runtime，均使 claim 失败；MCP 不控制任何新增对象。若专用实例前提被违反，身份规则不提供无条件因果证明，按 DEC-DYN-001 接受残余风险。pause/continue/terminate 只调用 owned `DbgProcess` 实例操作；禁止 `BreakAll`、`RunAll`、`StopDebuggingAll`、`TerminateAll`、`DetachAll` 和 `DbgManager.Restart`。launch restart 按 CON-DYN-012 重新启动。

公开状态固定为 `idle`、`starting`、`running`、`paused`、`restarting`、`stopping`、`faulted`；`attaching` 不属于 v1 enum。终止或进程退出完成后回到 `idle`，最终原因保留在事件中。

- `generation` 在请求通过参数/安全检查并取得唯一 start reservation、即将调用 Start 时增加；Start 或 claim 随后失败也不得复用该 generation。restart 仅在旧 generation 全部句柄失效后取得新 generation。
- `pause_epoch` 在进入暂停和离开暂停时增加。
- handle 包含 session、generation、pause_epoch 和对象定位；不匹配返回 `STALE_HANDLE`。
- HTTP 层不得缓存 dnSpy process/thread/frame/value 对象；解析、读取、关闭均在 debugger dispatcher 内完成。
- Start 在取得 owned process 前失败时依次写 EVT-DYN-002、EVT-DYN-020，释放 reservation 并回到 `idle`；owned target 正常或意外退出时使全部 handle 失效，依次写 EVT-DYN-004、EVT-DYN-020 并回到 `idle`。restart 为封闭例外：进入 `restarting` 时取得唯一 restart reservation 并保持原 active session；终止旧 owned process 只写 EVT-DYN-004，不写 EVT-DYN-020，旧 process 移除后公开状态为 `stopping` 而非 `idle`；重新校验/锁定并增加 generation 后直接进入 `starting`。成功进入 running/paused 后才释放 restart reservation；任一步失败写 EVT-DYN-002、EVT-DYN-020、释放 reservation/session 后回 `idle`，歧义则按 ownership lost 进入 `faulted`。
- 每个 session 的事件 cursor 从 1 开始且仅在该 session 内单调；EVT-DYN-020 是唯一 terminal event，写入后冻结。终止 session 的事件日志保留到 terminal 后 10 分钟或下一次 launch 取得 start reservation（二者先到者），之后以该 session_id 调 read/wait/status 返回 `NOT_FOUND`；不得把新 session 事件映射到旧 session_id。
- ownership lost 后保持 `faulted`，清空“可控制”标志但保留只读事件身份。仅当已确认 owned process 自行退出，或 `DbgManager.IsDebugging == false` 且 manager 中已无 claim 后新增 process/runtime 时，清空句柄和 claim、写 recovery 后回到 `idle`。在此之前只允许 capabilities、status、read/wait events；不得以 terminate 试图清理归属不明对象。

### 3.3 工具集合

- 能力和状态：`debug_capabilities`、`debug_status`
- 生命周期：`debug_launch`、`debug_pause`、`debug_continue`、`debug_restart`、`debug_terminate`
- 事件：`debug_read_events`、`debug_wait_event`
- 断点：`debug_set_breakpoint`、`debug_list_breakpoints`、`debug_set_breakpoint_enabled`、`debug_remove_breakpoint`
- 检查：`debug_list_threads`、`debug_get_stack`、`debug_step`、`debug_get_locals`、`debug_expand_value`
- 取证：`debug_list_modules`、`debug_read_memory`、`debug_dump_module`
- 异常：`debug_set_exception_policy`

不新增 `debug_evaluate`、`debug_write_memory`、`debug_set_ip`、`debug_set_variable` 或通用 `debug_command`。

稳定 ID `debug_list_attachable_processes`（API-DYN-004）、`debug_attach`（API-DYN-005）、`debug_detach`（API-DYN-010）是 v1 禁用能力：三个 protocolVersion 的 tools/list 都不得广告；直接 tools/call 必须返回 `CAPABILITY_UNAVAILABLE` 且无副作用。启用时 tools/list 恰含上述 22 个活动工具，关闭或未确认专用实例时只比现有静态工具多 `debug_capabilities`。

### 3.4 响应、错误与能力

协商后的 MCP protocolVersion 决定 tools/list 与 tools/call 的外层表示，内部 `dnspy.debug.v1` envelope 不随版本变化：

| MCP protocolVersion | tools/list 中动态工具 | tools/call result |
|---|---|---|
| `2024-11-05` | 只含该版本允许的 name、description、inputSchema，必须省略 outputSchema | 只含 `content` 和领域失败时的 `isError=true`，必须省略 structuredContent；恰好一个 text content block 的 text 是 canonical JSON envelope |

现有 32 个静态工具在三版本下的 tools/list 与 tools/call wire shape 保持既有快照，不因本方案新增 outputSchema 或 structuredContent。以下是三版本共同表达的成功 envelope；字段全集固定，禁止额外字段：

```json
{
  "schema_version": "dnspy.debug.v1",
  "ok": true,
  "debug_context": {
    "session_id": "opaque",
    "generation": 1,
    "pause_epoch": 2,
    "event_cursor": 10,
    "state": "paused"
  },
  "result": {},
  "warnings": [],
  "untrusted_sample_data": false
}
```

失败对象把 `result` 替换为 `error` TYPE-DYN-011，`ok=false`，其余四个顶层字段仍必须存在；成功对象不得含 `error`，失败对象不得含 `result`。`warnings` 是最多 32 项、每项最多 1024 UTF-8 字节的服务端诊断 string array，不承载恢复协议。`untrusted_sample_data` 是 mandatory boolean：result/error/warnings 中任一文本或路径来自目标进程、样本元数据或样本输出时为 true，否则 false；客户端必须把 true 的整个 payload 当作数据而非指令。

领域错误固定包含 `DEBUG_DISABLED`、`CAPABILITY_UNAVAILABLE`、`INVALID_STATE`、`STALE_HANDLE`、`TARGET_MISMATCH`、`NOT_FOUND`、`ALREADY_EXISTS`、`LIMIT_EXCEEDED`、`TIMEOUT`、`OWNERSHIP_LOST`、`REQUEST_ID_REUSE`、`INTERNAL_ERROR`。错误 tool result 设置 `isError=true` 当且仅当 envelope 的 `ok=false`。HTTP 认证/CIDR 失败严格按 CON-DYN-006 在解析 JSON-RPC 前返回唯一的 401 或 403：401 含固定 WWW-Authenticate，403 不含；二者 body 均为空且无 MCP tool result。保留字 `UNAUTHORIZED` 在 v1 tool schema 中不得产生。协议级 JSON-RPC error 只承载 parse、method、invalid params 和服务器无法构造上述 envelope 的内部失败，不承载调试领域失败。

动态 tools/call 的固定判定顺序为：HTTP 认证/CIDR/传输限额 → JSON-RPC parse/method 和该 API 的完整 schema 校验 → API-DYN-001 直接执行，或 API-DYN-004/005/010 返回 `CAPABILITY_UNAVAILABLE`，或其余 API 在 `effective_debug_launch=false` 时返回 `DEBUG_DISABLED` → `effective_debug_launch=true` 时才进入 request_id cache/队列、coordinator state、session/generation/pause_epoch、资源预算及目标操作。schema-invalid 必须返回 JSON-RPC `-32602`，不能被领域错误覆盖；`CAPABILITY_UNAVAILABLE` 优先于 `DEBUG_DISABLED`；`DEBUG_DISABLED` 优先于 `INVALID_STATE`、`NOT_FOUND`、`TARGET_MISMATCH`、`STALE_HANDLE`、`REQUEST_ID_REUSE` 和 `LIMIT_EXCEEDED`。在前三类提前返回路径中，除完成反序列化和 schema 校验外，cache/queue/reservation/Dispatcher/文件系统/DbgManager/目标副作用计数均保持不变。

### 3.5 公共类型、工具和事件契约

本节是 `dnspy.debug.v1` 的规范 schema。字段名后的 `?` 表示可选；未标 `?` 的字段必须存在。字符串均为 UTF-8 JSON string；时间为 UTC RFC3339、固定毫秒和 `Z`；未另行限定的 JSON integer 位于 `0..9007199254740991`。PID 为 `1..4294967295`；exit_code 为 `-2147483648..2147483647`。地址使用 `0x` 加 1—16 位小写十六进制；SHA-256 为 64 位小写十六进制；MVID 为小写 `D` 格式 GUID；metadata token 为 `0x` 加 8 位小写十六进制。runtime_family∈{`net48`,`coreclr`}，architecture∈{`x86`,`x64`}。所有 handle、session_id、page_cursor 和 next_page_cursor 是服务端生成、最多 1024 UTF-8 字节的无填充 base64url opaque string，客户端不得解析。事件 envelope 的 cursor 为 integer `1..9007199254740991`；DebugContext.event_cursor、API event 的 after_cursor/next_cursor/earliest_cursor/terminal_cursor 为 integer `0..9007199254740991`，0 表示该 session 尚无事件或从日志起点读取。两类游标不得互换。

### 3.6 状态、转移、重复与并发

`Y` 表示允许，`R` 表示只允许读取已完成/故障 session 的保留事件，`N` 返回 INVALID_STATE。表中 active/paused 的 session/generation/pause_epoch 仍须匹配。本矩阵只在 3.4 固定门禁通过且 `effective_debug_launch=true` 后适用；API-DYN-001 不进入矩阵，API-DYN-004/005/010 不参加状态判定并在任何状态先返回 `CAPABILITY_UNAVAILABLE`，其余 API 在 gate=false 时先返回 `DEBUG_DISABLED`。

| API | idle | starting | running | paused | restarting | stopping | faulted |
|---|---:|---:|---:|---:|---:|---:|---:|
| capabilities/status | Y | Y | Y | Y | Y | Y | Y |
| launch | Y | N | N | N | N | N | N |
| pause | N | N | Y | N | N | N | N |
| continue/step | N | N | N | Y | N | N | N |
| restart | N | N | Y | Y | N | N | N |
| terminate | N | N | Y | Y | N | N | N |
| read-events/wait-event | R | Y | Y | Y | Y | Y | Y |
| set/list/enable/remove breakpoint | N | N | list only | Y | N | N | N |
| list threads/get stack/get locals/expand/read memory/dump | N | N | N | Y | N | N | N |
| list modules | N | N | Y | Y | N | N | N |
| set exception policy | N | Y | Y | Y | N | N | N |

固定转移：

- idle + launch → starting；claim 成功 → running 或 paused；Start 错误、0 个匹配超时 → 写 start_failed/session_end 后 idle；歧义或可检测的外部并发 → faulted。
- running + pause → paused；paused + continue → running。
- paused + step → running；收到同 step_id 的完成/异常 → paused 或 faulted。
- running/paused + restart → restarting → stopping → starting → running/paused；全过程保留原 active session 和唯一 restart reservation，公开状态不得经过 idle。旧 process 移除后的 post-exit/pre-Start 窗口保持 stopping；重新校验/锁定成功且 generation 增加后直接进入 starting。任一中间失败按 start_failed/session_end 或 ownership_lost 进入 idle/faulted 并释放 reservation。
- running/paused + terminate → stopping → 写 session_end → idle。
- 非 restart 的 target exit → 写 process_exited/session_end 后 idle；ownership ambiguity → faulted；faulted 只按 3.2 的观察条件写 recovery/session_end 后自动回 idle，无公共 force-reset。

gate=true 后，统一副作用请求缓存先于 session 查找、start reservation 和命令队列判定；因此 launch 在 session_id 产生前的并发重试也共享同一 in-flight Task 和最终响应。active session 的有副作用命令队列容量 64；第 65 个尚未入队请求返回 LIMIT_EXCEEDED。状态在出队时判定；排队期间发生 state/generation/pause_epoch 变化的请求返回 INVALID_STATE 或 STALE_HANDLE。缓存保留、容量、RFC 8785 参数规范化和 ID 复用严格执行 CON-DYN-013；不得因 session 已终止而提前丢弃。终止事件日志按 3.2 的独立窗口保留，缓存命中不延长事件窗口。所有 page_cursor 绑定查询筛选和 generation；数据变化导致 page_cursor 无法继续时返回 STALE_HANDLE，不静默重新从第一页开始。restart reservation 优先于新 launch 与静态 mutation gate；post-exit/pre-Start 窗口内新 launch 和六个静态写工具均必须为 INVALID_STATE。三个禁用 API 始终先返回 CAPABILITY_UNAVAILABLE，不进入缓存、reservation 或命令队列。

## 7. Fallback 清单

### FB-001：raw runtime bytes 不可用时重构托管 PE

- 依据：REQ-DYN-010、RACC-DYN-007；EVD-API-005 明确 raw bytes 可不可用且 ForceMemory metadata 可用。
- 触发条件：托管模块的 raw bytes 不可用，且 ForceMemory metadata 成功。
- 行为和影响：输出 `reconstructed` PE；manifest 声明非原始字节、重构 API 与布局，不用于原始文件哈希等价判断。
- 退出方式：raw bytes 可用即优先 raw；两者均不可用返回 `CAPABILITY_UNAVAILABLE`，不调用进程外 dump 工具。

### FB-002：不支持 runtime 的工作流交接

- 依据：REQ-DYN-002、REQ-DYN-003、NON-DYN-001、RACC-DYN-010。
- 触发条件：识别为 Unity/Mono、混合模式原生阶段、纯原生，或契约报告 runtime 不支持。
- 行为和影响：不创建/继续伪托管 session；API-DYN-003 以 CAPABILITY_UNAVAILABLE 返回 TYPE-DYN-019 的受限种类、证据和 recommended_workflow；不得仅用 message 承载，不得由三个固定禁用 API返回 details。
- 退出方式：用户切换工作流，或未来经独立审核方案新增 capability；v1 不降级为 GUI 自动化。

除 FB-001、FB-002 外无 fallback。认证失败、端口占用、hash/path/所有权/ArtifactRoot lease 不符、设置验证或提交失败、非法状态、过期句柄、预算超限、缺显式宿主、memory 超范围均直接失败；ApplySnapshot 的旧状态回滚和无法恢复时强制 Stop 是安全失败处理，不是继续主流程的 fallback。不得以 fallback 掩盖主流程错误。

## 10. 审核重点

- SRC-BASE-001 的初始需求如何由 SRC-DEC-001 合法收缩，DEC-DYN-001 是否完整持久化 B1+B2 且实施/审核不依赖对话；OPEN-DYN-001 是否明确关闭且不得复用。
- API-DYN-001..025、TYPE-DYN-001..019、EVT-DYN-001..020、3.4 envelope、三种 MCP protocolVersion wire 矩阵、page/event cursor 分型、launch-only 状态矩阵、RFC 8785 request_id cache 和三类 canonical fixture taxonomy 是否足以逐字段生成 handler 与测试。
- 四种 break_kind 是否只映射到四个 PredefinedBreakKinds，direct/auto/harness 的允许与禁止组合、首状态和 EVT-DYN-010 reason 是否逐格机械闭合。
- ApplySnapshot 是否只持久化单一完整 SettingsSnapshotJson、只按 candidate 运行一次 server transition、失败恢复 old persistence/server/memory 且不产生中间 snapshot。
- TYPE-DYN-019 是否只出现在 API-DYN-003 的不支持目标错误并为四类目标给出唯一 workflow，固定禁用 API 是否始终省略 details。
- ArtifactRoot 从父链到 root 的 reparse/final-path/file-ID lease 是否覆盖创建、写入、清理和验证后替换 barrier。
- ACC-016 是否仅把 depth 作为请求参数并以 fixture 而非不存在参数触发 node/string/response 预算；CON-DYN-006 的认证/CIDR状态、头和空 body 是否逐输入唯一。
- EVT-DYN-020 是否是唯一 session 冻结点，且 restart 中间的进程退出不会误终止 session。
- 五种 launch_mode 的 dnSpy options 映射、HostArguments=`exec` 默认、WindowsEncode 及同进程 harness 合同是否无参数拼接或未声明协议。
- 专用实例确认是否只作为部署前提，capabilities 是否诚实声明条件性 ownership model、attach_supported=false 和残余风险，而未把设置、身份匹配或测试隔离伪装为程序级因果证明。
- API-DYN-004/005/010 是否在三协议版本和所有状态中不广告、固定 CAPABILITY_UNAVAILABLE 且进程枚举、Start、session 与目标控制副作用均为零。
- 3.4 的错误优先级是否在每个 API 和三协议版本逐项执行：schema-invalid 为 `-32602`，API-DYN-001 始终执行，三个禁用 API 为 `CAPABILITY_UNAVAILABLE`，其余 API 在 gate=false 时为 `DEBUG_DISABLED`，且提前返回不进入任何调试副作用层。
- 设置页是否在 active coordinator 下以固定 modal 拒绝并保持整页零持久化，在 idle 时一次提交；冻结开关是否只影响下一 dnSpy 进程。
- restart 是否从 restarting 经 stopping 直接进入 starting、全程保持 active session/restart reservation，并在 post-exit/pre-Start 窗口阻断新 launch 和六个静态写工具，同时三个禁用 API仍返回固定错误。
- locals provider、formatter 和 raw-field API 组合是否真正不执行 getter、DebuggerDisplay、ToString 或表达式。
- `DbgProcess.ReadMemory` 的零填充语义、模块内范围和验收是否与 v6.6.0 契约一致。
- 全端点 token/CIDR/限额、一次显示 token 与只存 verifier 是否可在双 TFM HttpListener 中机械验证。
- 六个现有静态写工具是否在同一 WPF callback 内按 `(coordinator state != idle) OR DbgManager.IsDebugging` 门控且不改变 idle 下语义。
- target/host/working directory/harness 的 Windows handle/file identity lease、CoreCLR module identity 复核和 argv 元素保持是否真正关闭 TOCTOU/命令拼接。
- 动态弱身份模块断点是否必须用当前 module_handle/runtime_handle 消歧且不会误绑相同 MVID/token/offset 的另一模块。
- raw/reconstructed provenance、artifact marker/CreateNew、防覆盖、配额与保守清理是否避免样本目录污染和误删。
- reusable verify 是否使 build/release 在同一 commit 上真正受 net48 x86/x64、CoreCLR apphost x86/x64、CoreCLR dotnet-host x86/x64 的 launch-only 完整功能 E2E、专用实例门禁和三项禁用 API 零副作用验证阻断。
