## 3. 固定范围与非目标

### 3.1 v1 范围

- .NET Framework EXE：启动和附加。
- CoreCLR apphost/EXE：启动和附加。
- 具有运行时配置、可由 `dotnet` 启动的 CoreCLR DLL：使用显式 CoreCLR host。
- 无入口类库：只允许附加到用户明确指定的宿主，或使用用户提供并单独校验哈希的 harness；扩展不得自动生成并执行任意 loader。
- 动态/内存托管模块：允许枚举和有来源标识的导出。

### 3.2 非目标

- Unity/Mono 远程调试、混合模式、内核态和纯原生调试。
- GUI 键鼠模拟、任意命令执行、任意路径文件写入。
- 写内存、SetIP、寄存器或变量赋值、函数求值、调试期 IL patch、force return。
- 对抗所有反调试、保证恶意样本一定可调试，或以 dnSpy 替代 x64dbg。
- 改变现有静态工具的业务语义；本方案只允许为线程隔离、安全门控和统一分派做兼容性重构。

## 4. 固定架构与公共协议

### 4.1 组件边界

固定采用以下调用方向：

```text
McpServer
  -> McpToolRegistry
       -> StaticToolProvider -> WPF Dispatcher
       -> DebugToolProvider
            -> DebugSessionCoordinator -> DbgManager.Dispatcher
                 -> DebugEventBuffer
                 -> DebugBreakpointStore
                 -> DebugHandleStore
                 -> DebugArtifactStore
```

`McpServer` 不直接识别具体静态或调试工具。静态工具保持 WPF Dispatcher 访问规则；调试工具不得经过现有的全局 `InvokeOnUiThread`，必须通过 `DbgManager.Dispatcher.BeginInvoke()` 和一次性 Task completion bridge 取得不可变 DTO。调试事件处理器不得等待 HTTP、WPF、磁盘或另一个 dispatcher。

### 4.2 会话状态

公开状态固定为：`idle`、`starting`、`attaching`、`running`、`paused`、`restarting`、`stopping`、`faulted`。终止、分离或进程退出完成后回到 `idle`，最终原因保留在事件中。

- `generation` 在成功接受 launch、attach、restart 后增加。
- `pause_epoch` 在进入暂停和离开暂停时增加。
- frame/value handle 必须包含 session、generation、pause_epoch 和对象定位信息。
- 任何不匹配都返回 `STALE_HANDLE`，不得自动映射到当前对象。
- 调试对象只在 `DbgManager.Dispatcher` 内解析、读取并关闭，HTTP 层只持有 DTO 和不透明 handle。

### 4.3 工具集合

v1 固定公开下列工具名：

- 能力和状态：`debug_capabilities`、`debug_status`
- 生命周期：`debug_launch`、`debug_list_attachable_processes`、`debug_attach`、`debug_pause`、`debug_continue`、`debug_restart`、`debug_terminate`、`debug_detach`
- 事件：`debug_read_events`、`debug_wait_event`
- 断点：`debug_set_breakpoint`、`debug_list_breakpoints`、`debug_set_breakpoint_enabled`、`debug_remove_breakpoint`
- 检查：`debug_list_threads`、`debug_get_stack`、`debug_step`、`debug_get_locals`、`debug_expand_value`
- 取证：`debug_list_modules`、`debug_read_memory`、`debug_dump_module`
- 异常：`debug_set_exception_policy`

不新增 `debug_evaluate`、`debug_write_memory`、`debug_set_ip`、`debug_set_variable` 或通用 `debug_command`。

### 4.4 统一响应和错误

调试工具的文本兼容响应和可选 `structuredContent` 必须表达同一对象，顶层固定包含：

```json
{
  "schema_version": "dnspy.debug.v1",
  "ok": true,
  "debug_context": {
    "session_id": "opaque",
    "generation": 1,
    "pause_epoch": 2,
    "event_cursor": 10
  },
  "result": {},
  "warnings": []
}
```

领域错误码固定至少包括：`DEBUG_DISABLED`、`UNAUTHORIZED`、`CAPABILITY_UNAVAILABLE`、`INVALID_STATE`、`STALE_HANDLE`、`TARGET_MISMATCH`、`NOT_FOUND`、`LIMIT_EXCEEDED`、`TIMEOUT` 和 `INTERNAL_ERROR`。错误响应必须包含当前状态和可机械执行的恢复条件，不得仅返回自由文本。

## 5. 实施契约

### IMP-001：工具注册与线程域隔离

- 来源：REQ-DYN-001、REQ-DYN-003；EVD-CODE-001、EVD-PROJ-001。
- 允许修改：`McpServer.cs`、`McpTools.cs`；新增 `Tools/IMcpToolProvider.cs`、`Tools/McpToolRegistry.cs`、静态 provider 适配器和 `Debugger/DebuggerDispatcherBridge.cs`。
- 现状：工具 schema、dispatch switch 和 WPF Dispatcher 包裹集中在 `McpTools`。
- 目标行为：服务器只调用 registry；静态 provider 仍在 WPF Dispatcher 执行；调试 provider 只在调试 dispatcher 解析 dnSpy 调试对象，并返回不可变 DTO。
- 前置条件：保持现有 32 个工具名称、schema 和成功响应兼容。
- 依赖与顺序：全方案第一项；IMP-002 至 IMP-010 均依赖本项。
- 允许自行裁决：内部类名、文件拆分粒度、registry 使用字典还是只读映射；不得改变公共工具名、线程边界或 MEF 装配方式。

### IMP-002：能力协商、响应封装与领域错误

- 来源：REQ-DYN-003、REQ-DYN-006。
- 允许修改：`McpProtocol.cs`、`McpServer.cs`、registry；新增调试 DTO、错误和 handle codec。
- 现状：MCP initialize 只报告通用协议能力，工具结果主要是 JSON 文本，`ExecuteTool` 捕获全部异常后无法稳定区分参数和领域错误。
- 目标行为：`debug_capabilities` 始终可用并返回构建版本、dnSpy API 基线、可用 runtime、已启用能力组、安全状态和限制；`tools/list` 除该能力查询工具外只广告已启用工具；统一响应携带 debug context；错误可机械分类。
- 前置条件：继续支持现有三种 MCP protocolVersion 和现有文本客户端。
- 依赖与顺序：依赖 IMP-001，先于所有具体调试工具。
- 允许自行裁决：DTO 的内部 record/class 实现和 JSON converter；公共字段、错误码和兼容文本含义不可变。

### IMP-003：远程传输安全与设置

- 来源：REQ-DYN-011、REQ-DYN-013；EVD-CODE-002、EVD-CODE-003。
- 允许修改：`McpServer.cs`、`McpSettings.cs`、`McpSettingsPage.cs`、`McpSettingsControl.xaml*`；新增认证、限额和网络设置辅助类。
- 现状：无认证、CORS 为 `*`、请求体无上限、非回环 host 原样绑定、端口可漂移，每请求可无限创建后台线程。
- 目标行为：回环为默认；非回环必须启用由加密安全随机数生成器产生的 32 字节 Bearer token；token 仅以 Windows DPAPI `CurrentUser` 密文持久化，UI 只在生成或轮换时显示一次明文；拒绝 `+`、`*`、`0.0.0.0`、`::` 等通配或全接口绑定；非回环请求必须同时匹配设置中的 CIDR 来源白名单，当前 VM 配置只允许 Ubuntu host-only 源地址；远程端口固定且绑定失败即失败；限制请求体、响应体、并发、会话、长轮询和空闲期；默认不返回跨域允许头。
- 前置条件：保留 HttpListener、Legacy SSE、Streamable HTTP 和 plain JSON-RPC；不得引入 Kestrel 或新的 TFM 分支。
- 依赖与顺序：依赖 IMP-001、IMP-002；未通过本项验收前，非回环地址不得广告 debug.control。
- 允许自行裁决：常量时间 token 比较、CIDR 匹配和限流器的内部类拆分及数据结构；不得改变 DPAPI `CurrentUser`、非回环强制认证与来源白名单、固定端口、拒绝通配绑定或各项公开限额。

### IMP-004：调试会话状态、句柄与事件日志

- 来源：REQ-DYN-005、REQ-DYN-006；EVD-API-001。
- 允许修改：新增 `Debugger/DebugSessionCoordinator.cs`、`DebugEventBuffer.cs`、`DebugHandleStore.cs`、事件 DTO；必要时修改调试 provider。
- 现状：无调试状态、事件或调试对象生命周期模型。
- 目标行为：实现第 4.2 节状态机、generation、pause_epoch、不透明句柄；订阅 `DbgManager` 事件并写入有界环形日志；提供 read/wait，报告 `events_lost` 和最早可读 cursor。
- 前置条件：服务通过 `IDbgManagerStartListener` 在首次调试前订阅；默认最多 4096 条且同时受总字节上限控制；wait 超时上限 30 秒。
- 依赖与顺序：依赖 IMP-001 至 IMP-003，先于 IMP-005 至 IMP-009。
- 允许自行裁决：环形缓冲内部容器和唤醒原语；状态名、游标单调性、上限和失效规则不可变。

### IMP-005：启动、附加和生命周期控制

- 来源：REQ-DYN-002、REQ-DYN-004、REQ-DYN-011。
- 允许修改：新增 lifecycle 工具 handler、启动目标验证器和 attach nonce 存储；引用 Debugger、Debugger.DotNet、Debugger.DotNet.CorDebug 项目。
- 现状：扩展没有调试契约引用或进程控制能力。
- 目标行为：支持 netfx/CoreCLR 自动识别与显式覆盖、入口/模块构造器/不暂停三种 break kind；launch 必须校验 allowed root 和 expected SHA-256；attach 只能使用枚举返回、有效期 30 秒且绑定 PID、进程启动时间与 runtime identity 的一次性 nonce，消费后立即失效；所有操作按状态机拒绝非法调用。
- 前置条件：无入口 DLL 必须要求显式宿主或 attach；宿主/harness 也必须受路径和哈希约束。
- 依赖与顺序：依赖 IMP-004；完成后才能实现断点和检查能力。
- 允许自行裁决：runtime 检测器内部组合方式；检测失败必须返回明确错误并要求显式 runtime，不得静默尝试执行其他宿主。

### IMP-006：强身份断点与异常暂停策略

- 来源：REQ-DYN-007、REQ-DYN-011；EVD-API-001。
- 允许修改：新增 `DebugBreakpointStore`、模块身份解析器和断点/异常工具 handler。
- 现状：无运行时断点；现有静态 method token 只定位 dnlib 数据库。
- 目标行为：磁盘模块以 SHA-256、MVID、MethodDef token、IL offset 验证后映射到 dnSpy `ModuleId`；动态模块使用 runtime identity 和 MVID 并标注较弱身份；断点只有收到实际 bound 状态后才报告 `bound=true`；仅修改 MCP 自己创建的断点。异常策略由当前 debug session 的事件处理器决定是否暂停，不写入用户全局异常设置。
- 前置条件：offset 必须是该方法的真实指令边界；condition、trace expression 和命中时函数求值不进入 v1。
- 依赖与顺序：依赖 IMP-004、IMP-005。
- 允许自行裁决：所有权元数据存入 DbgObject data 或独立映射；不得提供无差别 clear-all。

### IMP-007：线程、调用栈和步进

- 来源：REQ-DYN-006、REQ-DYN-008；EVD-API-001。
- 允许修改：新增 thread/stack/step handlers 和格式化 DTO。
- 现状：无运行时线程或 frame API。
- 目标行为：分页枚举线程；按 thread handle 读取有限数量 frame；返回 module、token、IL offset、native IP 和格式化名称；暂停时支持 step into/over/out，并用事件报告完成或错误。
- 前置条件：格式化 frame 不读取参数值；walker、frame 和 stepper 必须按 dnSpy 生命周期关闭。
- 依赖与顺序：依赖 IMP-004、IMP-005；IMP-008 依赖本项的 frame 定位。
- 允许自行裁决：frame DTO 的额外诊断字段；不得持有跨 continue 的 frame 实例。

### IMP-008：无副作用局部变量与字段展开

- 来源：REQ-DYN-009、REQ-DYN-011；EVD-API-001。
- 允许修改：新增 locals/value handlers、安全 formatter 和读取预算组件。
- 现状：无调试取值能力。
- 目标行为：读取参数、locals 和 `this`；固定启用 `NoFuncEval`、`NoSideEffects` 和 RawView；格式化不启用 FuncEval/ToString，并禁用 DebuggerDisplay；对象只展开原始字段；每次请求限制深度、节点、字符串和总字节。
- 前置条件：只允许 paused 状态和当前 pause_epoch；任何潜在函数调用返回安全拒绝或不可用，不得降级执行。
- 依赖与顺序：依赖 IMP-007。
- 允许自行裁决：默认展示十六进制或十进制等纯格式细节；禁止函数求值和 getter 的语义不可改变。

### IMP-009：模块、只读内存与临时产物

- 来源：REQ-DYN-010、REQ-DYN-011；EVD-API-001。

### ACC-024：不支持范围明确失败并交接

- 对应实施：IMP-002、IMP-005、IMP-011。
- 需求来源：REQ-DYN-002、REQ-DYN-003。
- 前置条件和输入：Unity/Mono、混合模式和纯原生目标各一份识别 fixture。
- 命令或操作：调用 capabilities 和 launch/attach 探测。
- 精确结果：返回 `CAPABILITY_UNAVAILABLE`，说明识别到的目标种类和建议工作流；混合/原生目标建议切换 PE/x64dbg；不创建调试 session、不启动进程。
- 证据与边界：响应和进程列表；假成功、错误启动或将不支持目标归类为 CoreCLR/netfx 即失败。

## 7. Fallback 清单

### FB-001：原始运行时模块字节不可用时重构托管 PE

- 依据：REQ-DYN-010；EVD-API-001 中 `IDbgDotNetRuntime.GetRawModuleBytes()` 允许返回不可用，`DbgMetadataService` 可从内存元数据加载。
- 触发条件：目标为托管模块、调试器返回 raw module bytes 不可用，且 ForceMemory 元数据加载成功。
- 行为和影响：允许输出 `reconstructed` 托管 PE；manifest 必须声明非原始字节、重构工具/API 和布局，不能把它用于原始文件哈希等价判断。
- 退出方式：一旦 raw bytes 可用即优先 raw；若两种方式均不可用则返回 `CAPABILITY_UNAVAILABLE`，不得再尝试进程外转储工具。

### FB-002：非托管或不支持运行时的工作流交接

- 依据：REQ-DYN-002、REQ-DYN-003。
- 触发条件：识别为 Unity/Mono、混合模式的原生阶段、纯原生模块，或 dnSpy 调试契约报告不支持该 runtime。
- 行为和影响：不创建或继续伪托管 session；返回目标种类、证据和 PE/x64dbg 或后续 Mono 能力的交接提示。
- 退出方式：用户切换到相应工作流，或未来经独立审核方案新增对应 capability；不得在 v1 内自动降级为 GUI 自动化。

除 FB-001、FB-002 外无其他 fallback。认证失败、固定端口占用、目标哈希不符、非法状态、句柄过期、预算超限、无入口 DLL 缺少显式宿主等均直接失败，不进入替代路径。

## 8. 实施顺序和发布边界

固定顺序为：IMP-001 → IMP-002 → IMP-003 → IMP-004 → IMP-005 → IMP-006/IMP-007/IMP-009 → IMP-008 → IMP-010 → IMP-011。

IMP-006、IMP-007、IMP-009 在共同依赖完成后可以分别编码，但不得在 IMP-010 安全门控和 IMP-011 全量验收完成前发布。任何实现拆分为多个 PR 时，每个 PR 都必须维持构建通过和现有静态工具兼容；调试工具可以受 capability flag 隐藏，不能以半实现状态对外广告。

## 10. 审核重点

- v1 仅覆盖 .NET Framework/CoreCLR 是否与实际恶意样本范围一致，Unity/Mono 和混合模式边界是否足够明确。
- Tool Registry 重构是否严格保留现有 32 个静态工具兼容性，并真正隔离 WPF 与调试 dispatcher。
- 非回环认证、固定端口、来源限制和资源上限是否能在 HttpListener 双 TFM 架构内机械验收。
- 强模块身份到 dnSpy `ModuleId` 的映射、动态模块较弱身份和 bound 验证是否会产生误命中。
- locals/字段展开的 API 组合是否确实不会调用 getter、DebuggerDisplay、ToString 或任何目标代码。
- 活动调试期间阻断静态 mutation 是否覆盖所有已有和后续新增写工具。
- raw 与 reconstructed 模块产物的 provenance 是否足以避免取证结论混淆。
- net48/CoreCLR 动态 E2E 是否真正进入 build/release 门禁，而不是只存在本地脚本。
