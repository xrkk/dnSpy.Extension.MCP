## 4. 审计意见

### AUD-017：runtime_matrix 对当前 dnSpy 实例报告不可实际启动的架构

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-002、REQ-DYN-003；CON-DYN-010；RACC-DYN-009；EVD-API-010；TYPE-DYN-010；API-DYN-001；IMP-002、IMP-011；ACC-002、ACC-022、ACC-029。
- 证据：
  1. EVD-API-010 和 CON-DYN-010 明确 CorDebug 只能调试与当前 dnSpy OS 进程同位数目标；相反 architecture 必须在 Start 前返回 CAPABILITY_UNAVAILABLE。
  2. TYPE-DYN-010 和 API-DYN-001 却固定返回 x86/x64 共 6 项，且每项都为 `launch=true`；对象没有当前 `host_architecture`、`available` 或 unavailable reason。
  3. ACC-002/022/029 又要求六项一律 launch=true，同时要求每个单独的 x86 或 x64 dnSpy 进程拒绝相反架构。故同一 x64 实例会对 x86 声称 launch=true，实际调用必然失败，x86 实例反之亦然。
- 风险：客户端不能从 capabilities 得到 REQ-DYN-003 要求的真实当前能力，必须依赖部署外知识猜测 architecture；两个实现也可把 runtime_matrix 解释成“产品总矩阵”或“实例可用矩阵”。
- 影响：能力协商、直接编码、交接和六项 E2E 的判定语义未闭合。
- 建议：区分产品支持矩阵与当前实例可用矩阵；至少固定当前 dnSpy `host_architecture`，并使异位数 entry 省略、`launch=false` 或带唯一 unavailable 状态。同步 TYPE-DYN-010、API-DYN-001、ACC-002/022/029，逐个 x86/x64 host 断言其实际可用项。

### AUD-018：ValueNode 的“同一响应父节点”与 breadth-first 跨页无重漏要求不可同时满足

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-006、REQ-DYN-009；RACC-DYN-006、RACC-DYN-011；EVD-API-009；TYPE-DYN-002/003/007；API-DYN-021；IMP-008；ACC-015、ACC-016、ACC-028。
- 证据：
  1. TYPE-DYN-007 要求 expand 的更深节点指向“同一响应中更早出现”的父节点。
  2. API-DYN-021 又要求按 parent 原始顺序做确定性 breadth-first 遍历，PageResult 每页最多 page_size 项，后续页只续读同一 snapshot。
  3. ACC-015 固定 `depth=2,page_size=2` 且分页无重漏；ACC-016 同样要求 breadth-first 和无重漏。
  4. 反例可机械构造：根的直接子节点依次 A、B、C，A 有子节点 A1；breadth-first 序列为 A、B、C、A1。page_size=2 时 A1 位于第二页，而其父 A 只在第一页。重复 A 会违反无重漏，不重复则违反“同一响应中父节点先出现”。
- 风险：合法树在第二层开始即可能无可生成的合规 wire；schema、handler 和 fixture 必须选择不同解释。
- 影响：公共类型、功能闭环、分页协议和 ACC-015/016 的可执行性未成立。
- 建议：唯一固定 parent 作用域，例如允许 `parent_value_handle` 引用同一 immutable snapshot 的先前页，并明确客户端可跨页解析；或设计不重复 item 的独立 parent 描述。增加 page boundary 恰好把 parent/child 分开的 fixture。

### AUD-019：最终页后的 value_handle 生命周期未闭合，形成“不可展开”或“资源上限可绕过”的二选一

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-006、REQ-DYN-009、REQ-DYN-011；CON-DYN-009；RACC-DYN-006、RACC-DYN-011；TYPE-DYN-007、TYPE-DYN-017；API-DYN-020/021；IMP-008；ACC-004、ACC-015、ACC-016、ACC-028。
- 证据：
  1. API-DYN-020/021 和 CON-DYN-009 要求无 next_page_cursor 的最终页返回后立即销毁 snapshot并释放每 pause_epoch 的 2-slot 容量。
  2. API-DYN-021 必须使用 API-DYN-020/021 返回的 `value_handle` 继续展开；这些 handle 仅明确在 continue/restart 后失效。方案没有规定 snapshot 销毁是否同时关闭/失效其 value handles。
  3. 若最终页销毁 handle，则只有一页的 locals 返回时 handle 立即失效，客户端拿到结果后无法 expand；若 handle 保留，则客户端可反复创建并读完 snapshot、释放 2-slot，同时累积每次最多 1024 个 pause-bound value/debugger 对象，现有固定限额没有总 handle/node 上限。
  4. TYPE-DYN-007 还未固定 `has_children=true` 时必须存在可用 `value_handle`；ACC-016 只验证销毁后的 cursor 和 continue 后的 handle，没有验证最终页后展开、handle 关闭计数或重复 snapshot 周期的总资源上界。
- 风险：一种实现破坏正常 expand 主流程，另一种实现允许在单次暂停中绕过 snapshot 上限造成内存/调试对象资源增长。
- 影响：正常、边界和资源闭环、句柄契约及验收边界未成立。
- 建议：固定 snapshot 与 value_handle 的所有权/关闭规则、`has_children` 的条件字段和每 pause_epoch 的总 handle/node 预算；验收须覆盖一页 locals 的最终页后 expand、最终页后旧 cursor、重复创建/消费 snapshot 的资源上界、continue 时准确关闭计数。

### AUD-020：调试线程域的绝对约束与 launch 的 WPF callback 例外互相冲突

- 严重度：阻断性。
- 来源或方案 ID：REQ-DYN-001、REQ-DYN-004；CON-DYN-003、CON-DYN-012；RACC-DYN-001、RACC-DYN-004；方案 3.2；IMP-001、IMP-004、IMP-005；ACC-001、ACC-034；EVD-API-007。
- 代码证据：dnSpy v6.6.0 `DbgManagerImpl.cs` blob `841ba23fa194df7156878542b167b01edb825f55` 的 `Start()` 克隆 options 后通过 `DbgThread(...)` 异步投递 `Start_DbgThread`；调用入口自身可从 UI/WPF 线程进入。
- 已证实问题：
  1. CON-DYN-003 与 IMP-001 都规定调试 provider“只经 DbgManager.Dispatcher”访问。
  2. 3.2 和 CON-DYN-012 又把 start claim、`DbgManager.IsDebugging` 预检和 `DbgManager.Start` 固定在一个 WPF Dispatcher callback。
  3. ACC-001 只接受调试 probe 为 DbgManager dispatcher，没有定义 launch 三操作是允许的 WPF 特例，亦没有分别核对 WPF 外层与 DbgManager 内层投递。
- 风险：实施者按 CON-DYN-003 会破坏方案用于缩小 UI Start 竞争窗口的 WPF 串行规则；按 3.2 则违反线程域验收。两种实现均可据正文自证。
- 影响：架构、线程安全、所有权关键路径、实施顺序和 ACC-001 无法机械闭合。
- 建议：在 CON-DYN-003/IMP-001 明确列出且仅列出 launch reservation/precheck/Start 的 WPF 例外，固定进入/退出哪个 dispatcher、哪些对象可在各线程读取；ACC-001/034 分别断言 WPF 外层 callback 与 DbgManager dispatcher 上的事件/对象解析。

### AUD-021：ApplySnapshot 的回滚持久化自身失败时可能在下次启动激活未成功应用的 candidate

- 严重度：阻断性安全与数据一致性问题。
- 来源或方案 ID：REQ-DYN-003、REQ-DYN-011、REQ-DYN-013、REQ-DYN-015；CON-DYN-006、CON-DYN-014；RACC-DYN-003、RACC-DYN-012；EVD-CODE-003；IMP-003；ACC-003、ACC-023、ACC-036。
- 代码/方案证据：
  1. 当前 `McpSettings.cs` blob `fdc31d531e9abb21800c3a456e3a9f53032a42f1` 只有逐属性持久化；v8 因而新增单值事务。
  2. CON-DYN-014 固定顺序为先持久化 candidate JSON，再执行 server transition；transition 失败后再把 old JSON 持久化一次、恢复 old server/memory。
  3. CON-DYN-014 和 ACC-036 定义了初次 persistence failure、server transition failure 和 rollback-listen failure，却没有定义“candidate 已持久化、transition 失败、随后 old JSON 回写也失败”的状态、错误、启动恢复或证据。
  4. 在该组合下，当前进程的 memory/server 可以保持 old 或 stopped，但持久对象仍是 candidate；下一次进程会把此前失败的远程 Host/CIDR/verifier/enablement candidate 当作当前设置加载。
- 风险：UI 显示应用失败后，重启仍可能启用未成功提交的监听或调试门禁配置，破坏失败可见性和远程安全预期。
- 影响：设置事务、数据一致性、安全回滚、用户可见结果和现实故障闭环未成立。
- 建议：固定可证明的 durable commit/recovery 协议，或在加载时能区分 staged/committed snapshot并 fail closed；ACC-036 增加“candidate persistence 成功→transition 失败→old persistence 回写失败→重启”的故障注入，逐项断言持久对象、监听、内存和用户提示。

### AUD-022：标准 JSON Schema 2020-12 不能按当前文字直接表达 UTF-8 字节限额

- 严重度：高。
- 来源或方案 ID：REQ-DYN-003、REQ-DYN-006、REQ-DYN-011；CON-DYN-009、CON-DYN-013；RACC-DYN-002、RACC-DYN-011；方案 3.4—3.5；TYPE-DYN-011/019；API-DYN-004/024；IMP-002、IMP-008；ACC-016、ACC-024、ACC-028；EVD-SCHEMA-001。
- 规范证据：JSON Schema Draft 2020-12 Validation 6.3.1 定义 `maxLength` 的 length 为 RFC 8259 字符数；它不是 UTF-8 序列化字节数。
- 已证实问题：方案要求单个 warning 1024 UTF-8 字节、name_filter 256 UTF-8 字节、UnsupportedTargetDetails.evidence.value 1024 UTF-8 字节、relative_name 128 UTF-8 字节等，同时要求单个 Draft 2020-12 schema“逐字表达”全部 API/TYPE/EVT，并把所有 schema-invalid 统一判为 `-32602`。方案没有声明自定义 vocabulary/keyword，也没有把标准 schema validation 与 UTF-8 byte validation 的固定顺序和错误证据分开。
- 风险：对多字节 Unicode 输入，标准 validator、按字符实现和按 UTF-8 字节实现会给出不同结果；contract fixture 不能单靠所指定 schema 冻结 wire。
- 影响：公共输入边界、两个独立实现的一致性和 ACC-028 的 schema validator 证据不完整。
- 建议：明确采用受版本控制的自定义 JSON Schema vocabulary/keyword，或把标准结构 schema 与确定性的 UTF-8 byte validator 分成两个命名阶段并固定都在副作用前返回 `-32602`；为每个字节字段加入 ASCII、BMP、非 BMP 的边界 fixture。
