### AUD-027：暂停请求与通用 Break 观察仍无因果相关性

- 本轮结论：复开；最小闭合条件未满足。
- 首次提出轮次：第 7 轮全面复审。
- 来源层级：当前方案实施/公共响应契约；REQ-DYN-004/005/008、CON-DYN-003/004/013、RACC-DYN-002/004/005。
- 复开来源分类：`本轮变更引入`。v14 新增的 `request_effect=caused_pause` 仍以“当前 pause record 已 issued”替代不存在的上游关联 token。
- 风险：高。会把另一个请求或外部原因造成的暂停归因给当前 P2，并向客户端返回虚假的 caused_pause。
- 方案位置：3.2 的 Break 候选和 pause record 结算规则；API-DYN-006；EVT-DYN-010；IMP-004/005；ACC-007/008/028。
- 代码证据：dnSpyEx v6.6.0 的 `DbgManagerImpl` 在写入 runtime BreakInfos 后发出 ProcessPaused，但 `DbgMessageBreakEventArgs` 和 ProcessPaused 都没有 request_id/control_epoch。`DbgMessageBreakEventArgs` 对 Break 的契约还覆盖“用户暂停或其他程序因其他原因暂停”，不能标识某次 MCP Break 调用。
- 确定性反例：P1 已 issued，30 秒超时并封口；P1 的 Break 影响迟到。随后 P2 issued。此时到达的唯一 Break/ProcessPaused 观察与“P2 导致暂停”在 session、generation、owned identity、BreakInfos 和事件字段上完全相同。v14 按当前规则把 P2 返回为 `reason=manual, request_effect=caused_pause`，但该暂停可能由 P1 导致；现有 API 无法区分。
- 影响：API-DYN-006 结果不真实；ACC-007/008 的 P1→P2 cause collision 不能机械判定；第 7 轮关于状态对账、旧响应封口的通过部分仍可继承，但“P2 因果”子项不能通过。
- 受影响的既有通过项：功能闭环、可交接实施性、决策闭合、验收契约；具体为 IMP-004/005、ACC-007/008/028 及 API-DYN-006/EVT-DYN-010 的因果字段。
- 最小闭合条件：不得仅凭“当前 record issued + Break”声明 caused_pause。在 stock API 无关联 token 的前提下，将这类观察固定为实际 stop reason 但 `request_effect=state_satisfied`，或删除因果承诺；ACC-007/008/028 必须加入“P1 late Break 在 P2 issued 后到达”，并断言唯一响应、事件、cache/lane 结算和旧响应不改写。
- 所需复审证据：更新后的 3.2/API-DYN-006/ACC-007/008/028 精确 diff；无 token adapter trace；上述反例的 response/event/cache/callback/lane 时间线。

### AUD-029：2 秒取消结算与 CancelIoEx 最终完成契约矛盾

- 本轮结论：复开；最小闭合条件未满足。
- 首次提出轮次：第 7 轮全面复审。
- 来源层级：当前方案资源、数据一致性和控制可用性契约；REQ-DYN-004/010/014、CON-DYN-008/009/013、RACC-DYN-004/007/009。
- 复开来源分类：`本轮变更引入`。v14 新增的 2000 ms 硬结算保证没有覆盖 CancelIoEx 后仍 pending 超过 grace 的合法完成态。
- 风险：中。实现若在 2 秒释放 record/buffer/handle 会违反 overlapped I/O 生命周期并可能破坏文件；若等待最终完成则违反 control/store/general/cache 的 2 秒结算保证。
- 方案位置：3.2 的 control cancellation；CON-DYN-009/013；API-DYN-001/024；IMP-004/009/011；ACC-019/022/028。
- 一手证据：Microsoft Learn CancelIoEx 明确只把请求标为取消，不等待完成；目标操作可能正常完成、被取消或以其他错误完成，调用方必须等待并检查最终 completion，且 completion 前不能安全释放或复用 OVERLAPPED 及相关资源。稳定 URL：`https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex`。
- 确定性反例：CreateNew 后一个 overlapped 1 MiB chunk 仍 pending。control 请求调用 CancelIoEx，2 秒后仍无 completion，随后在第 3 秒正常完成。v14 同时要求 2 秒内结算 artifact record/store lock/general slot/cache、记录 aborted_owned 的精确实际 length/SHA，并在最终 completion 后阻止继续写。2 秒时实际完成长度尚未知；释放生命周期资源不安全，保留它们又不满足硬结算。
- 影响：control preemption 的用户可见 TIMEOUT/INVALID_STATE、aborted_owned ledger、buffer/handle 生命周期和发布门禁不唯一；ACC-019 的三个 completion 分支没有“grace 后仍 pending”分支，ACC-022 的真实 volume 2 秒成功不能证明所有支持 volume 的取消上界。
- 受影响的既有通过项：正确性、数据一致性、资源、现实落地、功能闭环、可交接实施性、决策闭合和验收契约；具体为 IMP-004/009/011 与 ACC-019/022/028。
- 最小闭合条件：把 2000 ms 明确为 control 等待 grace 而不是 I/O 最终结算上界；若 grace 后仍 pending，control 返回唯一结果，artifact 进入显式 `canceling` 并继续持有 OVERLAPPED/buffer/file handle 和完整性资源直到最终 completion，再按正常完成/ERROR_OPERATION_ABORTED/其他错误结算 ledger。定义此期间后续控制、store admission、cache/general slot的唯一行为；或提供具有一手证据的同步硬取消机制，CancelIoEx 不能作为该证明。
- 所需复审证据：CON-DYN-009/013、3.2、API-DYN-024、ACC-019/022/028 的精确 diff；注入“超过 2000 ms 仍 pending”及随后三类最终 completion，逐项断言 response、file length/SHA、ledger、OVERLAPPED/buffer/handle lifetime、store/cache/lane 释放和后续控制。

- 证据与反例：API-DYN-006 明列七值 `manual, process, entry, breakpoint, exception, step, unknown`；ACC-028 却要求“API-DYN-006 schema 含八值 reason 与 request_effect”。EVT-DYN-010 另有八值，其中多出的 `module_cctor_or_entry` 是 initial launch pause reason，不是 API-DYN-006 当前枚举。一个 generator 采用 API 表会使 ACC-028 的基数断言失败，采用 ACC 文字则会无依据扩张 API-DYN-006。
- 影响：API-DYN-006 schema fixture 和 ACC-028 无法同时机械通过；影响条目 ID 完整性之外的验收契约与可交接实施性。
- 受影响的既有通过项：IMP-002、API-DYN-006、EVT-DYN-010 与 ACC-028 的 schema 一致性；其他 API/TYPE/EVT 枚举不受影响。
- 最小闭合条件：保持 API-DYN-006 当前七值语义，把 ACC-028 改为七值并另行明确校验 EVT-DYN-010 的八值；同步检查 schema、canonical fixture 和精确预期，不新增没有来源的 API reason。
- 所需复审证据：API-DYN-006/EVT-DYN-010/ACC-028 的精确 diff，以及三种 protocolVersion 下七值 result schema与八值 event schema的一致性报告。

### 3.5 审核循环熔断判定

AUD-027 和 AUD-029 均只经过一次作者处理，本轮是第一次以同一 ID 复开；未达到“同一 AUD 经两次处理仍以同一根因复开”的熔断条件。AUD-028 已关闭，AUD-030 首次提出。因此本轮不触发审核循环熔断。
