- 因变更回溯重新执行本阶段时, 更新回溯前已写入的同一份需求提炼文档, 不得新建另一个编号文档. 文档正式升版并记录本次变更, ID 按下述规则保持稳定.
- 正式化和升版均保留 `会谈输入` 中已经确定的访谈目标和固定文档写入目录, 不用其他内容覆盖. 旧文档缺少任一值时, 只使用入口按兼容规则恢复并传入的值.
- 正式化和升版均保留并更新 `Grill-Me 工作流状态` 章节; 该章节只承载编排状态, 不替代正式需求、对话记录或累计有效结论.
- 为每个正式需求目标分配稳定唯一的 `REQ-001` 等 ID, 为每个固定约束分配 `CON-001` 等 ID, 为每个非目标或明确不引入项分配 `NON-001` 等 ID, 为每个需求级可验收结果分配 `RACC-001` 等 ID.
- 每个 `RACC-xxx` 必须引用对应的 `REQ-xxx` 或 `CON-xxx`; 每个 `REQ-xxx` 必须至少有一个可验收落点. 同一文档内 ID 不得重复.
- ID 跨版本稳定. 后续正式升版不得重编号或复用; 新条目在同类最大编号后递增, 删除条目在版本变更记录中保留原 ID 和原因.
- 原子化只改变内容的拆分粒度和可引用性, 不减少已确认的信息. 术语、标签和技术名称只能命名机制, 必须同时写明其完整行为契约.
- 任何会影响实现、验收、职责、顺序、状态、生命周期、数据归属、接口、异常行为或非目标的当前有效结论都必须有明确的持久化位置. 已确认的算法或机制至少保留参与者及职责、输入输出、触发条件和执行顺序、状态归属与转换、创建到释放的生命周期、不变量、边界与失败行为、终止或释放条件和可观察验收结果.
- 记录需求目标, 范围, 非目标, 约束和可验收结果.
- 记录访谈中明确保留, 简化和删除的内容, 包括简化或删除的代价.
- 单独列出 "明确不引入的机制", 后续方案不得默认重新加入.
- 记录仍然存在的未知项和风险并逐项分类: 会改变需求方向、范围、规范性约束或非目标的为 `方向阻断型`, 未经用户确认不得完成本阶段; 会使 RACC 无法形成可判定证据的为 `验收阻断型`, 不得进入总纲审核; 只影响 Pxx 数量、顺序或职责的为 `方案组织型`, 交给后续组织评估并记录关闭条件; 不改变上述语义的为 `纯实现型`, 才允许交给子方案或实施者. 每项写责任层级、关闭所需证据和当前状态, 不得笼统写成后续方案解决.
- 不得把已经否决的建议, 需求范围外的功能或访谈中没有确认的推测写成正式需求.
- 为 `累计有效结论` 中的每项结论记录对应对话记录序号、正式章节和适用的 `REQ/CON/NON/RACC` ID; 每个正式条目也必须能回溯到对话记录、已确认的固定背景或明确证据. 简化和删除只能来自用户已确认的取舍及代价, 不得作为整理时的编辑性压缩.
- 对仍在生效的方向性选择, 正式条目除结论外还要保留适用前提、主要取舍和重新裁决触发条件, 并双向引用原对话记录. 后续实施遇到未决点时, 只有当前事实符合该选择的适用前提且未命中重新裁决条件, 才能沿已选方向继续; 否则不得从术语、推荐项或被否决选项自行类推, 必须回到需求确认.
- 正式化时只为原对话记录增加状态和映射, 不压缩、改写或删除其中的问题、用户原始回答和采用原因. 正式化后逐条重读累计结论和对话记录, 检查遗漏、弱化、泛化、错误合并和无依据改写并当场修正. 完成标志是当前有效结论全部有完整明确落点、无法解释的语义损失为零、提示词泄漏和未决候选均为零, 且第三方只读正式需求章节就能重建已确认的行为而无需猜测术语含义.
