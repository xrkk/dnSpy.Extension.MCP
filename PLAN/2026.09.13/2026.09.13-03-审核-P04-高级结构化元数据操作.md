## 6. 审核意见（AUD，跨轮稳定 ID）

### AUD-001（中）IMP-005 将 marshal 结构化表示误归源于生产 codec `EditStructuredSignatureCodec`

- 来源层：子方案 §3 IMP-005／§2 盘点 Marshal 行。
- 反例：`Editing/EditStructuredSignatureCodec.cs`（135 行，指纹见 §3）仅处理类型/调用签名（TypeNode/CallNode），无任何 marshal 编码路径（全文件与 `Editing/` 生产代码 grep "marshal" 仅命中 `EditFingerprint.cs` 指纹串接与互操作 `Marshal.GetLastWin32Error`）。P03 轮次 28 验证的 8 类 marshal 形状（实施记录 §32：simple/raw/fixed string/safe array/fixed array/array/custom/interface，`samples=14 classes=8` 双架构退出 0）位于 **test-only** harness 类 `tests/edit/P03StoreHarness/MarshalSnapshotCandidate.cs`/`MarshalSnapshotProbe.cs`，非生产代码。
- 风险：实现者按"同源复用既有表示"预期找不到生产路径；生产 marshal 编解码实为新增代码，其往返保真与重载断言不因 harness 验证自动成立；工作量与复用声明失真。
- 影响：IMP-005、IMP-009（schema 冻结枚举来源）、ACC-004 第 6 类证据口径。受影响既有通过项：无（P03 §32 证据本身有效）。
- 最小闭合条件：修正 IMP-005 事实陈述，指明 8 类形状来源为 P03 轮次 28 的 test-only 候选类，并要求将其提升为生产 codec（含往返与重载断言纳入 ACC-004 第 6 类）或等价新实现。
- 复审证据预期：修订后的 IMP-005 文本与新增生产 codec 落点声明。

### AUD-002（中）CON-017 的"风险回报"切片未落点；§5 "自动成立"论断与机制事实不符

- 来源层：子方案 §5 门禁自注、§3 各 IMP、§4 ACC-004；总纲 OUT-004 独立验收目标（"保存重载、检查点恢复、风险回报"）、§9.2 OUT-004 行、§13.8；需求 CON-017。
- 反例：风险发射是逐 kind 硬编码——`EditOperationRegistry.cs` 各分支自行 `Risk("signature_change")/Risk("public_delete")/Risk("body_change")/Risk("eh_change")`，`operation-lowering.json` 的 `delete_policy` 逐 kind 写明 `public_unreferenced_is_risk`；协调器仅汇总 `outcome.Risks`（`EditTransactionCoordinator.cs:228/418/424`）。新 kind（attribute_add/remove、security_add/remove）与新字段（pinvoke/marshal/layout/initial_data/constraints/overrides）的风险分类在子方案任何 IMP 中均未定义，ACC-004 亦无 risk_ids/confirmed_risk_ids 断言。例：对 public 类型挂 `[SecurityCritical]`/`[Obsolete]` 类属性属行为性修改，若无分支级分类则 review 零风险项，CON-017"提交后的回报必须显式列出确认内容和受影响引用"对新操作静默落空。
- 风险：高风险编辑无风险回报，违反 CON-017 与总纲 §13.8；P09 汇总时无法回补。
- 影响：ACC-004 的"通过/失败边界"未覆盖 OUT-004 验收目标之一；受影响既有通过项：P02 ACC-010 机制本身不受影响。
- 最小闭合条件：在相关 IMP（或新增专项条目）为每个新 kind/字段冻结风险分类（或附理由显式声明"无非结构性风险"），并在 ACC-004 成功样本中增加可机械断言的风险回报观察点（review 列出 risk_ids、commit 回报列出 confirmed_risk_ids）。
- 复审证据预期：修订后的 IMP/ACC-004 文本。

### AUD-003（中）IMP-006 的 `exact_import` 旗标无 dnlib 4.5.0 事实来源；未声明排除的 ImplMap 旗标组

### AUD-004（中低）IMP-007 SecurityAction 域标注不精确，且 XML→Blob Spike 是方案唯一未闭合事实依赖、先于冻结

### AUD-005（低）IMP-004 pack 合法集标注"dnlib 写入器事实"未获本地证据支持；API 名与 dnlib 实名有偏差

- 来源层：子方案 §3 IMP-004、§3 序言 API 清单。
- 反例：dnlib 4.5.0 中 `ClassLayout` 暴露数值属性 `PackingSize`/`ClassSize`（dnlib.xml），无 PackingSize 合法集枚举，dnlib.dll 亦无 `Pack1..Pack128` 类成员；所引"dnlib 写入器事实"在本地可核证据（dnlib.xml＋二进制）中不存在。集合 {0,1,2,4,8,16,32,64,128} 本身与 ECMA-335 ClassLayout PackingSize 合法值一致，方向无误但事实源应改为标准或附 dnlib 写入器源证据。另：方案写 "PackSize"，dnlib 属性为 `PackingSize`；`DeclSecurity(Action,Blob,Parent)` 中 `GetBlob` 存在而 "Parent" 在 dnlib.xml 无对应属性（父子关系经 owner 集合表达）。
- 风险：实现者按错误成员名/事实源绑定 API 或复验时找不到出处。
- 影响：IMP-004、IMP-009 常量表冻结。
- 最小闭合条件：改引 ECMA-335（或补 dnlib 写入器源证据）为 pack 集事实源；API 清单更正为 `ClassLayout.PackingSize/ClassSize` 并更正 DeclSecurity 归属表述。
- 复审证据预期：修订后的常量表与 API 清单。

### AUD-009（低）IMP-008 initial_data 上限与操作字节预算不相容，声明上限不可达

- 来源层：子方案 §3 IMP-008；代码事实 `EditContracts.cs:15/23`（`MaxNormalizedOperationBytes = MaxResourceBytes = 8 MiB`）、`EditTransactionCoordinator.cs:218/413`（全事务规范化操作累计字节 ≤ 8 MiB）。
- 反例：`initial_data` 以 base64 内嵌操作 JSON，8 MiB 原始字节编码后约 11 MiB，必然超 8 MiB 累计操作预算；按"上限＝MaxResourceBytes 同源"声明的上限永不可达（实际可达上限约 6 MiB 原始字节且随事务内其他操作递减）。ACC-004 第 9 类非法样本"超限字节"需明确以哪个上限判定。
- 风险：冻结 schema 声明不可达域；非法样本构造与错误码归属（容量错误 vs 结构拒绝）不确定。
- 影响：IMP-008、IMP-009、ACC-004 第 9 类。
- 最小闭合条件：由 `MaxNormalizedOperationBytes` 推导并声明实际生效上限（计入 base64 膨胀与操作 JSON 其余字节），或将超限判定明确挂接到既有容量错误路径。
- 复审证据预期：修订后的上限推导。

### AUD-010（低）未重申 net48/net10.0-windows 双 TFM 构建义务

- 来源层：总纲 §3.2（构建目标负责人"每个Pxx"）；先例 P03 子方案（v5）明文"net48 与 net10.0-windows 都必须 0 error"；子方案 §3 IMP-010/§4 ACC-004 仅证 x86/x64 双架构。

- 影响：IMP-010、ACC-004 前置条件。
- 最小闭合条件：在 IMP-010/ACC-004 前置中补入既有稳定构建命令的 net48/net10 0-error 要求。
