## 6. 专项语义复审

### 6.1 公开 Interface、schema、状态、错误和幂等

8 个新产品工具、5 个既有编辑工具扩展和 2 个仅测试模式工具的职责、权威 owner、input/output 核心字段和广告边界已冻结；运行时与测试共用声明式 schema 文件，不建第二手写契约。状态只有 `idle|editing|reviewed|applying|committing|committed_without_checkpoint|live_state_unknown`，持久 history 不冒充 busy 状态，唯一协调器仍是可变状态权威。

P03 新错误、P02 继承错误、恢复建议、`request_id` 同 payload 重放/异 payload 拒绝、成功与失败 terminal 记录、跨传输重连 recovery ID 和已解决 recovery 的不重复 live/package 动作均有单一语义。plain HTTP 不取得 owner 或路径/恢复细节。除 `AUD-004` 的复合失败分支外，未发现第二状态、绕过、错误吞并或幂等歧义。

### 6.2 `source_identity.v1` 与 resolver

family、lineage、checkpoint 和 replay 身份均为服务端随机 ID；`source_identity.v1` 保存 MVID、baseline image/semantic SHA，以及可用时的 handle-derived volume/file ID、final-path SHA-256、on-disk SHA 和默认输出别名。resolver 先用进程内 `ModuleDef`→family 绑定，否则使用 MVID 与唯一 active-head 内容或全部文件身份形成候选；显式 family 只过滤候选而不猜测。

该算法对 pathless、Save As、同路径替换、相同副本、多 loaded module、多 active leaf、显式 family 和跨进程都给出 match/conflict/new-family 结果；无安全匹配时拒绝或建新 family，不以路径/名称/MVID 单值静默合并。冲突和 history/status/accept 只对已初始化会话暴露 family/lineage/MVID/fingerprint/path-hash 匹配摘要，plain HTTP 不暴露原始路径或身份细节。该设计的自动匹配较保守，但有确定性并符合“不错绑”和显式接纳方向。

### 6.3 temp identity、句柄/file ID、package/ZIP 和容量

temp ID 为服务端独立 `tmp-[0-9a-f]{32}`，不把不可信 `request_id` 原文、清洗值或截断值纳入路径；幂等终态和 PartialCommit 持有原 temp ID/path/file ID/length/SHA，完成与删除需求请求所有权及 file ID 复核。NTFS、非重解析、handle-derived final path 和同目录原子 create/replace 在 live/最终文件变化前是能力门禁。

单 final/temp 压缩长度 512 MiB、单 lineage 旧 final+当前 temp 1 GiB、仓库含 final/temp/orphan/residual/unknown 共 8 GiB/4096 对象/128 有效 lineage；单 ZIP 最多 4096 物理 entry、总声明展开和单次读取最多 1 GiB，manifest/operation/baseline/payload 有类别上限，operation 数用 checked-add 并固定绝对上限。CRC/实际长度/SHA、重复/大小写别名/穿越/未知项均 fail-closed。所有计量先于创建/分配/读取，超限为既有 `EDIT_CAPACITY_EXCEEDED` 且旧 package/live/output 零变化。

cleanup 失败不再伪装 idle：它保留原 recovery 并只重试 file-ID 绑定的清理；进程崩溃孤立 temp 不自动提升/删除，只读报告并计量，非法/不可计量对象阻止新写。正常成功稳定态无 temp 与已报告崩溃残留不再矛盾。边界值、高压缩比、伪长度、截断/CRC、重复/别名/穿越、残留累积和 final/temp 竞态均已进入 `ACC-029`。

### 6.4 PartialCommit、history、三态、migration、export 和 legacy

`committed_without_checkpoint` 是进程级唯一记录，统一 `commit|undo|redo|restore|migration`。五类操作都是 prewrite/readback→live→package switch；prewrite/readback 失败零副作用，live 失败时 inverse 成功回 pre-state、失败进 `live_state_unknown`，finalize 失败保留 operation kind 和 pre/post 事实。`retry_checkpoint` 只采用 post-head 且不重放 forward；`undo_live` 只回 pre-live/head，清理完成前不回 idle；冲突保留 partial，inverse 失败进 unknown。`edit_accept_live` 明确不能吞并这些内部失败。这一闭环对存储阶段失败、恢复重试和重连幂等是唯一的；会话关闭与 live 阶段复合失败的例外见 `AUD-004`。

单 package/单 baseline、不变父链、显式 child Redo、LCA 导航、checkpoint 内局部 object-ID map、`exact|validated_drift|unverified_drift` 权限、未知 format/kind/version 硬停、validated 明确确认后建 migration child，以及 replay ID 的 package/tool/live/head 失效条件均已冻结。默认与显式导出均是同目录 temp→重载/结构/fingerprint/length/SHA→原子 create/replace；不修改 package，不覆盖源、checkpoint 或 temp，不伪装 package+output 跨文件原子。

六个旧写工具均在已持有权威 context 的 `StaticToolProvider` 转入 `LegacyEditAdapter`；patch/force/nop/rename 使用同一 begin→apply→review→commit，revert 仅撤销直接兼容 head，save 仅映射 export，并要求删除 `ilSnapshots/CilBodySnapshot/ilEditLock` 和直接 live/save 分派。没有第二实时写入、历史或保存状态的计划通道。

### 6.5 双 TFM、双架构、回归、文档与 ACC 可执行性

`net48` 和 `net10.0-windows` 必须 0 error，P03 全功能在 x64/x86 各执行一次；P01/P02/static/debug/Python/security 共同回归不得退化。英文/中文 README、MCP 完整说明、第三方完整测试提示词和 P03 定向提示词均有精确落点，工具数量以注册表为事实来源。

`ACC-011/012/013/014/020/024/025/029` 的前置、输入、实际动作、独立读回证据和失败/外部阻断边界可仅凭 P03 与 P01/P02 执行。新 runner 尚未创建时只冻结路径、case schema、证据目录和退出码，未伪造命令。`ACC-019` 的六屏障×三关闭方式×双架构已能证明普通成功与 finalize 失败，但未能证明线性化后 live forward/inverse 失败的唯一结果，故 9 项中只有该项不可独立验收。

- 反例：提交已在 Dispatcher 执行第一项 live 变更，此时收到 session close；随后第二项 forward 因 P02 已支持的实时边界故障而失败。若 inverse 成功，§6 第 3 步和行 201 要求 live 回到 pre-fingerprint、旧 package/head 不变，且原本说事务可重新 review/rollback；但行 203 又要求一旦越过第一项 live 变更，关闭必须推进到“有效 package 或 `committed_without_checkpoint`”。目标 live 已不存在，不能建立诚实的目标 checkpoint；若强行建 PartialCommit，§7 的两个恢复动作都要求 live 等于 post-fingerprint，立即进入冲突死路。若 inverse 也失败，§6 要求 `live_state_unknown`，同样不在行 203 和 `ACC-019` 规定的“checkpoint 或 partial”二元结果中。
- 影响：实施者可选择“关闭规则压过 live 失败”、“恢复规则压过关闭”或“构造不可恢复 partial”，且都不会被现有 `ACC-019` 的“无存储故障/只有 finalize 故障”预期唯一拒绝。这使 `RACC-019` 不可验收，并影响 `IMP-003/008/009`、`ACC-019/024`、提交线性化、unknown 状态、terminal request、temp 清理和会话名额释放结论。
- 最小闭合条件：不新增产品状态，明确“close 已越过第一 live mutation”与 live forward 失败、inverse 成功/失败、temp cleanup 成功/失败的优先级表。至少冻结：（1）live 成功时才进入有效 checkpoint/finalize partial；（2）forward 失败且 inverse 成功时的 pre-live/head/package/temp、已关闭事务和 terminal 结果；（3）inverse 失败时的 `live_state_unknown`、旧 head/package、temp 所有权和可用恢复动作；（4）cleanup 失败不能误报 idle。同步收窄行 203 的绝对描述。
- 必需复审证据：在 `commit_after_live_first_mutation` 屏障后，对后续 forward 注入失败，并分别使 inverse 成功/失败、cleanup 成功/失败；在 x64/x86 对 DELETE、流断开、listener Stop 读回 live pre/post fingerprint、head/package/temp/file ID、state/recovery/terminal request、旧会话失效、16 名额释放和新会话可用动作；证明不建错 checkpoint、不重放 mutation、不把 unknown 伪装 partial/idle。
- 判定：首次意见的普通六屏障覆盖已实质改进，但“所有可达提交阶段的唯一关闭结果”未满足，故原 ID 复开，不新建 `AUD-006`。

### AUD-005：关闭

- 复核证据：方案 v1 §7、§8.1-§8.2、`IMP-003/004/005`、`ACC-011/013/024`。PartialCommit 已扩展为五个 operation kind；Undo、Redo、exact restore 和 validated migration 均先完整 prewrite/readback，再改 live，最后切 package。prewrite/readback、live forward/inverse、finalize、retry/undo/cleanup、unknown、session close、重连和幂等操作的一般终态已冻结，`edit_accept_live` 不得吞并内部失败。`ACC-024` 要求对五类 operation 的 prewrite/readback/finalize 逐点故障、恢复 inverse/cleanup 失败、重复 recovery 和全导出阻断独立读回。
- 判定：首次意见指向的 navigation/migration package-finalize 终态已有唯一共用闭环。`AUD-004` 复开是 commit session-close 与 live 应用失败的复合分支，不否定本项已闭合的存储 finalize 问题。

## 8. 新意见与首次通过方向
