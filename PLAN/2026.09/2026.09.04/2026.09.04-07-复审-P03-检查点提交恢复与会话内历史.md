## 4. 七个必答问题的独立结论

### 4.1 §6 优先级表是否覆盖且互斥

**即时分支覆盖，但端到端不闭合。** 七行表能区分线性化前 cleanup 成功/失败、线性化后 live success 的 finalize 成功/失败、forward 失败后的 inverse 成功/失败，以及 inverse 成功后的 cleanup 成功/失败。表中立即结果互斥，且正确限定只有 live success 才能产生 checkpoint 或 finalize partial。

但 inverse 失败行只写“只允许 query/P02 显式 live 恢复，成功后再清 temp”。该后续转换没有对应的产品动作、owner 规则或可查询 terminal 转换，因而完整生命周期并未由七行表穷尽。不能用即时状态互斥代替端到端终态唯一。

### 4.2 `aborted_temp_cleanup` 投影和 `cleanup_temp`

**该子状态单独看是诚实、单一且有界的。** §4.1、§6、§7 一致规定：只有已证明 live/pre-head/旧 package 为 pre-state 且原 temp 删除失败时，才以既有 `committing` 投影 `aborted_temp_cleanup`；`edit_status` 从新初始化会话返回 recovery kind、允许动作和完整绑定身份；它与 checkpoint-finalize partial 互斥，不是第二事务。

`cleanup_temp` 只接受该 recovery，必须核对 path、file ID、length、SHA、pre-live/head/package，只重试删除；不得 forward、inverse、finalize、切包或建 checkpoint。失败保持同 recovery，不回 idle。这个局部闭合通过，并保持 `AUD-002/003` 的所有权和容量结论。

### 4.3 unknown → P02 显式恢复 → temp cleanup

**不唯一，且没有可执行产品交接。** 可达反例为：旧 session 已越过第一项 live mutation，随后 close；后续 forward 失败，inverse 也失败。§6 将结果置为 `live_state_unknown`，temp 附在 unknown 上下文，旧 owner/session 已撤销。

此时 v2 冻结的产品接口没有任何一个动作能执行所称的“P02 显式 live 恢复”：

- §4.2 明确 `retry_checkpoint/undo_live` 只处理 finalize partial，`cleanup_temp` 只处理 live 已经回到 pre-state 的 `aborted_temp_cleanup`。
- §4.3 明确 `edit_rollback` 保持 P02 输入及语义；新 session 又不得续用旧 transaction。
- P02 当前产品 `edit_rollback` 只结束私有事务，不执行 emergency live inverse；P02 真实 inverse-failure cleanup 是 `DNMCP_TEST=1` 的测试动作，不是产品恢复入口。

因此实现者只能在“unknown 永久阻断”“让 cleanup_temp 越权执行 inverse”“让新 session 越权 rollback 旧事务”“外部改变 live 后自行猜测并回 idle”之间自行选择。后三者分别违反 only-delete、session ownership 或 unknown 不伪装不变量；第一种不满足 v2 声称的可恢复交接。恢复失败如何继续保存 unknown 上下文、恢复成功如何原子转交 temp cleanup，也没有产品调用边界。这正是 `AUD-004` 的同一 close/forward/inverse/cleanup 终态根因。

### 4.4 close、串行权、旧/新 session 和 16 名额

**串行权原则清楚，但生命周期观测不闭合。** §6/§8.1 已明确 close 只撤 session ownership，不得覆盖已取得串行权操作根据 live/inverse/cleanup/finalize 得出的状态；P01 的 session 字典先移除再通知保证旧 session 失效并释放 16 名额；§7 也禁止新 session 续用旧 transaction。这些原则通过。

缺口有两部分：其一是上节 unknown 后没有新 session 可调用的产品恢复动作；其二是 `ACC-019` 要求新 session 读回 `terminal request`，但 §4.3 的 `edit_status` 投影只有 transaction/history/recovery，§4.2 的 history/recover 也没有通用 terminal 查询，§4.4 只说有界保存 terminal 而未给出查询字段。在线性化前 close+cleanup 成功、forward rollback+cleanup 成功等 `idle` 且无 recovery、无新 checkpoint 的分支，新 session 无法机械区分并归因原请求的 canceled/rolled_back terminal。成功 checkpoint 可证明历史变化，却仍不能按 ACC 读回请求 terminal。故“旧 session 失效、名额释放”闭合，“新 session 对所有唯一终态的可观察动作集合”未闭合。

### 4.5 `ACC-019/024` 故障矩阵

**不能机械完成题定矩阵。** 两项 ACC 已覆盖 x86/x64、DELETE/流断开/listener Stop、六屏障、live success、forward/inverse/cleanup/finalize 故障，并明确把错 checkpoint、错 partial、错 idle、unknown 伪装、重放、会话泄漏列为失败，方向正确。

但矩阵无法生成两个必需 oracle：

1. inverse failure 后的 cleanup success/failure 必须先经过“P02 显式 live 恢复”，而这个产品 action 不存在；`cleanup_temp` 此时按契约必须拒绝。
2. 无 recovery 的 canceled/rolled_back/success 分支要求新 session 读回 terminal request，而公开 status/history/recover 没有该投影。

所以 runner 要么跳过组合，要么调用不广告测试入口，要么自创产品动作/字段；三者都不能算只凭 P03 与 P01/P02 执行的机械验收。当前矩阵能拒绝初始错 checkpoint/partial/idle/unknown、forward 重放和名额泄漏，但不能证明 unknown→恢复→cleanup 的完整链，也不能在断链响应不可达时证明 terminal 幂等归属。

### 4.6 `RACC-019` 与需求保真

**未恢复为完整可验收。** `RACC-019` 的旧 session 失效、16 名额释放、重连取得新 session、旧 transaction 不可续用、checkpoint/finalize partial 可查询均有名义落点；但其 P03 `ACC-019` 又要求覆盖 close 落入 unknown/rolled-back 的可达结果并读回 terminal/actions。由于上述产品恢复和 terminal 查询 oracle 缺失，这项不能仅凭冻结接口机械完成。

- 风险级别：**高**
- 稳定引用：`REQ-007/017`、`CON-005/007/020`、`RACC-019`、`OUT-003/P03`；P03 v2 §4.1/4.2/4.3/4.4、§6 七行表及测试屏障、§7、§8.1、`IMP-003/004/008/009`、`ACC-019/024`；P02 `EditTransactionCoordinator` 的 single gate、forward/inverse fault、unknown 和 session-close 事实。
