## 1. 问题与证据

P03 红门禁（r24 登记，harness `TestReloadedTailInverses`）：`parameter_remove` 删除→写出→重载→inverse 恢复后，检查点镜像必须逐字节等于原检查点。轮次 38 已完成的墓碑图形清理使 TypeDef/Method/Param 表完全一致，剩余差异被隔离为**唯一一行 TypeRef**：

- dnlib `PreserveTokensMetadata.ReUseDeletedParamRows` 为被删参数槽生成占位结构时，`CreateDummyPtrTableType` 创建的墓碑类型以 `module.CorLibTypes.Object.TypeDefOrRef` 为基类；若源模块引用表没有等价 System.Object 行，写出时追加一行。轮次 38 的 fixture 实证为 TR45→TR46、行 46=System.Object（该 fixture 的 Object 行位于中部 RID 16，追加源于 dnlib 内部路径无等价检查，与"fixture 无 Object 行"无关——本节按 AUD-101 修正此前表述）。
- 定义表（TypeDef/Method/Param/Event/Property）行数由活对象最大 RID 计算，可随图形清理收缩；引用表（TypeRef/MemberRef/StandAloneSig/TypeSpec/MethodSpec）行位由**源文件行数**保留（`CreateEmptyTableRows`），图形操作永不脱落。
- 因此在现行 PreserveRids 检查点编码内，"删除态引入基线中不存在的引用行"使精确镜像恢复结构性不可达。反证同时成立：generic_parameter_remove（无墓碑）与 canonical 编码均逐字节精确。

该镜像等式是 §8.1 导航不变量（"live image/semantic fingerprint 必须同时等于该 target 的当前 replay 结果"）和 checkpoint 节点 `result image SHA` 可复现性的直接要求，不允许以弱化断言或仅比语义替代。

## 2. 变更内容（v3，替代 v2 全部机制）

**v2 证伪证据（VM 双架构实证，spike SPIKE-PROBE/SPIKE-B 诊断）**：
- `SPIKE-PROBE typeref-rows 45->45 probe-base=System.Object token=0x01000010 pseudo-rid=0x0100003f`——图形类型以 `CorLibTypes.Object.TypeDefOrRef`（伪 RID）为基类经检查点写出后不新增引用行，基类按值映射到既有等价行。
- `SPIKE-B ... TR46 ... objectrefs_deleted=16:0x01000010+46:0x0100002e`——删除态写出由 dnlib `ReUseDeletedParamRows` 内部创建的 dummy_ptr 基类在写出早期阶段（AllocateMemberDefRids，先于类型遍历）无条件追加第二行 System.Object；引用表行数此后从各源文件继承，图形操作不可脱落。A=TR45 与 C=TR46 无法经写出期归一对称。

**v3 机制（操作期墓碑）**：

1. **forward `parameter_remove`**：应用时不再使被删 ParamDef 脱离图形，而是把它**重新挂到 P03 墓碑宿主**：每模块惰性创建一个墓碑类型 `TypeDefUser("dnspy.mcp.edit", "DeletedMemberRows", base=module.CorLibTypes.Object.TypeDefOrRef, NotPublic|Abstract|Sealed)`（静态类形状，AUD-002）；每个被删参数行创建一个宿主方法 `MethodDefUser("d<param-rid:X6>", MethodSig.CreateInstance(void), Private|Static|HideBySig)`（AUD-102：常规私有静态方法形状，不含 Virtual/Abstract 位，规避 sealed 类含抽象虚方法的 CLR 加载风险），参数行保持原 rid/名称/sequence/attributes 移入该方法 ParamDefs。墓碑类型/方法均为 User 对象，写出时确定落在类型/方法表尾。
2. **RID/引用对称机理**：参数行不脱离其 rid（无空洞）→ 写出器 `NeedPtrTable` 不会触发 `ReUseDeletedParamRows` → 不创建 dummy_ptr → 不追加任何引用行；墓碑类型基类经类型写出路径按值去重到既有 System.Object 行。**显式前提（AUD-101）**：本机理仅在模块引用表已含等价 System.Object 行时闭合（红门禁 fixture 满足，SPIKE-PROBE 45→45 映射行 0x01000010 为证）；无 Object 行的模块中墓碑基类会追加一行并由后续状态继承，同 v2 边界，显式归入 PLAN-CHANGE-001 兜底，本变更不声称覆盖。A（基线）=干净表；B（删除态）=干净表+墓碑（尾置）；C（恢复态）=inverse 移回参数并移除空置墓碑后与 A 完全同构。
3. **inverse（`parameter_tail_restore`）**：识别参数行由墓碑宿主方法持有（宿主名 `d<rid>` 与行 rid 匹配、宿主类型符合墓碑标记+形状）、移回真实 owner 记录位置（保留对象身份），随后移除空置宿主方法；墓碑类型无任何方法时一并移除（均在表尾，无空洞）。轮次 38 实现的墓碑清理逻辑改为面向本墓碑形状（不再匹配 dnlib dummy_ptr 的 GUID 命名），失败恢复与 Undo 按容器层级精确还原。
4. **forward Undo**：与 inverse 同构——参数移回 owner、清理空置墓碑结构。
5. **指纹投影**：`EditFingerprint.Projection` 的 `excludeWriterTombstones` 分支排除 P03 墓碑类型（namespace+名称前缀+形状核对）；`Compute`（完整指纹）不排除，保持删除态对墓碑存在性的可见性。v2 的 `IsCheckpointSentinel` 谓词与 `NormalizeCheckpointSentinel` 写出归一随 v3 移除。
6. **作用范围**：forward `parameter_remove` 内部行为、inverse 恢复、指纹投影、公开 schema/包格式/其余操作语义不变。后续 field/method/event/property 中部行删除的同类空洞问题按同一机制在后续轮次扩展（本变更只落地 parameter 并登记机制）。

## 3. 边界、代价与不变量

- **代价**：删除态的检查点镜像/导出产物与 dnSpy 树中可见一个 P03 墓碑类型（含被删行宿主方法），恢复/Undo 后消失；基线与无删除状态零变化、零新增行（相较 v2 的全员哨兵更小）。墓碑形状为常规静态类+常规 flags 方法（与 dnlib 自身墓碑行同类），可重载。
- **后续 Pxx 操作关系（AUD-003/AUD-103）**：墓碑与写者墓碑同待遇——不从公开操作隐藏、不做特殊拒绝或白名单；P04-P08 操作若以其为目标，按一般类型操作语义处理并如实反映在指纹/风险中。公开 `method_remove`/`type_remove` 命中墓碑宿主/类型会重现 RID 空洞并回到引用行不对称形态（v1 形态），该入口显式由 PLAN-CHANGE-001 兜底，本变更不扩权处理。field/method/event/property 中部行删除的同类空洞按 §2.6 机制后续扩展。
- **结构验证口径（AUD-106）**：墓碑宿主"ParamDefs 非空、签名为零参 void"的形态在 `EditStructuralValidator` 中以显式登记的豁免跳过（`EditDeletedRowsTombstone.IsTombstone` 命中即整型跳过），不是放宽既有规则——样本类型永远不满足墓碑形状谓词。
- **不变量核对**：CON-009（一谱系一包、原子替换）不变；CON-011/CON-016（导出门禁/默认输出）不变；CON-024（内联 schema）不变；§5.1 包格式与操作信封不变；NON-010/011 不引入数据库/防篡改；红门禁断言原文不动；总纲第 7 节 fallback 清单不新增条目。
- **可逆性**：变更集中于 forward 参数删除、inverse 恢复、指纹投影与结构验证豁免四处；无持久格式变化（P03 未发布，无既有生产包需要迁移）。回滚即代码还原。
- **PLAN-CHANGE-001 关系**：本变更只关闭"引用表行继承导致的镜像不对称"这一子项；完整 inverse 表示（其余更新种类、definition_remove 子树、跨重载零 RID/伪 RID 绑定持久化、包消费与导航统一）仍按 PLAN-CHANGE-001 开放。

- 备选方向复核（v3 修订）：①仅预置 Object 引用行——无合法图形级中性机制；②引用表放弃 RID 保持——破坏跨检查点 token 稳定（轮次 5 反例）；③地址/写出映射表示——正确但属 PLAN-CHANGE-001 完整表示工作，保留为后续；④操作期墓票——v2 证伪后确认为唯一在写出器行为之外的关闭点，forward 语义变化限于内部宿主归属（公开 schema/操作 JSON/断言不变），定为 v3 方案。

- 结论：v3 按 v3 增量审核（AUD-101~106）逐项处理后实施；实施验证已通过（见实施记录轮次 39）。
