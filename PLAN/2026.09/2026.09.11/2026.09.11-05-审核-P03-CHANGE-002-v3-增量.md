## 2. 逐项增量审核发现

### 2.1 通过项

- **P-101（通过）v2 证伪推理与新实证自洽，"写出期归一原理性不可对称"推论成立。**
  SPIKE-PROBE（图形类型伪基类 45→45、按值映射到既有行 0x01000010）与 SPIKE-B（dummy_ptr 基类无条件追加第二行 16+46 双 Object 行）互补，且与 dnlib 源码结构吻合：`CreateDummyPtrTableType` 直接 `AddTypeDefOrRef(module.CorLibTypes.Object.TypeDefOrRef)`，该文件内无既有等价 TypeRef 检查；调用点位于 `AllocateMemberDefRids` 内（先于类型遍历），与文档"写出早期阶段"表述一致。结合既有实证（引用表行位由源文件行数保留、图形操作不可脱落），任何 materialize 期归一钩子都无法对称 A(TR45)/C(TR46)。v2 的 TypeDef 归一成功（T35/T35）而 TypeRef 不对称的失败形态与该机理完全一致。证伪链自洽。
- **P-102（通过）v3 核心机理经 dnlib 源码核对成立，四态推演在"模块已有 System.Object 引用行"前提下闭合。**
  源码核对：`NeedPtrTable => preserveRids && !wasSorted`；`wasSorted` 仅当排序后 rid 序列非顺排（有缺口）时为 false。v3 参数行保持原 rid（仅 owner 换为宿主方法，Param 的 `MemberDefDict` 对 MD defs 按 rid 保位排序，owner 归属不参与 rid 排序）→ Param 表无缺口顺排 → `NeedPtrTable=false` → `ReUseDeletedParamRows` 不触发 → 不创建 dummy_ptr → 不追加引用行。四态：A=干净表（TR45 含既有 TR16=System.Object）；B=表尾墓碑类型+宿主方法、参数行原 rid、TR45 不变（墓碑基类走类型遍历路径按值去重到既有行）；C=inverse 表尾移除宿主/墓碑（无空洞）、引用行位继承 45 行不变，与 A 同构；D（再删除）与 B 同构。红门禁 fixture 满足"已有 Object 行"前提（SPIKE-PROBE 45→45 映射 0x01000010 为既有行铁证）。
- **P-103（通过）flags 1478 声明精确。** dnlib 源码 mp 行 flags = `Public(0x6)|Virtual(0x40)|HideBySig(0x80)|NewSlot(0x100)|Abstract(0x400)` = 1478，签名 `CreateInstance(void)` 一致；v3 文档"与 dnlib 墓碑 mp 行同构的常规 flags"的方法部分精确成立。
- **P-104（通过）Ptr 表不生成且不引入镜像差异（按审核方任务重点核对）。** wasSorted 语义核对结论：Param/Method rid 无缺口时天然顺排，不生成 ParamPtr/MethodPtr 表；A/C 同构（均无 Ptr 表）故逐字节等式不受 Ptr 表影响；即便未来缺口场景生成 Ptr 表，其内容亦为确定性写出产物。附带收益：避免 dnlib 源码注释明确指出的 "peverify does not support the ParamPtr table" 验证器兼容问题。
- **P-105（通过）v1 意见在 v3 中的延续状态合理。** AUD-001 的关联备选④被采纳并补充完整机理；AUD-002 的"常规形状"意图延续（但见 AUD-102 的形状差异）；AUD-003 待遇声明延续至墓碑（§3）；AUD-004 诊断常驻延续（§4.1，含 sentinel 字段改报墓碑字段）。
- **P-106（通过）程序链完整且断言原则得到执行。** v1 审核→04 处理→v2 实施→VM 证伪→回退登记→v3 送审的链条完整；处理记录 §32 "以既有红门禁断言为最终判定，失败即回退重新登记，不在实现层静默调整"的判定路径实际触发并执行，未发生静默弱化。

### 2.2 问题项

- **AUD-101（问题）v3 对称机理存在未闭合边界：无 System.Object 引用行的模块，且文档内部证据矛盾未调和。**
  - 边界：模块若无既有 System.Object TypeRef 行，删除态墓碑基类经类型遍历路径按值去重无目标 → 追加一行；恢复态墓碑移除但引用行位由源文件继承不可脱落 → A(TR45)≠C(TR46)，与 v1 原问题同构。§2.2 括号"（无则追加一次且各状态一致——基线无墓碑时不涉及）"的"各状态一致"不成立：B 追加、C 继承、A 无，恰恰不一致。
  - 证据矛盾：§1（v1 原文沿用）称"fixture 原 45 行 TypeRef 中无 Object 行"，而 §2 SPIKE-PROBE（45→45、probe-base 映射既有行 0x01000010=TR16）与 SPIKE-B（16:0x01000010+46:0x0100002e 双 Object 行）证明该 fixture **已有** System.Object 行（TR16）。红门禁的真实机理是"dummy_ptr 不查等价行无条件追加第二行"，而非"无 Object 行时追加首行"。§1 的 v1 期误判（基于轮次 38 尾部诊断推断）在 v3 未修正。
  - 验证计划自相矛盾：§4.3 负例"恢复后墓碑完全移除且 TypeRef 行数不变（含无 System.Object 行的模块）"——按机理，无 Object 行模块的恢复态 TypeRef 行数会变，该负例将失败，把会失败的负例当通过条件。
  - 最小闭合条件（任一，须回写文档）：(a) 修正 §1/§2 矛盾，将"模块已有 System.Object 引用行"显式声明为 v3 机制前提，无 Object 行模块的精确镜像恢复明确归入 PLAN-CHANGE-001 完整表示兜底，并把 §4.3 该负例改为与前提一致的形式（如：构造无 Object 行 fixture，断言行为按已登记边界可预测）；或 (b) 补不依赖既有 Object 行的机制（例如墓碑基类指向模块内既有 TypeDef——Extends 为 TypeDefOrRef 直指 TypeDef 行、零 TypeRef 影响，但需评估该形状可加载性与被指向类型的生命周期；或其他等效机制）。
- **AUD-102（问题）墓碑类型形状"与 dnlib 自身墓碑同类"声明不准确，现形状存在 CLR 加载风险且先例不覆盖。**
  dnlib 源码 `CreateDummyPtrTableType` 的 dummy_ptr 类型形状为 `NotPublic|AutoLayout|Class|Abstract|AnsiClass`（**非 Sealed**，非静态类）；v3 墓碑为 `NotPublic|Abstract|Sealed`（静态类）+ 宿主方法 flags 1478（含 `Virtual|Abstract` 位）。"Sealed 类含 abstract 虚方法"组合在 CLR 类型加载上存在 TypeLoadException 风险（sealed 类无法被继承实现抽象方法；C# 编译器与常规元数据均不产生该组合）。§3"与 dnlib 自身墓碑行同类"与 §5"dnlib 自身 PreserveTokens 输出同类形状已被 dnSpy 生态长期接受"的先例引用不覆盖该形状差异——先例是非 Sealed 形状。删除态导出产物含墓碑，该风险直接落在导出产物可加载性上。
  最小闭合条件：宿主方法改用静态类兼容的常规形状（如 `Private|Static|HideBySig`），或类型改用与 dnlib dummy_ptr 一致的非 Sealed Abstract 形状（此时 flags 1478 保持成立）；或保留现形状但以删除态导出产物的真实 CLR 加载证据（VM 内实际加载，非仅 dnlib 重载）支撑。v3 已不受 dnlib 行为约束，宿主方法形状可自由选择完全常规组合，修复成本低。
- **AUD-104（问题，文档一致性）v3 残留 v2 版本管理痕迹，结论行指向已证伪版本。**
  §4 标题"验证计划（v2）"、§5 标题"作者自评（v2 复评）"、§5 结论行"v2 按审核修订后建议实施"均指向已被证伪并回退的 v2；§3 可逆性"变更集中于单个写出函数与指纹投影一处分支"是 v2 机制描述（v3 变更点为 forward `parameter_remove`、inverse 恢复、指纹投影，写出函数归一随 v2 移除）。执行方按文档现状可能误读实施对象。最小闭合：升版清理上述四处文字。
- **AUD-105（问题，实施前置）声称已回退的 v2 哨兵代码仍存在于工作区。**
  文档 §6 与处理记录 §26 均声称"回退 v2 哨兵代码（NormalizeCheckpointSentinel/IsCheckpointSentinel/投影排除）"，但工作区实测仍存在：`Editing/EditWorkspace.cs:122,133-145`（`NormalizeCheckpointSentinel` 及其调用）、`Editing/EditFingerprint.cs:88,144-148`（`IsCheckpointSentinel` 与投影排除分支）、`tests/edit/P03StoreHarness/Program.cs:390,399`（哨兵诊断）。文档-工作区状态不一致；若不处理，v2 证伪的写出期归一将随 v3 实施继续生效并污染镜像。最小闭合：v3 实施第一步完成该回退，并把"机械扫描无 `IsCheckpointSentinel`/`NormalizeCheckpointSentinel`/`CheckpointMarker` 残留"纳入 §4 验证计划。

### 2.3 建议项

- **AUD-103（建议）公开操作命中墓碑宿主的后果未声明。** §3 已声明墓碑与写者墓碑同待遇（AUD-003 处理延续），但未指出具体后果：公开 `method_remove`/`type_remove` 命中墓碑宿主会使参数行重新脱离图形、Param 表重现 RID 空洞 → `ReUseDeletedParamRows` 重新触发 → 回到 v1 引用行不对称形态。该入口属 PLAN-CHANGE-001 definition_remove/完整表示的既有开放问题，非 v3 退步，但应在 §3 代价/风险中显式声明，或在 §4.3 增加该场景负例（预期行为登记而非静默）。
- **AUD-106（建议）结构验证器对宿主方法的口径未声明。** 宿主方法为 `ParamDefs` 非空（持有被删参数行）而签名为零参 `instance void`——`EditStructuralValidator` 若校验"ParamDefs 行数与签名参数数一致"将拒绝墓碑；轮次 38 前写者墓碑只存在于写出后 detached 图，事务/live 图上的结构验证从未见过该形态。实施时需核对相应规则并登记口径（为墓碑形状放行或排除须以显式登记，不得静默放宽既有验证断言）。
