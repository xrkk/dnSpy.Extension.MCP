### 3.2 问题项

- **AUD-001（问题）关闭机理存在 RID 错位缺口：§2.3 幂等条款"已存在哨兵不重复添加"与 A=C 逐字节等式冲突。**
  - 推演（全部基于已实证的 dnlib 机制与现有代码路径）：
    - 基线镜像 A：原图无墓碑，materialize 追加哨兵后二次写出，哨兵 TypeDef RID=35（表尾），A = T35（34 样本 + 哨兵@35）/TR46。
    - 删除态镜像 B：第一次写出时 writer 先创建 dummy_ptr 墓碑（RID 35），materialize 重载后追加哨兵，二次写出时哨兵按活对象最大 RID 追加为 RID 36，B = T36（含 dummy_ptr@35 + 哨兵@36）。
    - 恢复态 C：恢复图重载自 B（哨兵已在 RID 36）；`RestoreParameterTail` 清理 dummy_ptr@35 后，活对象最大 RID 仍为 36 且 RID 35 成为中间空洞；dnlib PreserveRids 按活对象最大 RID 定行数并为空洞生成 dummy.{GUID} 行（`EditFingerprint.cs:131-132` 注释确认该 writer 行为）；materialize 后按 §2.3 识别既有哨兵"不重复添加"，最终 C = T36（dummy@35 + 哨兵@36）。
    - 结论：A = T35/哨兵@35，C = T36/dummy@35 + 哨兵@36，TypeDef 行数与哨兵 RID 均不对称，A ≠ C，红门禁无法以本变更关闭。§2.4"同一图状态产出唯一镜像"的声明在该场景下不成立——同一逻辑图状态因 RID 布局差异产出不同镜像。
  - 影响评估：现有 `TestReloadedTailInverses` 断言原文将直接捕获该失败（不会弱化既有断言），故错误实现无法静默通过；但被审文档的关闭机理论证（§2"关闭机理：A=B=C 均携带哨兵与 Object 引用行…表集合与堆内容一致"）只论证了 Object 引用行对称，未论证 TypeDef 行位对称，按文档实施将无法转绿。
  - 最小闭合条件（任选其一，并回写文档）：materialize 阶段对既有哨兵采用"移除后按确定性命名在表尾重追加"的 RID 归一策略（移除哨兵后活对象最大 RID 回到 34，无空洞，重追加 RID=35，C=A 成立）；或在墓碑清理路径同步移除哨兵交由写出端统一重追加；同时验证计划补充 B→C 路径的哨兵 RID/dummy 空洞专项诊断（见 AUD-004）。
  - 受影响通过项：无既有绿灯被推翻（红门禁当前即为红）；本意见阻断的是"按文档现状实施即可转绿"的预期。
  - 关联：备选④（操作期墓碑）的排除论证以"写出期哨兵已足以对称"为前提（§5 备选复核），该前提在补齐 RID 归一策略前不完整成立。

- **AUD-002（问题）哨兵形状"Interface|Abstract + 显式基类 System.Object"是非常规元数据组合，代价声明未覆盖其可加载性/验证风险。**
  - 被审文档 §2.1 在 attributes `NotPublic|Interface|Abstract` 后注"（接口合法无基类）"，却又显式设置基类 = `CorLibTypes.Object.TypeDefOrRef`。CLI 元数据惯例（ECMA-335 TypeDef.Extends）对接口类型的 Extends 预期为空，接口的型关系经 InterfaceImpl 表表达；dnlib 不拒绝写出该组合，但公共验证器（PEVerify）与部分运行时加载路径可能对"接口带 Extends"报告异常。该哨兵经检查点路径进入导出产物后长期存在（§3 已声明"导出产物含标记"），而 §3"语义为零影响（无成员、不被引用、不执行）"未覆盖此点。
  - 对照证据：既有 dummy_ptr 墓碑为 Abstract class + Object 基类（实施记录 §42），同模块写出/重载已双架构实证可行；选择 class 形状不引入该非常规性，同样满足"引入 Object 引用行"的目标。
  - 最小闭合条件：或改用与 dummy_ptr 同形状的无成员 abstract class；或保留 Interface 形状但（a）文档如实声明该组合的非常规性及其接受理由，（b）验证计划为经检查点导出的产物补充真实 CLR 加载（或 PEVerify 等公共验证器）证据，不能仅以 dnlib 重载（`ACC-014` 现有口径）替代运行时可加载性结论。
  - 受影响通过项：P04-P08 后续所有保存重载/导出验收若复用该形状，需同步该证据要求。

### 3.3 建议项

- **AUD-003（建议）哨兵与公开操作及后续 Pxx 的交互未声明。**
  - 哨兵是 live 私有图重载产物中可见的普通类型；公开 type 级操作（重命名/删除/加特性）与 P04-P08 的类型枚举、影响扫描理论上可命中 `dnspy.mcp.edit` 哨兵。若哨兵被公开操作删除或改名，materialize 端的重追加/识别语义（尤其 AUD-001 修复后"移除重追加"与用户改名后缀识别的交互）将影响谱系内镜像确定性。建议实施时明确：公开操作命中哨兵标记命名空间时确定性拒绝，或定义其完整交互语义；识别逻辑需兼容碰撞重命名后的后缀形式，避免下一轮 materialize 双哨兵（§2.4 负例仅覆盖命名，未覆盖识别-后缀兼容）。
- **AUD-004（建议）保留表计数诊断为 harness 常驻输出。**
  - 轮次 38 的 `tables_pre/post`、`refs_tail` spike 诊断是定位本类问题的唯一高效证据；建议按验证计划第 5 条的既有证据协议将其转为 `TestReloadedTailInverses` 常驻输出（或失败时自动附加），避免 AUD-001 类失败重演"红但无定位"的取证成本。该项与 AUD-001 的闭合验证直接配套。
