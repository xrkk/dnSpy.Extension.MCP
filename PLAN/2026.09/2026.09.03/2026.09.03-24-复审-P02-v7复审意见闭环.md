### 4.2 TypeSig 删除向量的 fail-open 反例

当前 TypeSig 数据确实把 `context + owner_type_arity + owner_method_arity` 作为机器字段，当前独立 parser 也对现存向量执行 `< arity`、Void 和 final-byref 规则。这一正向改进成立。

但是 validator 不维护所需向量的独立固定身份集合，只对“当前源中还剩下的 valid/invalid 数组”执行 `all()`。在隔离副本中，从规范源删除以下五个关键 negative vector 后重新生成：

- `!0` + owner type arity 0；
- `!1` + owner type arity 1；
- `!!0` + owner method arity 0；
- `System.Int32&&`；
- `System.Int32&*`。

validator 仍报告 117/117、0 errors、六个 RACC 全 true、PASS。现有 `typesig-owner-arity-removed` 变异只会把一个 valid row 改成 parser 必拒绝的输入，不能发现关键边界向量被整体删除。因此审计 20 要求的“删改向量会 fail closed”不成立；普通 fixture 可以避开 owner 边界和 suffix 缺口。

### 4.3 EmbeddedPdb live target 不是 dnlib 4.5 公开对象路径

当前 corpus 把 EmbeddedPdb 的路径冻结为：

`PdbMethod.SequencePoints[0].Document.Url`

这不是 dnlib 4.5.0 的真实公开模型。固定 DLL 的 XML API、仓库既有 S02 Spike 和独立反射结果一致：

- `dnlib.DotNet.Pdb.PdbMethod` 的公开属性只有 `Scope`；
- sequence point 位于 `dnlib.DotNet.Emit.Instruction.SequencePoint`；
-文档 URL 的可达路径是选中 `MethodDef.Body.Instructions[i].SequencePoint.Document.Url`，其中 selector 必须定位实际持有 sequence point 的 instruction，而不是 `PdbMethod.SequencePoints[index]`。

独立反射程序输出：`PdbMethod=Scope`、`Instruction.SequencePoint=dnlib.DotNet.Pdb.SequencePoint`、`PdbDocument.Url=System.String`。把契约路径原样写成 C# 后，以同一 dnlib 4.5.0 DLL 编译，得到 `CS1061: 'PdbMethod' does not contain a definition for 'SequencePoints'`。既有 `tests/spikes/dnspy-feasibility/FeasibilityExtension.cs` 也通过 `m.Body.Instructions.Count(i => i.SequencePoint is not null)` 读回，并通过 `instruction.SequencePoint.Document` 处理文档。

validator 的“独立”常量表复制了同一个错误字符串，故 `component-recipes:exact-live-actions` 只证明 source 与 validator 共同同意一个不存在的路径。现有错误 target 变异改成 `byte-buffer` 才失败，不能验证原 target 真实可编译/可解析。于是五 channel 中 EmbeddedPdb 的 target/action/readback/restore 不可执行，六份 evidence artifact 的 component suite 无法按规范完成。

### 4.4 capacity 常量和 lifecycle 没有同一可执行闭包

begin/apply 的 schema payload 与 `1/2 MiB` per-response、`64/4 MiB`、`1024/32 MiB` 当前数值相容；把 `apply_response_bytes` 改为 1 会失败，这一项已闭合。

但 validator 没有消费 `review_tombstone_entries`、`review_tombstone_bytes`、`rollback_slot_bytes` 与 lifecycle/serializer 的关系。在隔离副本中同时把三者从 `64 / 65536 / 65536` 改为 `1 / 1 / 1`，再由 generator 正常重生成全部对象，validator 仍报告 117/117、0 errors、六个 RACC 全 true、PASS；报告中的 lifecycle 仍硬写 `tombstones<64` 和 `tombstones=64`。

该反例直接破坏 `r1→...→r65`、第 66 次 capacity error 和 session terminal response slot，却不触发任何语义错误。原始成功 rollback output 的 schema 上界实测为 25,708 bytes，也已大于变异后的 1-byte slot；当前 validator 仍不检查。故这些不是已消费的共同容量模型，而是彼此并列的数字与字符串。apply/rollback/close/timeout 的清零方向存在，但 byte/entry/lifecycle 没有机器绑定，审计 20 的“不得出现未消费常量”未闭合。

### 4.5 fault 单调用和 runner 聚合语义仍只受宽松字符串检查

当前静态 fault row 的 240 唯一、manifest/oracle min=max=240、24-row 最大整调用 trace 数值均正确。空/重复/截断 manifest 可被 schema cardinality 拒绝，这部分闭合。

但是“actual trace 是真实有序前缀且注入时以 armed row 结尾”以及“runner 保存 240 份互异 ArtifactRoot 证据”只存在于 `fault_suite_contract` 的自然语言字符串。validator 对 per-call 只检查数组长度为 4；对 runner 只检查数组长度、第一句含 `one new transaction`、第三句含 `exactly once`。

在隔离规范源中把：

- actual trace 规则改成“可以是与 armed fault 无关的任意 schema-valid sequence”；
- artifact 规则改成“所有调用可以复用同一个 evidence artifact”；

并正常重生成后，validator 仍为 117/117、0 errors、六个 RACC 全 true、PASS。也就是说，实现可回报不以 armed row 结束的 trace，runner 可复用一份 artifact，而当前“独立 validator”仍认定 `RACC-009=true`。现有 14 个失败控制没有覆盖这两个最小条件。manifest 的局部 cardinality 已闭合，但 reverse-after 的可证明前缀和 240-call 外部唯一覆盖仍未形成可执行 oracle。
