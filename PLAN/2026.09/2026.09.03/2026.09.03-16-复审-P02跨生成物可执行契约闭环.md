### 2.2 独立反例摘要

1. **传输上限反例**：不导入 generator，独立递归 `edit_review.outputSchema`，得三个顶层 oneOf 上界为 `14,687,498 / 4,919,113 / 9,309,810` bytes，因此 v5 的 `14,687,498`、16 MiB slot 及 `2,089,718` 内部余量算术本身成立。但 P01 已实施的 `ResponseBudget.MaxResponseBytes=8,388,608`，`McpServer.RenderBoundedResponse` 会把任何超限完整 JSON-RPC 响应替换为 `-32603`。最大 success 分支比传输上限多 `6,298,890` bytes，带 validation attempt 的 error 分支也超限；尚未计入 MCP/JSON-RPC 外层及可能的 text/structuredContent 重复。
2. **稀疏 attributes 反例**：`TypeAttributes=0x40`、`FieldAttributes=0x8`、`PropertyAttributes=0x1`、`ParamAttributes=0x20` 全部满足标准 schema 的 `minimum<=value<=maximum`，却都满足 `(value & ~mask)!=0`。`x-dnspy-defined-bit-mask` 是注解而非标准 JSON Schema 约束；契约虽给出 mask 和 Spike 文字的位运算方向，但 validator/5 个变异没有非法稀疏位证据。
3. **常量反例**：`u8` schema 的 maximum 是 `9,223,372,036,854,775,807`，因此拒绝合法 `UInt64` 上半区 `2^63..2^64-1`。单 scalar char、r4/r8 有限边界、property/event add/update nullability 的当前方向可以从源和 schema 恢复，但不能消除这个数值合法域缺口。
4. **TypeSig 反例**：契约 EBNF 引用了未定义的 `generic_name`；独立 validator parser 会同时接受 `Example.Box<System.String>`、`Example.Box`1<System.String,System.Int32>`、`System.Int32<System.String>`、`System.Void[]` 和任意大 `!<uint>`。实施者仍需决定 generic arity/非泛型构造/上下文中 Void 是解析拒绝还是结构验证拒绝。18 个 OperandType 名称集齐全，opcode 运行时从 dnlib 4.5.0 表取类型的方向也已指定，但没有任何 opcode→OperandType 全表 golden/突变证据证明完整消费。
5. **component 假独立反例**：61 个 recipe 全部由一个模板生成，实际差异只是 `category:Component` 标签；target 均为 `primary-element`，mutate 均为 `replace-component-payload-with-sentinel`，reorder 均为 `rotate-enumeration-order-by-one`，readback 均为 `component-specific-canonical-sha256`。它们没有字段/RID/API/预期读回值，且对通常只有一行的 Module/Assembly 也要求“two distinct elements”。额外临时变异把全部 action 换成同一 `shared-adapter:<component>:echo-label:<mode>` 模板，并以“只记录请求”代替 reorder；validator 的 `component-recipes` 类别仍为 true，无 component/negative-control 错误，只剩字节再生成哈希错误。
6. **fault 单调用/聚合反例**：240 rows 可从 lowering 独立推导，且 golden 与四个公开 evidence 数组确为同一九字段 schema/projection。但 `edit_test_fault` 每次只能 arm 一个 ID，方案又要求“逐 fault ID 新事务”。在一次故障调用内，actual trace 只能是到失败点的前缀，covered 只能证明当次注入，不可能同时等于全套 manifest/oracle。九工具 schema、capacity state 和 fault result 均没有跨调用 suite accumulator/artifact 的身份、去重、重置、完成与清理语义，故“单次四集合”与“全套聚合”两种实现方向仍需实施者裁决。
7. **动态七分支反例**：同一组 7 个 dynamic branch 原样出现在 `edit_review` 的 success result 和带 `validation_attempt` 的 error 两侧。因此 `ok=true + blocked/failed` 和 `ok=false + passed/not_requested` 都是 schema 合法输出，与 v5 §5 “失败/阻断不生成 review”直接冲突。此外 blocked 和三个 failed branch 的 `failure.phase` 均不加区别地允许 `precheck|write|launch|run|terminate|delete`，例如 artifact=false/未尝试删除却报 `phase=delete` 仍合法，events/artifact/cleanup/failure 并未真正闭合。
8. **requirements fidelity 反例**：新 validator 不再按总 errors 直接硬编码 6/6，这一改进成立；但映射不是逐 RACC 全语义证据。例如 RACC-002 只映射 `cache-transitions` 的一个 rollback 检查和 review lifecycle，不检查 DELETE、600 秒边界、listener restart、stdio 同 URL、端口变化不猜测/不重放；RACC-026 只检查错误码存在和没有额外工具，不检查分析保持可用或零副作用。额外变异删除 `close|timeout` transition 并用重复行保持数量后，报告仍给 `cache-transitions=true` 和 `RACC-002=true`，只报再生成哈希差异。
9. **`all()` 空集合风险**：`component-recipes`、`operation-set`、`type-sig`、`attribute-domains`、`constant-accessor-rules`、`fault-schema-golden`、`capacity-schema-bound`、`dynamic-state-contract`、`error-contract` 类别均用对名称前缀的 `all(...)` 计算，未先断言匹配集合非空。当前正常生成物中这些前缀均有检查，因此尚未单独构成当前报告的全绿利用；但它是明确的假通过原语，而且 `untestable` 只检查类别 key 存在，不检查该类别是否有实证集合。

## 4. validator 判定

- **已成立的改进**：先读存量，再向临时目录再生成并逐字节对比；不 import generator；TypeSig 有独立 parser；fault rows 可从 lowering 独立重建；review 上界有独立递归计算；5 个指定变异确实命中目标错误。
- **仍不是完整语义 validator**：它验证 component 字符串包含组件名，不验证真实 mutation；验证四个 evidence 的 item schema 相同，不验证单调用/聚合语义；验证 dynamic 分支局部形状，不验证它与 success/error/review 的互斥；验证 internal review slot，不读 P01 固定传输上限。
- **五个变异的作用边界**：它们能证明特定 JSON 变化会被发现，但不能发现“标签仍 component-specific，真实 handler 始终修改同一对象”，也没有覆盖稀疏 mask、`u8`、dynamic 信封互斥、8 MiB 传输上限或 fidelity 语义缩减。
- **fidelity 计算**：已从 `requirements-map.json` 与 evidence booleans 计算，不再是旧版总错误条件分支；但 evidence booleans 本身不覆盖对应 RACC 的全部动作/不变式，故 6/6 仍不是需求保真证据。

## 6. 边界、继承、影响和 v4→v5 结论

- **P01/P02**：P01 owner/session/VM/idle 前置已落地且 v5 只消费不改写；但 P01 同时固定的 8 MiB 完整响应上限必须被继承，16 MiB review slot 不能隐式把传输上限扩大。
- **P02/P03**：五产品工具仍无 commit/checkpoint/export/Undo/Redo，四测试入口仍不广告并要求同调用恢复；AUD-007 和 P03 唯一完整提交边界未越界。
- **IMP/ACC 影响**：未闭合问题直接影响 `IMP-001/003/004/005/006/008`、`ACC-003/009/010`；`ACC-009` 当前无一致 oracle，`ACC-010` 的公开输出互斥关系不成立。
- **非目标/fallback**：v5 没有引入原始编辑、AsmEditor、并行事务、磁盘副本、自动端口猜测或无审查产品提交；未声明新 fallback。
- **后序依赖**：P02 名义上仍只依赖 P01，没有把 P03-P09 当作通过前置；但当前契约未通过，P03 不得消费这些事实。
- **v4→v5**：方案文本仅引入 Spike 生成物和新哈希，没有改 Pxx/OUT、工具数、IMP/ACC、NON 或 fallback；因此无范围越界。但这不等于“只解除熔断”：新契约把 review slot 提到 16 MiB，实际与上游 8 MiB 传输固定事实冲突；其他三个熔断根因也仅在字符串/局部 shape 层面闭合。
- **继承通过项**：AUD-002、AUD-004、AUD-007、AUD-008，P01 前置，稳定 IMP/ACC ID，NON/fallback 和五产品/四测试工具边界，均未被本轮反例推翻。

## 7. 熔断判定与精确结论

AUD-003、AUD-005、AUD-006 在记录 12/13 已因“契约各域之间缺少可执行交叉约束和独立反例验证”同根因复开；Spike 14 是指定的上游解除尝试。本轮又独立证明：corpus 仍可以标签代替实际 component mutation，review 仍与上游固定传输容量不相容，fault/dynamic 仍没有同一可执行生命周期。这不是新的审核口径，而是指定解除证据未满足原最小闭合条件。

故：

- 需求保真独立计数为 `6/3/0/1/2`，非 `6/6/0/0/0`；
- P02 v5 仍为“未审核, 不得实施”，不得进入 P02 业务实现或 P03；
- 本轮精确结论：**审核循环熔断**。
