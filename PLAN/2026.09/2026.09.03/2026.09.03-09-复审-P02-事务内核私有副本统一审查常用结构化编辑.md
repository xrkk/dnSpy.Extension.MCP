## 4. 活跃审计意见与语义反例

### AUD-001：严格 schema 仍不能从正文唯一生成

- 严重度：高；根因连续性：与 03、05、07 的“公开 schema/IL operand 不是唯一机械规范”相同。
- 证据：v3 第 134、154、164-166、188、225 行及第 89-96 行。
- 反例 1：`error.details.conflict` 只有 `{expected,actual}` 字段名。`EDIT_REVISION_CONFLICT` 需要整数，`EDIT_LIVE_MODULE_CONFLICT` 需要 SHA-256；正文既未给二者类型 union，也未把 error code 绑定到 details.kind/nullable 分支。实现 A 对所有冲突使用字符串，实现 B 对修订使用整数，均能声称符合字段表，但严格客户端只能接受其中一种。
- 反例 2：第 225 行只绑定 InlineI/InlineI8/ShortInlineR/InlineR/InlineString，遗漏合法且常用的 `ShortInlineI`，也未固定 ShortInlineVar/InlineVar 的可编码索引范围。`ldc.i4.s` 是接受 i32、按 sbyte 拒绝，还是整体能力拒绝，仍由实施者决定。
- 反例 3：四个测试入口声称封闭 schema，但 `fault_manifest`、`actual_mutation_trace` 及其中元素没有字段、required、上限或 discriminator；第 96 行又向第 93 行声明的封闭 result 追加未声明的 `emergency_cleanup`。
- 影响：违反 `CON-024`，并使 `IMP-003/004/008`、`ACC-003/009/010` 和 Python/严格 MCP 宿主无法共享唯一 wire contract。

### AUD-002：无 ParamDef 物化及结构错误/risk 边界仍自相矛盾

- 严重度：高；根因连续性：与 03、05、07 的“参数字节语义和结构硬阻断不唯一”相同。
- 证据：v3 第 218、229、238、242-244、286、324、328 行。
- 反例 1：第 218 行要求通过 owner method+index 更新无 ParamDef 槽时物化 ParamDef；第 286 行的唯一 live lowering 只列 name、attributes、MethodSig slot type，没有 `Method.ParamDefs insert`，也没有其顺序和反向值。私有副本可多出 ParamDef，实时 apply/restore 却无法按 oracle 得到同一图。
- 反例 2：第 229、238 行规定仍被引用/附着的删除必须 `EDIT_VALIDATION_FAILED`；第 244 行又把“删除仍被本模块引用的对象”列为可确认 risk。相同输入同时具有硬失败和可确认继续两个互斥结果。
- 反例 3：ACC-003 只测 ParamDef Sequence 同步/重复，没有冻结 Sequence=0 return 拒绝，以及无/部分/完整 ParamDef 三类基线的物化、update/remove、object ID 和失败回滚证据。
- 影响：`parameter_update/remove` 的私有字节、实时 primitive、revision、对象映射和风险边界不唯一；`RACC-003` 只能覆盖较窄 fixture，构成语义弱化。

### AUD-003：完整指纹的声明证据不可达

- 严重度：高；根因分类：证据不足；算法方向保留，不否定完整像方案本身。
- 证据：v3 第 92、146、303、328 行。
- 反例：唯一公开的 external mutation seam 只有 rename type、add interface、add custom attribute、reorder types；ACC-003 却要求逐 metadata table/edge 单点变化，并明确声称覆盖 PDB、FieldRVA/resource、opaque blob 和未知 attachment。测试 runner 无法仅凭四个封闭入口制造这些变化，也没有另一个有名称、输入和清理语义的内部 seam。
- 影响：实现可以只对四种可造变化通过，却把其余覆盖域留作未执行断言；`AUD-003` 的算法文字与证据闭环不能同时判定通过。

### AUD-005：review 独立容量仍不能保证合法审查可达

- 严重度：高；根因连续性：与 03、05、07 的“有界资源下 review/rollback 可达性不成立”相同。
- 证据：v3 第 85、119-124、173、175-188、332 行。
- 反例 1：review slot 为 1 MiB，但合法 review 可同时含最多 512 KiB 规范 diff、256 个 risk；每个 risk 又允许 `object` 和 `description` 各 4096 字符，尚未计 dynamic events、validation、fingerprints 和 envelope 就可超过 1 MiB。正文禁止逐出并声称一次 review 始终可达，却没有总序列化上限、截断规则或合法容量错误。
- 反例 2：事务内 `review A → apply → review B` 时，旧 A 的 request ID 按第 85 行仍在活动事务中；第 121-122 行只有一个独立 review slot且既有项不逐出。覆盖 A、拒绝 B、保存两项或重放失效 A 均未冻结。
- 影响：ACC-009 的“apply cache 满载后新 review 和其重放一致”不证明最大合法事务或第二次 review 可达；幂等响应与资源上限仍可能互相破坏。

### AUD-006：primitive/fault 独立 oracle 和失败证据仍不成立

- 严重度：高；根因连续性：与 03、05、07 的“fault seam/primitive oracle 由实现自行解释”相同。
- 证据：v3 第 93-96、164-166、218、268-291、332、341 行。
- 反例 1：稳定 ID 模板是 `fp-<operation_index>-<step_index>-<kind>-before|after`，而正/反向类别只是模板外的另一字段。scalar update 的正向和反向具有相同 operation index、step index、kind 与 before/after，故 fault ID 冲突。`edit_test_fault` 只按 ID arm 且首个命中即清空，想注入反向点会先在正向命中，无法完成 ACC-009 要求的独立反向失败。
- 反例 2：无 ParamDef 物化缺少 ParamDefs insert primitive；test oracle 按表不会生成，实际 trace 若正确生成则四集合不等，若不生成则实时图与私有图不等。
- 反例 3：正向或反向注入后 `edit_test_apply_and_restore` 必须返回 error；第 164-166 行规定 error 无 success result，但 fault manifest/actual trace 只声明在 success result。ACC-009 要求的失败 manifest/trace/covered 证据没有合法响应或取回位置。
- 影响：`RACC-009` 的“每个实时应用步骤”无法枚举和逐点注入，半应用/恢复失败测试可以遗漏真实 primitive，属于不可验收。
