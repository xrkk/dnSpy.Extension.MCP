## 4. 完整语义复核与独立反例

### 4.1 已闭合并继承的部分

- P01 owner 只来自 `McpCallContext.AuthoritativeSessionId`，plain HTTP 不可拥有事务；session lifecycle 以字典移除为幂等关闭边界。
- P02 产品只广告五工具；四个测试入口不广告；没有产品 commit/checkpoint/export/Undo/Redo，P02/P03 边界保持。
- 22 个 operation kind、parameter materialize 的 private/forward/reverse、return ParamDef 拒绝、referenced/attached delete hard-fail 未回退；AUD-002 保持闭合。
- 异 ID loser、rollback 取消、锁外 waiter、异步 continuation、generation 和跨事务 ID 主规则未回退；AUD-004 保持闭合。
- dnlib 4.5.0 的 229-row opcode map、八个 mask、`u8=2^64-1`、稀疏位向量、dynamic success/error 顶层状态分离和 P01 8 MiB 常量均已进入生成契约。
- 测试 apply/restore 三终态、端口 15378→15379 显式更新且不扫描/猜测/重放分别保持 AUD-007/AUD-008 闭合。

### 4.2 反例一：TypeSig “context/index 已闭合”仍不是可执行门禁

`operation_semantics.type_sig.context_rules` 声称 generic index 必须存在于 owner context，但独立 parser 的输入只有文本和 `field|parameter|method_return` 字符串，没有 owner 的 type/method generic arity。实测 `TypeSig("!0","field")` 与 `TypeSig("!!12","parameter")` 都返回 true，即使“owner arity=0”无法传入。现有 valid/invalid vectors也只有 `!65536` 的全局数值上界，没有 `!0`/`!!0` 对零 arity、恰好边界和越一的 owner-context 案例。相同 parser 还接受 `System.Int32&&` 与 `System.Int32&*`；suffix 的上下文合法性只能留给实现者另行裁决。

因此 v6 所称 arity/context/Void/index 只部分机械化；validator 的 `type-sig:*` 全绿不能证明 owner-context 不变量。`requirements-map` 的 `typesig-vectors` 只是自然语言动作和证据标签，没有补足这些输入/预期。

### 4.3 反例二：61 个“exact”组件 recipe 中存在不可执行案例

全部 61 个 recipe 都要求 `projection_atom_count_minimum=2` 并为 reorder 使用 `reverse-component-projection-enumerator`。但 ECMA-335 Module table 对一个模块只有一行，Assembly table 对普通程序集至多一行；当前 corpus 仍要求 `fp-component-module:reorder` 和 `fp-component-assembly:reorder` 具有两个可逆序 atom及 raw-order digest 变化。这两个案例无法由任何符合 P02“普通纯托管单模块 EXE/DLL”前置的 fixture 满足。

此外 mutate action 统一为“对写出像中定位的 row/stream payload byte 做 XOR”。P02 的冲突对象却是 dnSpy 当前 live `ModuleDef`；方案没有提供把任意 metadata/PDB/opaque 字节 XOR 映射为同一 live graph 的 component-specific dnlib mutation，且不能替换 dnSpy live `ModuleDef`。若只对序列化字节或独立 reload 图做 XOR，证明的是输入字节 SHA 会变，不是 UI/live graph 的完整指纹会捕获该 component。validator 只对拍 locator/action 字典和哈希，未检查 fixture 可满足性、live graph 可达性或 restore 的实际语义。

### 4.4 反例三：capacity golden 的 begin/apply 响应上限没有参与容量证明

`capacity-golden.limits` 固定 `begin_cache_bytes=4 MiB/64 entries`、`apply_cache_bytes=32 MiB/1024 entries`，并固定单响应 `apply_response_bytes=24,576`；历史 v3 明确 begin/apply 单响应上限为 64/24 KiB。独立递归当前 schema 得到：

- `edit_begin` success 上界 437,988 bytes，通用 error 上界 517,179 bytes；
- `edit_apply` success 上界 1,712,099 bytes，通用 error 上界 517,179 bytes。

generator/validator 只把这些值与 8 MiB transport 比较，从不把 begin 分摊上限或 `apply_response_bytes` 与 schema/实际缓存响应交叉验证。最小失败控制把规范源中的 `apply_response_bytes` 从 24,576 改为 1、同步重生成后，validator 仍为 118/118 PASS，同时报告 `edit_apply.payload_max_bytes=1,712,099`。因此该 limit 是未消费常量，不能证明字节相同重放、缓存满载和最大合法响应可同时成立。

连续 review 也只枚举 first/new/old/apply-success 四行，并把 tombstone 固定为 1；对 `review r1 → r2 → r3 → replay r1` 没有唯一规则。若只保留一个旧 tombstone，r1 的幂等/稳定 stale 事实丢失；若保留全部，当前没有 tombstone 条目/字节上限。validator 只检查四行存在和包含 `review(new-id)`，不检查任意 N 次的有界闭包。

### 4.5 反例四：reverse fault 的 actual trace 容量不足

fault golden 对每个 live primitive 同时产生 before/after row。`event_update` 和 `property_update` 各有 6 个 forward、6 个 reverse primitive，因此完整 apply→restore 路径各有 24 个实际边界 row；生成的 24 个 fault ID 也确实存在。`execution_evidence.actual_mutation_trace.maxItems` 却固定为 16。

对晚期 reverse fault，调用必须先真实抵达 12 个 forward 边界，再抵达 reverse 前缀，并以 armed reverse row 结尾；按当前“actual trace 为真实抵达的有序前缀”定义，最多需要 24 行，无法装入 16 行。若 reverse 开始时清空 trace、只记录当前 direction，便不再是本次调用实际抵达路径的完整前缀，也不能证明 forward 已真实执行；契约没有定义这种投影。

公开 schema 对 `fault_manifest/oracle_faults` 也只有 `maxItems=240`、没有 `minItems=240` 或 uniqueness，空 manifest/oracle 仍满足局部 schema。正文的“完整全集”是自然语言，validator 只核对这段字符串和静态 golden，没有验证 runtime evidence 的前缀/终点/单点/聚合关系。当前 11 个变异没有覆盖 16→24、空全集或重复 row。

## 5. AUD 稳定判定、影响与最小闭合条件

### AUD-001：操作合法域仍非唯一可执行规范

- 本轮结论：**未闭合，同根因复开**；严重度：高；根因分类：方案抽象错误/验证不足。
- 反例：TypeSig parser 无 owner arity 输入，无法执行 `!n/!!n must exist in owner context`；suffix/context 合法性仍由实现者补充。
- 影响：`IMP-003/004/005/008`、`ACC-003`、`RACC-003`，以及 P03 对规范操作事实的消费。
- 最小闭合条件：把 owner type/method arity和签名位置作为 TypeSig validation vector 的机器输入；固定 `!n/!!n` 边界/越一、Void、ByRef/pointer/array 组合的逐 context 结果；validator 必须从这些向量计算通过，而非只检查规则字符串出现。
- 复审证据：所有 context×owner arity×index 边界向量、非法 suffix 组合、实际 schema/structural error code 和无副作用结果。

### AUD-003：完整指纹 mutation corpus 仍不可执行

- 本轮结论：**未闭合，同根因复开**；严重度：高；根因分类：证据不足/不可执行 recipe。
- 反例：Module/Assembly reorder 的 `projection_atom_count_minimum=2` 不可满足；raw image XOR 没有 live `ModuleDef` component-specific mutation 路径。
- 影响：`IMP-002/006/007/008`、`ACC-001/003/009/010`，以及 UI 外部变化冲突、反向恢复完整性和 P03-P08 继承。
- 最小闭合条件：逐 component 给出可由纯托管单模块 fixture 满足的 atom 基数和真实 dnlib live graph target/action/readback/restore；单例 component 不强造 reorder，须用另一个真实规范化顺序负例；runner 必须证明 action 改的是指定 live component，而非独立字节缓冲区。
- 复审证据：61 组件逐例 fixture identity、live object/API、动作前后 component readback、完整指纹、恢复读回；不可构造组件须调整覆盖声明而不能伪造 atom。

### AUD-005：响应/缓存/review 容量仍没有同一闭包

- 本轮结论：**未闭合，同根因复开**；严重度：高；根因分类：方案抽象错误。
- 反例：24 KiB apply response limit 与 1,712,099-byte schema 上界互不校验；把 limit 改成 1 后 validator 仍 PASS；第三次 review 的旧 tombstone 无有界语义。
- 影响：`IMP-001/003/005/008`、`ACC-001/002/009`，尤其同 ID 完整响应重放、满载恢复与 review 可达性。
- 最小闭合条件：从实际 begin/apply output schema 和固定 serializer 推导每响应上界并与每项/总缓存容量同时求解，或收紧 schema；将任意 N 次 review 的 full slot、tombstone 上限、旧 ID 响应和超限恢复写入 capacity golden。
- 复审证据：begin/apply 最大合法 success/error 的真实序列化/缓存/重放；条目和字节分别满载；r1/r2/r3/旧 ID/超限/rollback/close/timeout 的完整状态矩阵；对未消费 limit 的 mutation 必须使 validator 失败。

### AUD-006：fault 生命周期仍没有可承载的单调用证据模型

- 本轮结论：**未闭合，同根因复开**；严重度：高；根因分类：方案抽象错误/不可验收恢复 oracle。
- 反例：event/property update 的真实 forward+reverse 边界前缀最多 24 行，而 schema trace 上限只有 16；manifest/oracle schema 又不强制完整唯一全集。
- 影响：`IMP-006/008`、`ACC-009`；不能证明所有 reverse 故障均发生在真实 forward 之后，也不能排除漏 primitive 的全绿报告。
- 最小闭合条件：冻结 actual trace 的精确投影和 direction 边界；若记录整次调用，容量至少覆盖最大 forward+reverse before/after 路径；若分相记录，分别提供 forward/reverse trace 并显式关联。manifest/oracle 必须由 schema或 runner 的机器断言强制 240 条、唯一、逐行等于 golden；runner 聚合须验证 240 份互异 ArtifactRoot 证据和 covered 恰好一次。
- 复审证据：对 `event_update/property_update` 最后一个 reverse-after fault 保存完整可验证 trace；删除、重复、截断 manifest/trace/covered 的失败控制。

## 8. 熔断判定与精确结论

`AUD-001`、`AUD-003`、`AUD-005`、`AUD-006` 均为记录 03/05/07/09/12/16 已连续追踪的同根因意见。复审 16 和处理 17 已精确要求：完整 TypeSig context、可执行 component-specific recipe、跨 schema/capacity 的上界闭包，以及 fault 单调用/外部聚合的唯一证据模型。Spike 18/v6 是该上游解除尝试，但本轮仍以实际生成物和独立反例证明同一根因存在；不是需求变化、代码漂移、环境阻碍或审核口径变化。
