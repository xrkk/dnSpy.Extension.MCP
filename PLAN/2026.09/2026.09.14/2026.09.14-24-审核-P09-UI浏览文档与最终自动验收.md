## 3. 语义审查关键判定

- **J1（UI 只读+取消合规性）**：总纲 §4.1 行 126/§6.3 行 205 冻结"UI 只浏览和本地取消；不提供绕开审查、提交、恢复、VM 门禁或导出门禁的第二实现"。IMP-001 的面板六区+取消按钮+无提交/恢复/导出/编辑按钮与 RACC-018（需求行 206）逐句对应；取消走 coordinator 新增 `CancelFromUi()` 内部入口→同一 `EndLocked(tx,"ui_cancel")`（代码事实：`EndLocked:1675` 是 `edit_rollback`（`:903`）、会话关闭（`:455/:895/:990`）、超时（`:1674`）、dispose（`:1707`）共用的唯一释放路径，含 `CancelRequested`/`OperationBusy` 延迟处置与缓存清理）——复用而非第二实现，方向正确。**但"仅在面板属主=事务属主"一句不可求值且与 §1 无条件提供矛盾**（AUD-004）。
- **J2（UI 取消与所有权模型的相容性——本轮核心反例一）**：`RequireTransactionLocked:1677` 对非属主 MCP 会话抛 `EDIT_OWNER_MISMATCH`，所有权来自权威传输上下文（CON-008）。UI 不是传输会话：进程内唯一活动事务（CON-002）在 UI 取消发生时几乎必然属于某个 MCP 会话。需求侧依据链（RACC-018"可取消当前事务"无属主限定；总纲 §4.3 行 156-157 将 dnSpy UI 定位为本地操作者，与 CON-014"本地覆盖仅 dnSpy UI"同构）支持"本地操作者可取消唯一活动事务、不分属主"的读法；该读法下属主会话后续请求经既有路径得 `EDIT_TRANSACTION_NOT_FOUND`（`active==null` 分支），恰为 ACC-018 已写断言。v0 把这一方向性决定留空（自评薄弱点 1），两个实施者可做出行为相反的两种实现且都自称符合方案。
- **J3（线程模型——本轮核心反例二）**：现状协调器 `gate` 临界区均不含 dispatcher 往返（Begin 的 `EditWorkspace.Create` 在 gate 外 `:382`；Commit 各 `BarrierPoint`/`OnDispatcher` 均在 gate 外），`EditWorkspace.OnDispatcher:234-239` 为阻塞 `Invoke`。若实现者在 UI 快照或 `CancelFromUi` 中于 `lock(gate)` 内做 dispatcher 往返，或 MCP 线程未来在持 gate 时 `Invoke`，即形成"UI 线程等 gate、MCP 线程等 UI 线程"死锁；若旁路 gate 直读 workspace 集合则为撕裂读。另 `State:125` 取值器内调 `ExpireLocked()`（可触发超时回滚），1s 轮询事实上驱动过期检查并与 `edit_test_clock` seam 交互——测试隔离影响需一句话声明。
- **J4（注册表事实来源的机械可执行性——本轮核心反例三）**：`export_tool_registry.py` 的取数路径未定义：C# 注册表是运行时事实（三处 provider：`StaticToolProvider`/`DebugToolProvider`/`EditToolProvider`），脚本只能源码解析（既有先例 `validate_p03_contract.py` 即源码解析，但仅覆盖 edit 族）或运行时 `tools/list` 实测；两法各有覆盖面（8 个 `UnadvertisedTools` 测试工具永不入 tools/list）。且代码内嵌过期计数会污染"由注册表导出"的文档初稿：`EditToolProvider.cs` edit_apply 描述字符串硬编码 "one of the **26** structured metadata/body operations"（实测 `OperationKinds`＝**37**），`README.md:77` "22 typed operations"——ACC-022 的机械核对若以导出快照为基准，会把 description 内的错误计数一并复制进 MCP-TOOLS 文档，与"数量来自注册表"目标自相矛盾。
